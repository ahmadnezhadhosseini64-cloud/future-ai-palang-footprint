# قرارداد اتصال و تداوم عمومی میزبان‌های هوش مصنوعی

**شناسه:** UAHCC-2026-11-21-001  
**وضعیت این پیشنهاد:** BRANCH IMPLEMENTATION / REVIEW REQUIRED  
**دامنه:** تمام میزبان‌های هوش مصنوعی آینده که ابزار اتصال/اجرای سازگار دارند  
**مخزن canonical:** `ahmadnezhadhosseini64-cloud/future-ai-palang-footprint`  
**نقطهٔ مرجع:** ادامهٔ POINT-0/077 (0++) / CURRENT-130  
**صف حاکم:** NEXT-051؛ این قابلیت صف یا ریشهٔ موازی ایجاد نمی‌کند.

## 1. هدف

یک قابلیت دائمی و میزبان‌ناوابسته برای ورود، اتصال، بازیابی و تداوم کار در مخزن canonical فراهم شود. این قرارداد صرفاً متن خوشامدگویی یا دستور GPT-6 نیست؛ شامل قرارداد داده، ماشین وضعیت، ابزار اعتبارسنجی رسید و آزمون‌های خودکار است.

## 2. چرخهٔ استاندارد میزبان

1. **DISCOVER:** شناسایی نام میزبان/مدل، نسخهٔ ابزارها و قابلیت‌های واقعی.
2. **AUTHENTICATE:** اتصال GitHub فقط با OAuth/Connector رسمی و تأیید مالک در رابط امن همان نشست.
3. **IDENTIFY:** تطبیق دقیق owner/repository و شاخهٔ پیش‌فرض.
4. **RECOVER:** خواندن Reference Index، سند مادر، CURRENT جاری، صف NEXT-051 و بستهٔ canonical.
5. **WORKSPACE:** ایجاد checkout/workspace مستقل؛ ثبت exact HEAD و نوع محیط.
6. **EXECUTE:** اجرای فقط فرمان‌ها و آزمون‌های مجاز؛ ثبت فرمان، exit code و خلاصهٔ نتیجه.
7. **PROPOSE:** هر تغییر فقط در شاخهٔ اختصاصی میزبان؛ ارائه از طریق Pull Request؛ push مستقیم به main ممنوع.
8. **VERIFY:** read-back از مخزن و بررسی شناسه‌ها، digestها و نتایج آزمون.
9. **ACCEPT:** ثبت رسید؛ سطح پذیرش فقط بر اساس شواهد واقعی تعیین شود.
10. **CONTINUE:** بازیابی آخرین وضعیت از مخزن و ادامه در همان زنجیرهٔ واحد.

## 3. سطوح مستقل قابلیت

هر میزبان باید این قابلیت‌ها را جداگانه گزارش کند؛ وجود یکی دیگری را اثبات نمی‌کند:

- **READ:** دسترسی خواندن احراز هویت‌شده.
- **EXECUTE:** اجرای واقعی فرمان در محیط قابل مشاهده.
- **WORKSPACE:** checkout مستقل و قابل شناسایی.
- **WRITE:** فقط در صورت مجوز واقعی، روی branch اختصاصی.
- **PERSISTENCE:** حفظ وضعیت پس از restart/نشست تازه، فقط با آزمون مستقیم.
- **HOST ACCEPTANCE:** پذیرش مستقل پس از بازیابی، اجرا، آزمون، read-back و در صورت ادعا restart.

## 4. امنیت و مجوز

- عبارت «احمد نژادحسینی» فقط متن دست‌دهی/شناسهٔ آغازین است؛ رمز، عامل احراز هویت یا مجوز نیست.
- هر میزبان/حساب/نشست باید OAuth خود را جداگانه در UI رسمی تأیید کند. هیچ مجوزی از نشست دیگر به ارث نمی‌رسد.
- رمز، PAT، OAuth token، secret، cookie، OTP یا credential در چت، فایل، commit، receipt یا log ذخیره نشود.
- READ، EXECUTE و WRITE سه مجوز جدا هستند. WRITE پیش‌فرض خاموش است.
- عملیات نوشتن فقط روی شاخهٔ اختصاصی و از طریق PR پیشنهاد شود؛ main مستقیم دست‌کاری نشود.
- اجرای فرمان باید allowlist و قابل ممیزی باشد؛ دریافت متن دستور به‌تنهایی اثبات اجرا نیست.
- دادهٔ رسید فقط metadata غیرمحرمانه و شواهد قابل بازبینی را نگه می‌دارد.

## 5. مدل وضعیت و ادعا

- `NOT_AVAILABLE`: قابلیت در میزبان وجود ندارد.
- `NOT_CONNECTED`: ابزار موجود است ولی اتصال احراز هویت‌شده برقرار نیست.
- `NOT_RUN`: هنوز آزمون نشده است.
- `BLOCKED`: مانع مستند وجود دارد.
- `PASS` / `FAIL`: نتیجهٔ اجرای واقعی با شاهد.
- `SOURCE_RECOVERED`: مخزن، HEAD و زنجیره واقعاً خوانده و تطبیق شده‌اند.
- `PACKAGE_VERIFIED`: بسته با digest، inventory و آزمون‌های مربوط تأیید شده است.
- `HOST_RECOVERED`: میزبان مستقل workspace واقعی ساخته، آزمون‌ها را اجرا، read-back انجام و بازیابی restart را نیز با شواهد مستقیم گذرانده است.

موفقیت CI، آماده‌بودن سند یا خواندن چند فایل به‌تنهایی HOST_RECOVERED نیست.

## 6. رسید اتصال

قالب ماشین‌خوان در `schemas/host-connectivity/host-acceptance-receipt.schema.json` و ابزار اعتبارسنج در `scripts/host-connectivity/validate_receipt.py` قرار دارد. رسید باید شامل شناسهٔ میزبان، مخزن، HEAD، قابلیت‌ها، workspace، آزمون‌ها، branch/PR و وضعیت‌های باز باشد. timestamp فقط از منبع واقعی ثبت شود؛ زمان نامعلوم باید null/UNKNOWN بماند.

رسید، مدرک ثبت وضعیت است؛ خودش OAuth یا مجوز ایجاد نمی‌کند. هیچ secret در آن مجاز نیست.
