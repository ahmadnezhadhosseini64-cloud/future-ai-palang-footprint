## Purpose
Ensure that approved valuable productions are not lost when final Repository persistence is unavailable, and ensure that pending items can later be reconciled, registered, retrieved, and verified without duplicate or false registration.

## Core Rule
No Repository Access → No Loss.

Repository availability is not the definition of knowledge existence. A temporary failure of GitHub, an integration, a tool, or another persistence target may block formal registration, but must not erase an approved production.

## Lifecycle
APPROVED → PENDING_REGISTRATION → RECHECK → RECONCILE → REGISTER → RETRIEVE → VERIFY → ACTIVE

Failure during registration or verification returns the item to an appropriate pending/investigation state rather than falsely marking it active.

## Stable Identity
A pending item retains one permanent Registration ID. Repeated registration attempts are recorded as attempts/events and must not create duplicate artifacts.

## Reconciliation
Before re-registering after an outage, compare the Pending Registry with the target Repository to detect items that were already registered, partially registered, conflicting, or missing. Reconciliation precedes blind retry.

## Error Classification
Errors should be classified where possible, including:
- 403 / access or integration permission
- 404 / repository or path problem
- conflict / reconciliation required
- network or transient failure / retryable
- invalid content / review required
- verification failure / investigate

Retry behavior must depend on the error class.

## Priority
Pending items may carry priority such as CRITICAL, HIGH, NORMAL, or LOW. Priority affects processing order only and must never justify deletion or abandonment of lower-priority items.

## Tool Independence
The Registration Recovery & Reconciliation Layer is independent of any single Repository provider. GitHub is a persistence target, not the architectural definition of the recovery mechanism.

## Verification Gate
Successful write is not sufficient. An item becomes officially registered/active only after:
REGISTER → RETRIEVE → VERIFY.

## Relation to Recovery Buffer
Recovery Buffer preserves approved productions during persistence failure. This layer governs their later recheck, reconciliation, registration, retrieval, verification, and transition to ACTIVE.
