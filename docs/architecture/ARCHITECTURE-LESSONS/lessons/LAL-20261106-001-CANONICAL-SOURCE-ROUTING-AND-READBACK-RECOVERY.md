## 1. خلاصهٔ درس

وقتی کاربر می‌گوید یک سند در مخزن پروژه وجود دارد، جست‌وجو در فضای فایل‌های ChatGPT یا Library به‌تنهایی پاسخ‌گوی درخواست نیست. «مخزن GitHub» و «Library گفتگو» دو مقصد مستقل با نمایه‌ها، مسیرها و شواهد جداگانه‌اند. پیدا نشدن فایل در یکی، نبودن آن در دیگری را ثابت نمی‌کند.

در این مورد، تلاش‌های ابتدایی به‌اشتباه روی Library متمرکز شد و نسخه‌ای قدیمی/نامرتبط دیده شد؛ در حالی که نسخهٔ نهایی از ابتدا در مسیر مشخص GitHub موجود بود. بازیابی درست با خواندن مستقیم فایل از مسیر دقیق در شاخهٔ `main` انجام شد. سپس جست‌وجوی مخزن، دو سند راهنمای پوشه را آشکار کرد که نگاشت رسمی نام کوتاه «۲ زبانه آخر» به مسیر قطعی را تعریف می‌کردند.

## 3. روش عملیاتی استاندارد

1. **تشخیص مقصد از قصد کاربر:** اگر کاربر می‌گوید «در مخزن/پروژه/GitHub ذخیره شده»، منبع اصلی را مخزن تعیین کن؛ Library را مقصدی جداگانه تلقی کن.
2. **خواندن نقشهٔ رسمی پیش از جست‌وجوی پراکنده:** README پوشه، فهرست بازیابی و Reference Index مرتبط را بخوان.
3. **تبدیل نام کوتاه به مسیر canonical:** نام‌هایی مانند «گواهی آخر»، «چکیده آخر» و «۲ زبانه آخر» را با نگاشت رسمی به مسیر دقیق وصل کن؛ شباهت عنوان را معیار کافی ندان.
4. **بازیابی کامل از مقصد درست:** فایل را از شاخه/نسخهٔ مشخص با fetch مستقیم بخوان؛ قطعهٔ جست‌وجو یا عنوان فایل، جایگزین محتوای کامل نیست.
5. **بازخوانی و تطبیق:** متن کامل، مسیر، branch، blob SHA، شناسه‌ها و ویژگی‌های کلیدی سند را بررسی کن.
6. **در صورت شکست، راهبرد را عوض کن:** اگر مسیر معلوم نیست، جست‌وجوی درون همان مخزن را با نام دقیق، عبارت‌های عنوان و شناسه‌ها انجام بده؛ سپس راهنمای رسمی کشف‌شده را fetch کن و دوباره مسیر قطعی را بخوان.
7. **گزارش مرز شواهد:** وجود فایل، خواندن فایل، تطبیق محتوا، ثبت تغییر و آزمون میزبان مستقل، وضعیت‌های جدا هستند.
8. **حفظ تاریخچه:** نسخهٔ قدیمی یا فایل هم‌نام را بدون اجازهٔ کاربر بازنویسی/حذف نکن؛ فقط سند متناظر با نام درخواستی را ارائه کن.

## 4. درخت تصمیم کوتاه

- درخواست «از مخزن» → GitHub repository first.
- درخواست «از Library/فایل‌های گفتگو» → Library first.
