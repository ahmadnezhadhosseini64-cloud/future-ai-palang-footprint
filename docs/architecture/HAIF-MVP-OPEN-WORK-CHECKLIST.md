# HAIF MVP — چک‌لیست زندهٔ کارهای باز و مسیر رشد

**وضعیت:** ACTIVE / LIVING — فهرست اجرایی، نه گواهی تکمیل  
**دامنه:** پایهٔ مدل اولیه، پیام واحد، بستهٔ قابل‌انتقال، میزبان مستقل و رشد کنترل‌شده  
**قانون:** هر مورد فقط با شاهد و read-back واقعی بسته می‌شود. «مستند شده» با «اجرا شده» یکی نیست.

## اصل محصول
یک پیام واحد + یک بستهٔ تجمیع‌شده → بازیابی وضعیت از مخزن → محیط مستقل میزبان → اجرای کار واقعی → آزمون و تحویل خروجی → بررسی مالک → رشد کنترل‌شده.

## ۶. کارهای زیرساختی و اولویت‌های بعدی

- [ ] **P0 — بستهٔ ZIP واقعی:** build، دانلود artifact، inventory، SHA-256، استخراج پاک و تست مجدد.
- [ ] **P0 — پیام واحد نهایی:** تطبیق متن پیام با بسته و مسیرهای جاری main/candidate.
- [ ] **P0 — اولین میزبان مستقل:** اجرای واقعی ورود و رسید؛ اگر ابزار میزبان workspace ندارد، مانع دقیق ثبت شود.
- [ ] **P1 — چک‌لیست میزبان‌محور:** انتخاب و واگذاری اولین کار مستقل با خروجی قابل‌سنجش.
- [ ] **P1 — ثبت و بازیابی پایدار:** آزمون restart و import/export.
- [ ] **P1 — ثبت خودکار تعاملات:** فقط پس از یافتن API/hook مجاز؛ فعلاً ادعای خودکار بودن ممنوع.
- [ ] **P1 — مسیر promotion به CHILD:** بررسی مالک‌محور، بدون مسیر نوشتن میزبان به MASTER.
- [ ] **P1 — آزمون تعارض چندمیزبانی:** دو workspace مستقل و reconciliation.
- [ ] **P2 — اتصال‌های بیرونی:** فقط وقتی نیاز عملی مشخص شد؛ نه پیش‌شرط MVP.
- [ ] **P2 — رابط کاربری:** پس از اثبات چرخهٔ ورود، اجرا، ذخیره و بازیابی؛ نه پیش از آن.

## ۷. کارهای صریحاً خارج از مسیر بحرانی فعلی

Buffer، Dropbox، mirror و اتصال‌های بیرونی تا زمانی که یک نیاز مشخص و اولویت‌دار را حل نکنند، پیش‌شرط ساخت MVP یا ورود میزبان نیستند. بررسی آن‌ها نباید جای بستهٔ واحد، فضای مستقل و آزمون میزبان را بگیرد.

## قانون به‌روزرسانی
در هر چرخه فقط وضعیت مواردی را تغییر بده که شاهد تازه دارند. مورد بسته‌شده باید SHA، آزمون و read-back داشته باشد. موارد نامعلوم را OPEN / NOT VERIFIED نگه دار. این فایل تنها چک‌لیست اجرایی MVP است؛ چک‌لیست موازی نساز.

## نقطهٔ اتصال 0++ — ورود دومرحله‌ای میزبان (گفت‌وگوی مالک، 2026-11-24)

**جایگاه:** ادامهٔ POINT-0/GOLDEN؛ متصل به مسیر اجرایی CURRENT-145 → NEXT-051 و کار نامزد PR #147. این یادداشت ریشه، صف یا معماری موازی ایجاد نمی‌کند و جایگزین زنجیرهٔ رسمی IN/OUT/EVT/TIME/CURRENT نیست.

**دستور مالک:** ورود میزبان باید دو مرحلهٔ جدا و تحت کنترل مالک داشته باشد:

1. **پیام اول — ورود فقط‌خواندنی:** میزبان مخزن و بسته را می‌خواند، baseline و SHA واقعی را بازیابی می‌کند، اسناد مرجع و وضعیت جاری را می‌خواند، توانایی‌های واقعی محیطش را گزارش می‌دهد و رسید ورود می‌سازد. در این مرحله هیچ مجوز نوشتن یا شناسهٔ فعال میزبان صادر نمی‌شود.
2. **پیام دوم — فعال‌سازی پس از تأیید مالک:** فقط پس از بررسی رسید مرحلهٔ اول، مالک برای همان میزبان شناسه و فضای کاری مستقل تعیین می‌کند و محدودهٔ مجاز نوشتن/اجرا را مشخص می‌سازد. مجوز باید با کنترل واقعی مخزن/فضای کاری اعمال شود؛ متن پیام به‌تنهایی کنترل امنیتی نیست.
3. **کار و بازگشت:** میزبان فقط در فضای اختصاص‌یافته کار می‌کند، آزمون و read-back انجام می‌دهد و خروجی و رسید قابل‌راستی‌آزمایی تحویل می‌دهد. ادغام در MASTER/main فقط با بررسی و تصمیم مالک انجام می‌شود.

**قیود قطعی:** میزبان هرگز دسترسی نوشتن مستقیم یا غیرمستقیم به MASTER/main و RAHM ندارد؛ هیچ میزبان حق صدور Host ID برای خودش را ندارد؛ عبارت «احمد نژادحسینی» شناسهٔ اعلام مالکیت/شروع فرایند است، نه رمز یا مجوز دسترسی.

**آزمون‌های لازم پیش از ادعای موفقیت:**
- مرحلهٔ اول در یک میزبان واقعاً تازه اجرا شود و SHA و فایل‌های خوانده‌شده با مخزن تطبیق داده شوند.
- بدون پیام دوم، تلاش نوشتن در هسته رد شود.
- پس از پیام دوم، نوشتن فقط در فضای مستقل تعیین‌شده موفق شود و نوشتن خارج از آن رد شود.
- شناسه و فضای کاری به همان میزبان و همان رسید متصل باشند؛ میزبان دیگر نتواند از آن‌ها استفاده کند.
- پس از restart، فضای کاری و رسید بازیابی شوند.
- خروجی با آزمون، SHA و read-back تحویل شود؛ فقط مالک بتواند آن را برای ادغام پیشنهاد کند.

**وضعیت فعلی:** DESIGN INTENT RECORDED / IMPLEMENTATION NOT VERIFIED. این یادداشت اثبات نمی‌کند که مدل اکنون اجرا می‌شود یا محدودیت GitHub برقرار شده است. امکان‌پذیری باید با نمونهٔ واقعی و آزمون مثبت/منفی ثابت شود. اگر محیط میزبان یا سطح دسترسی GitHub نتواند جداسازی واقعی را فراهم کند، همان‌جا مانع فنی ثبت می‌شود؛ راه‌حل نمایشی یا ادعای موفقیت پذیرفته نیست.

**تعهد اجرایی:** PR #147 باید این مدل دومرحله‌ای را در مسیر MVP پوشش دهد یا صریحاً به‌عنوان مانع باز ثبت کند. پیش از اثبات آزمون‌ها، نسخه نهایی/قابل‌استفاده اعلام نشود.
