## 1. قاعدهٔ دائمی

از این پس، در هر ثبت مهم پروژه، مستندسازی، سند مرجع، بازخوانی، تطبیق، راستی‌آزمایی، رویداد، لنگر ۰.۰، خروجی دستیار یا ورودی کاربر، **زمان عملیات دستیار/سیستم باید ثبت شود** و زمان اصلیِ لنگر عملیاتی است. نبودن زمان دقیق پیام کاربر هرگز دلیل حذف زمان عملیات دستیار نیست.

## 2. قالب ثبت زمان

هر زمان که منبع زمانی معتبر در دسترس باشد، زمان را به شکل زیر ثبت کن:

- `Assistant/System operation time / زمان عملیات دستیار-سیستم: YYYY-MM-DDTHH:mm:ss+03:30`
- `UTC equivalent / معادل UTC: YYYY-MM-DDTHH:mm:ssZ`
- `Timezone / منطقهٔ زمانی: Asia/Tehran (+03:30)`
- `Time source / منبع زمان: system time widget / trusted execution timestamp / repository commit timestamp`
- `Timestamp scope / دامنهٔ زمان: operation-start, write/commit, read-back, audit`

زمان عملیات را به وقت تهران تبدیل و نمایش بده؛ اگر زمان UTC یا زمان commit نیز در دسترس است، آن را نیز نگه دار تا تبدیل قابل بررسی باشد. هر مرحلهٔ دارای زمان مستقل—شروع عملیات، ثبت در مخزن، بازخوانی، ممیزی—باید زمان خودش را داشته باشد؛ زمان شروع را به‌جای زمان commit یا read-back جا نزن.

## 3. دو زمان، اگر هر دو موجود باشند

اگر زمان دقیق ورودی کاربر واقعاً از فرادادهٔ قابل اتکا یا خود پیام در دسترس باشد، هر دو ثبت شوند:

1. `User message time / زمان پیام کاربر`
2. `Assistant/System operation time / زمان عملیات دستیار-سیستم`

همراه هرکدام منطقهٔ زمانی و منبع ثبت شود. اختلاف زمانی فقط وقتی محاسبه شود که هر دو زمان قابل اتکا و قابل مقایسه باشند؛ مقدار اختلاف با واحد و جهت روشن (مثلاً «عملیات 4 دقیقه پس از پیام») نوشته شود. اگر زمان پیام کاربر موجود نیست، مقدار `UNKNOWN / UNAVAILABLE` ثبت می‌شود، اما زمان دستیار همچنان باید ثبت شود.

## 4. جلوگیری از جعل و اختلاط زمان‌ها

- تاریخ ثبت سند، زمان ارسال پیام، زمان شروع کار، زمان commit و زمان بازخوانی مفاهیم جدا هستند.
- زمان commit مخزن نباید به‌عنوان زمان پیام کاربر معرفی شود.
- اگر منبع دقیق زمان در دسترس نیست، همان فیلد با علت `UNAVAILABLE / NOT CAPTURED` مشخص شود؛ زمان ساختگی درج نشود.
- اگر فقط تاریخ روز در دسترس است، تاریخ روز و دقت واقعی آن اعلام شود؛ ثانیه یا دقیقه حدس زده نشود.
- زمان ابزار معتبر، در صورت ارائه، باید دقیقاً با منطقهٔ زمانی مشخص ثبت شود؛ زمان محلی تهران معادل UTC را می‌توان با اختلاف رسمی منطقه محاسبه کرد.
- در ثبت‌های تاریخی، اطلاعات زمانِ جدید نباید وانمود کند که زمان قدیمی از ابتدا ثبت شده بوده است؛ زمان افزوده‌شده با منبع و زمان ثبت اصلاحیه مشخص شود.

## 5. لنگر مستقل هر ورودی و خروجی

هر ورودی/خروجی مهم باید حداقل شامل این موارد باشد: شناسهٔ پایدار، شناسهٔ تولید، نسخه، تاریخ و زمان عملیات دستیار به وقت تهران، معادل UTC، منطقهٔ زمانی، منبع زمان، زمان پیام کاربر اگر در دسترس است، اختلاف دو زمان اگر قابل محاسبه است، منشأ، پیوند به لنگر والد، شواهد، محدودیت، وضعیت، مقصد ذخیره‌سازی و اقدام بعدی.

`CAPTURE TIME → WRITE → READ-BACK → MATCH → VERIFY → RECORD READ-BACK TIME → STATUS`

معنی: ثبت زمان معتبر → نوشتن → بازخوانی → تطبیق → تأیید → ثبت زمان بازخوانی → تعیین وضعیت.
