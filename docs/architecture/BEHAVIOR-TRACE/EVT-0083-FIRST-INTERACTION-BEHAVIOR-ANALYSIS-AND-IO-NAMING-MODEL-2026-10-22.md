## 1. نام رویداد و دامنه
**نام رسمی:** «رویداد نخستِ دریافت ورودی، تحلیل رفتار دوسویه، تولید خروجی و ایجاد الگوی معماری زنده»  
**نام کوتاه:** `FIOBAM` — First Interaction Observation & Behavior Architecture Model («مدل نخست مشاهدهٔ تعامل و معماری رفتار»).

این رویداد درخواست کاربر برای تحلیل رفتار ورودی و خروجی دستیار، نام‌گذاری کل چرخه، ساخت مدل قابل رشد، شماره‌گذاری زوج‌های ورودی/خروجی، و پیوند دادن آن‌ها به سند مرجع و لنگر مستقل را ثبت می‌کند. ثبت، شواهد همین تعامل قابل مشاهده را پوشش می‌دهد؛ ادعای ثبت خودکار همهٔ تعاملات آینده در هر میزبان نیست.

## 2. بازسازی رفتار همین تعامل
### ورودی کاربر — مشاهدهٔ مستقیم
کاربر خواست:
1. ورودی خودش و خروجی دستیار رفتارشناسی شوند.
2. قالب معماری پروژه به الگو و مدل تبدیل شود.
3. لنگر زمانی و لنگر مستقل ساخته و فعال نگه داشته شوند.
4. کل چرخهٔ ورودی/خروجی نخست نام‌گذاری و به‌صورت رویداد ثبت شود.
5. قاعدهٔ نام‌گذاری و شماره‌گذاری ورودی‌ها و خروجی‌های بعدی ساخته شود.
6. مدل رفتاری تعاملی، قابل رشد و توسعه، با سند مرجع کامل زنده ثبت شود.

### پاسخ/رفتار دستیار — فقط بر مبنای خروجی قابل مشاهده
- بازیابی زمینهٔ پروژه و اسناد قبلی مرتبط انجام شد.
- شماره‌های EVT-0076، EVT-0077، EVT-0078 و EVT-0081 قبلاً استفاده شده‌اند؛ بنابراین از استفادهٔ مجدد آن‌ها اجتناب شد و شمارهٔ بعدی پس از بررسی، EVT-0083 انتخاب شد.
- مدل نام‌گذاری زوجی و معماری رویداد/شاهد/لنگر/سند مرجع تعریف می‌شود.
- محدودیت مهم: زمان دقیق میزبان برای دریافت پیام و زمان تولید پاسخ مستقل از commit در این محیط قابل اثبات نیست؛ این فیلدها نباید با زمان commit جایگزین شوند.

## 3. تحلیل رفتاری و رابطهٔ علت‌ومعلولی
- **نیاز ورودی:** استمرار، قابلیت بازیابی، ردیابی دقیق رفتار و جلوگیری از گم‌شدن ارتباط ورودی با خروجی.
- **رفتار مورد انتظار دستیار:** حفظ متن/معنای ورودی، تفکیک مشاهده از تفسیر، ساخت شناسهٔ پایدار، ثبت شاهد، نوشتن و بازخوانی، سپس اعلام محدودیت‌ها.
- **ریسک رفتاری:** ادعای «ثبت شد» بدون اثبات مقصد؛ ساخت زمان یا شمارهٔ تکراری؛ یکی گرفتن بررسی با موفقیت؛ ادعای اجرای پس‌زمینه یا خودکارسازی اثبات‌نشده.
- **قاعدهٔ اصلاحی:** هر ادعا باید برچسب منشأ داشته باشد؛ هر مقصد وضعیت مستقل دارد؛ هر عملیات مهم شاهد مستقل دارد؛ هر لنگر تازه افزایشی است و لنگر قبلی را نمی‌بندد.
- **مرز استنباط:** این تحلیل، الگوی رفتار مشاهده‌شده و الزامات درخواستی را توصیف می‌کند، نه دسترسی به زنجیرهٔ تفکر پنهان دستیار.

## 4. قرارداد نام‌گذاری و شماره‌گذاری
### شناسهٔ زوج تعامل
برای هر چرخهٔ کاربر/دستیار یک شناسهٔ زوج بساز:
- `INT-YYYYMMDD-NNN` — شناسهٔ تعامل؛ تاریخ بر اساس تاریخ ثبت/بازهٔ ثبت معتبر و شمارهٔ ترتیبی یکتا.
- `IN-YYYYMMDD-NNN` — ورودی کاربر متناظر با همان زوج.
- `OUT-YYYYMMDD-NNN` — خروجی قابل مشاهدهٔ دستیار متناظر با همان زوج.
- `EVT-NNNN-SLUG-YYYY-MM-DD` — رویداد مستقل معماری.
- `PALANG-[TOPIC]-0.0-YYYY-MM-DD-NNN` — لنگر مستقل بازیابی.
- `PALANG-[TOPIC]-LIVING-REFERENCE-YYYY-MM-DD-NNN` — شناسهٔ سند مرجع زنده.
- `Production ID` برای زنجیرهٔ تولید/ثبت مستقل می‌ماند؛ با Stable ID یا EVT کوتاه یکی فرض نشود.

### قواعد یکتایی
1. پیش از تخصیص EVT، جست‌وجوی مخزن برای شماره و نام پیشنهادی الزامی است؛ شمارهٔ موجود هرگز دوباره استفاده نشود.
2. شمارهٔ NNN برای زوج‌های تعامل در محدودهٔ همان تاریخ از آخرین شمارهٔ تأییدشده ادامه یابد؛ اگر شمارندهٔ قابل‌اعتماد وجود ندارد، شناسهٔ غیرتکراری با شناسهٔ پایدار/UUID ثبت و شکاف شمارنده باز بماند؛ شماره از روی حدس انتخاب نشود.
3. IN و OUT همیشه NNN مشترک دارند و یک زوج‌اند؛ اگر خروجی هنوز تولید نشده یا ثبت نشده، وضعیتش `PENDING` است و زوج کامل اعلام نمی‌شود.
4. اصلاح/تکرار خروجی، نسخه را افزایش می‌دهد؛ رویداد تازه فقط وقتی لازم است که اتفاق/تصمیم جدید مستقلی رخ داده باشد.
5. تاریخ نام فایل، تاریخ رویداد یا تاریخ ثبت را بدون برچسب با یکدیگر جایگزین نکن.
6. اگر زمان دقیق پیام در دسترس نیست، `user_message_time = UNKNOWN / NOT CAPTURED`; زمان commit واقعی همان فایل به‌عنوان زمان ثبت مخزن ثبت می‌شود.

## 5. مدل رفتاری قابل رشد
`CAPTURE → CLASSIFY → PAIR → IDENTIFY → PROVENANCE → TEMPORAL ANCHOR → EVIDENCE → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → REGISTER LINKS → RESUME → LEARN`

ترجمه: دریافت → دسته‌بندی → زوج‌سازی → شناسه‌گذاری → منشأ → لنگر زمانی → شاهد → نوشتن → بازخوانی → تطبیق → راستی‌آزمایی → رفع تعارض → پیونددهی → ادامه → یادگیری معماری.

هر مورد جدید می‌تواند نوع ورودی/خروجی، برچسب رفتاری، فرضیه، شاهد، آزمون، GAP، تصمیم و نسخهٔ مدل را گسترش دهد؛ اما فقط پس از ثبت منشأ و شاهد. تغییر مدل باید نسخه‌دار و قابل بازگشت باشد.

## 6. حداقل ساختار داده
`interaction_id, input_id, output_id, event_id, stable_id, production_id, version, input_observation, output_observation, behavior_tags[], interpretation[], claims[], evidence_refs[], timestamps{user_message_time, repository_commit_utc, tehran_derived}, parent_ids[], destination_statuses[], open_gaps[], next_action, readback_result, match_result, verification_status`.

هر فیلد زمانی باید منبع و معنای خود را مشخص کند. UTC معیار زمان ثبت مخزن است و معادل تهران از همان instant مشتق می‌شود. زمان پیام، اگر قابل دسترس نباشد، ناموجود می‌ماند.

## 8. مقصدها و محدودیت‌ها
- Repository: این رویداد در مخزن ثبت می‌شود؛ موفقیت نهایی فقط پس از بازخوانی قابل اعلام است.
- Gmail: در سابقهٔ اخیر BLOCKED / NOT SENT؛ این رویداد ایمیلی ارسال نمی‌کند.
- Library / Buffer / Persistent Memory: نیازمند شاهد مستقل برای همین ثبت.
- Dropbox: OPEN / NOT VERIFIED؛ آزمون اتصال/نوشتن/بازیابی هنوز جداگانه لازم است.
- زمان دقیق پیام و تولید خروجی در میزبان: UNKNOWN / NOT CAPTURED.
- زمان ثبت مخزن: از commit واقعی همین فایل پس از نوشتن استخراج شود.

## 9. گام ادامه
1. سند مرجع و لنگر مستقل را بنویس و بازخوانی کن.
2. مدل را به معماری اولیهٔ اپ و نمایهٔ رویدادها پیوند بده.
3. در گام بعد، دفتر زوج‌های تعامل را به‌صورت دادهٔ قابل آزمون (JSON Schema و نمونهٔ JSON) تعریف کن.
4. آزمون بازیابی باید از `INT/IN/OUT` به EVT، سند مرجع و لنگر برسد و پس از شروع مجدد نیز همان زنجیره را بازیابی کند.
5. خودکارسازی زندهٔ دریافت همهٔ پیام‌ها فقط پس از اتصال producer/runtime و آزمون مستقل قابل اعلام است.
