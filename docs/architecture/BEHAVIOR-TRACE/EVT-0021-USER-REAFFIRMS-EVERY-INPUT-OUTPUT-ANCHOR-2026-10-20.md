## منشأ و درخواست
کاربر صریحاً تأکید کرد که قاعدهٔ ثبت‌شده در مخزن باید از این پس برای هر ورودی کاربر و هر خروجی دستیار اجرا شود؛ هر رویداد باید لنگر، مستندسازی، ثبت زمانی با منشأ، قواعد حاکم، وضعیت واقعی و مسیر بازیابی داشته باشد. این درخواست، تأیید دوبارهٔ اجرای قرارداد موجود است، نه جایگزینی لنگرهای قبلی.

## قاعده اجرایی لازم
1. هر ورودی کاربر و هر خروجی دستیار به‌عنوان رویداد قابل‌ردیابی بررسی شود و به لنگر جاری/رویدادهای مرتبط متصل گردد.
2. برای گفت‌وگوی ساده، رکورد فشردهٔ قابل‌بازیابی کافی است؛ برای تصمیم، قاعده، اصلاح، اقدام یا خروجی بادوام، رکورد کامل و در صورت نیاز سند مرجع ایجاد یا نسخه‌دار به‌روزرسانی شود.
3. منشأ، ارتباط با رویدادهای قبلی، Stable ID، Production ID، نسخه، تاریخ، منطقه زمانی، شاهد زمان، وضعیت، محدودیت‌ها و اقدام بعدی حفظ شود.
4. زمان دقیق پیام فقط در صورت وجود شاهد ثبت شود؛ در غیر این صورت UNKNOWN / UNVERIFIED بماند. زمان commit فقط زمان ثبت مخزن را اثبات می‌کند و جای زمان پیام را نمی‌گیرد.
5. اجرای مخزن: WRITE → READ-BACK → MATCH → VERIFY (نوشتن ← بازخوانی ← تطبیق ← تأیید). هر فایل تغییرکرده پس از نوشتن بازخوانی و محتوای مورد انتظار با آن تطبیق داده شود.
6. وضعیت Repository، Library، Buffer، Persistent Memory و Dropbox جداگانه ثبت شود. اثبات یک مقصد، اثبات مقصد دیگر نیست.
7. هیچ ادعای «ثبت شد»، «کامل شد»، «زنده شد» یا «فعال شد» بدون شاهد متناسب مجاز نیست.
8. لنگرهای ۰.۰ قبلی و لنگر مستقل Dropbox حذف، ادغام یا بسته نشوند مگر با دستور روشن کاربر و شواهد لازم.
9. اگر ثبت یا بازخوانی ممکن نبود، کار با وضعیت OPEN / BLOCKED / PENDING حفظ شود و بستهٔ کامل قابل‌بازیابی برای ادامه ارائه گردد؛ گزارش صرف جایگزین اجرای واقعی نیست.
