# EVT-0081 — لنگر زمانی جایگزین + شواهد مستقل هر مرحله

## 1. منشأ و علت ثبت
کاربر یادآوری کرد که دو قاعده باید هم‌زمان و یکپارچه اجرا شوند؛ پاسخ قبلی لنگر جایگزین را توضیح داده بود، اما اتصال صریح آن به ثبت مستقل شواهد هر مرحله را به‌اندازهٔ کافی روشن و عملیاتی نکرده بود. این رویداد اصلاحی، تاریخچهٔ قبلی را حذف یا بازنویسی نمی‌کند.

## 2. دو تعهد هم‌زمان و حاکم

### تعهد A — لنگر زمانی جایگزین
- اگر زمان واقعی پیام کاربر از فرادادهٔ معتبر قابل‌دسترسی نیست، فیلد زمان پیام با `UNAVAILABLE / NOT CAPTURED` باقی می‌ماند.
- برای آنکه ثبت بی‌لنگر نماند، زمان واقعی commit همان رکورد در مخزن به‌عنوان `repository_registration_anchor` ثبت می‌شود.
- UTC مرجع اصلی است؛ معادل `Asia/Tehran (UTC+03:30)` از همان لحظهٔ واقعی commit به دست می‌آید و پس از UTC نمایش داده می‌شود.
- زمان ثبت مخزن هرگز به‌جای زمان پیام یا زمان وقوع رویداد جا زده نمی‌شود.
- زمان هر فایل، زمان بازخوانی و لنگر نهایی زنجیره از یکدیگر جدا هستند.

### تعهد B — شواهد مستقل برای هر مرحله
برای هر مرحله، رکورد شواهد جداگانه نگه داشته شود؛ یک timestamp یا موفقیت مرحلهٔ اول، شاهد مراحل بعدی نیست:
1. **WRITE / نوشتن:** مقصد، مسیر، شناسهٔ محتوا و نتیجهٔ عملیات.
2. **READ-BACK / بازخوانی:** منبع واقعی خواندن، زمان بازخوانی اگر قابل‌دسترسی باشد، مسیر و نتیجه.
3. **MATCH / تطبیق:** مقایسهٔ محتوا، شناسه، نسخه، پیوندها و در صورت امکان hash.
4. **VERIFY / راستی‌آزمایی:** آزمون، نتیجهٔ PASS/FAIL/BLOCKED/NOT RUN و شاهد.
5. **RECONCILE / تطبیق با معماری:** پیوند به سند مادر، لنگر ۰.۰، نمایه و صف مربوط.
6. **STATUS / وضعیت:** آنچه اثبات شده، آنچه باز مانده و اقدام بعدی.
7. **CHAIN FINAL / لنگر نهایی زنجیره:** commit واقعی نهایی‌کنندهٔ بسته، با UTC و معادل تهران؛ این لنگر جای شواهد تک‌مرحله‌ای را نمی‌گیرد.

هر شاهد باید به همان مرحله و همان مقصد نسبت داده شود. نتیجهٔ GitHub، اثبات Buffer، Persistent Memory، Library یا Dropbox نیست.

## 3. چرخهٔ الزامی ترکیبی
`PRESERVE → IDENTIFY → REPOSITORY TIME ANCHOR → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS`

ترجمه: حفظ → شناسایی → لنگر زمان ثبت مخزن → نوشتن → بازخوانی → تطبیق → راستی‌آزمایی → تطبیق معماری → اعلام وضعیت.

**قاعدهٔ دوگانه:** هیچ رکوردی بدون لنگر قابل‌بازیابی رها نشود؛ هیچ مرحله‌ای نیز بدون شاهد خودش موفق اعلام نشود.

## 4. قالب حداقلی ثبت زمان و شاهد
- `user_message_time`: زمان پیام از منبع معتبر، یا `UNAVAILABLE / NOT CAPTURED`.
- `repository_registration_anchor_utc`: زمان commit واقعی رکورد، UTC.
- `repository_registration_anchor_tehran`: معادل Asia/Tehran از همان commit.
- `file_commit_time`: زمان واقعی commit فایل مشخص.
- `readback_time`: فقط اگر زمان واقعی بازخوانی در دسترس باشد؛ در غیر این صورت نامعلوم.
- `stage_evidence[]`: یک رکورد مستقل برای هر مرحله، شامل نام مرحله، مقصد، نتیجه، شاهد/پیوند و محدودیت.
- `chain_final_anchor_utc` و `chain_final_anchor_tehran`: زمان commit واقعی نهایی‌کنندهٔ زنجیره.
- `limitations`: زمان‌ها یا شواهدی که واقعاً در دسترس نیستند.

زمان commit را برای پرکردن زمان بازخوانی، زمان پیام یا زمان رویداد استفاده نکن.

## 5. معیار پذیرش
- هر دو تعهد در یک زنجیره اجرا شده باشند.
- زمان UTC و معادل تهران بر پایهٔ commit واقعی و با منشأ مشخص باشند.
- زمان پیام ناموجود، ناموجود باقی بماند و جعل نشود.
- هر مرحله شاهد و نتیجهٔ جداگانه داشته باشد.
- نوشتن بدون بازخوانی، یا بازخوانی بدون تطبیق، ثبت کامل محسوب نشود.
- وضعیت مقصدها مستقل باشد.
- سند مرجع، لنگر ۰.۰ و نمایه به این رویداد پیوند داشته باشند و پس از ویرایش بازخوانی شوند.
