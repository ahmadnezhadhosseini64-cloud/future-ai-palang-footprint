## 1. هدف و معنای فرمان
از این نسخه به بعد، فرمان کاربر «خاک‌برداری» یا «خاک‌برداری کن» به معنی اجرای روتین کامل کشف، بازخوانی، بازیابی، تطبیق، تکمیل و راستی‌آزمایی کارهای باز پروژه است؛ نه صرفاً تهیه گزارش یا فهرست کارها. هر مرحله‌ای که ابزار، دسترسی و مجوز اجازه می‌دهد باید در همان اجرا واقعاً انجام شود. هر مرحلهٔ غیرقابل اجرا باید با مانع، شاهد آخرین مرحلهٔ موفق، مقصد باقی‌مانده و اقدام بعدی باز نگه داشته شود.

این قرارداد مکمل قرارداد مادر MRV، قرارداد فرمان «ثبت کن»، قرارداد UIALAC-2026-10-20-001 و پرونده EVERY-INPUT-OUTPUT-EXECUTION-GATES-2026-10-20-001 است؛ جایگزین هیچ‌کدام نیست.

## 2. دروازه‌های اجباری هر خاک‌برداری
1. بازیابی نسخهٔ جاری مخزن، نمایهٔ اسناد مرجع، صف معماری، پرونده‌های خاک‌برداری قبلی، دفتر شکاف‌ها و نقاط ۰.۰.
2. بازخوانی خود اسناد مقصد؛ به فهرست‌ها، خلاصه‌های گفتگو یا نتیجهٔ جست‌وجوی ناقص بسنده نکن.
3. شناسایی همهٔ پرونده‌های باز/ناقص/قطع‌شده/در انتظار/دارای شواهد متناقض؛ شناسه‌های تاریخی را حفظ کن و موردی را فقط به‌دلیل ایجاد قرارداد جدید کنار نگذار.
4. بررسی روابط هر مورد با سند مادر MRV، قرارداد حاکم «ثبت کن»، UIALAC، دفتر رفتار تعامل، صف یکپارچه‌سازی، شاخص مرجع و دفتر ۰.۰.
5. تعیین کار اجرایی بعدی برای هر مورد و اجرای واقعی آن، تا جایی که ابزار و مجوز موجود است؛ صرف بازنویسی وضعیت یا ساخت گزارش، اجرای کار محسوب نمی‌شود.
6. برای هر فایل/مقصد: WRITE → READ-BACK → MATCH → VERIFY (نوشتن ← بازخوانی ← تطبیق ← تأیید). پس از نوشتن، همان مقصد دوباره خوانده شود و محتوای مورد انتظار با محتوای خوانده‌شده تطبیق داده شود.
7. حل تکرارها با حفظ منشأ و تاریخچه؛ تعارض‌ها باید مستند و باز بمانند تا شواهد کافی فراهم شود.
8. به‌روزرسانی صف و شاخص‌ها با نتیجهٔ واقعی، شواهد، نسخه/commit و اقدام باقی‌مانده؛ سپس بازخوانی مجدد پیوندها و رکوردهای به‌روزشده.
9. ثبت نقطهٔ ادامهٔ قابل‌بازیابی در پایان هر اجرا؛ اگر همهٔ شروط تکمیل نشد، پرونده باز بماند.
10. گزارش پایانی فقط نتیجهٔ عملیات واقعی را خلاصه کند و جایگزین سند مرجع کامل و مسیر قابل بازیابی نشود.

## 3. مقصدهای مستقل که باید جداگانه بررسی شوند
- Repository / مخزن GitHub: مسیر دقیق، عملیات نوشتن، commit، بازخوانی و تطبیق محتوا.
- Reference Index / نمایه اسناد مرجع: وجود شناسه، پیوند صحیح و بازخوانی پس از تغییر.
- Architecture Integration Queue / صف یکپارچه‌سازی معماری: وضعیت پرونده، وابستگی‌ها، مقصدها و اقدام بعدی.
- Independent Reference Library / صندوق مستقل اسناد مرجع: وجود واقعی فایل در کتابخانهٔ مستقل و شاهد بازخوانی؛ مسیر مخزن GitHub به‌تنهایی کافی نیست.
- Buffer / بافر: ابتدا سازوکار واقعی بافر شناسایی شود؛ سپس ذخیره و بازیابی آن با شاهد. اگر سازوکار قابل دسترس نیست، UNVERIFIED / تأییدنشده ثبت شود.
- Persistent Memory / حافظهٔ پایدار: فقط بر اساس سازوکار واقعی حافظه و شواهد قابل مشاهده گزارش شود؛ commit مخزن اثبات حافظه نیست.
- Dropbox / دراپ‌باکس: اتصال، ذخیرهٔ آزمایشی، بازیابی همان داده و تطبیق دقیق؛ اتصال یا آزمون‌نشده بودن باید صریح باقی بماند.
- Master Reference / سند مرجع مادر: تطبیق معنایی و ساختاری با حفظ نقش سند مادر و تاریخچهٔ نسخه‌ها.
- Automation / خودکارسازی: وجود سند یا دستور به‌تنهایی اثبات اجرای خودکار روی هر ورودی/خروجی یا اجرای پس‌زمینه نیست؛ فقط آزمون اجرایی سرتاسری می‌تواند چنین ادعایی را پشتیبانی کند.

برای هر مقصد، وضعیت جداگانه ثبت شود: VERIFIED / تأییدشده، PARTIAL / ناقص، PENDING / در انتظار، BLOCKED / مسدود، UNAVAILABLE / در دسترس نیست، یا NOT VERIFIED / تأییدنشده. وضعیت یک مقصد به مقصد دیگر تعمیم داده نشود.

## 5. روش تکمیل کارهای ناقص
برای هر مورد:
1. هویت، شناسه، نسخه، منشأ، زنجیرهٔ والد/فرزند و آخرین وضعیت را بازخوانی کن.
2. آخرین مرحلهٔ واقعاً تکمیل‌شده و آخرین شاهد معتبر را تعیین کن.
3. مقصد دقیق و معیار پذیرش را مشخص کن.
4. تغییر لازم را در مقصد واقعی اعمال کن؛ در صورت نبود دسترسی، تغییر را انجام‌شده وانمود نکن.
5. همان مقصد را دوباره بخوان، محتوای مورد انتظار را تطبیق بده و شاهد ثبت کن.
6. سند مادر، صف، نمایه و دفتر مرتبط را در صورت نیاز به‌روزرسانی کن و هرکدام را جداگانه بازخوانی کن.
7. فقط وضعیت مرحله‌ای را ارتقا بده که شاهد دارد. پروندهٔ کلی تا تکمیل تمام تعهدهای لازم PARTIAL / PENDING می‌ماند.
8. اگر محدودیت باقی است، ثبت توقف باید شامل Last Completed Step / آخرین مرحلهٔ تکمیل‌شده، Last Verified Evidence / آخرین شاهد تأییدشده، Pending Destinations / مقصدهای باقی‌مانده، Blocking Constraint / مانع، Next Action / اقدام بعدی و Resume Pointer / مسیر ادامه باشد.

## 6. آزمون Dropbox
لنگر Dropbox بدون شواهد تازه باز می‌ماند. آزمون پذیرش باید این توالی را طی کند:
1. اتصال واقعی حساب/سرویس و دسترسی مجاز تأیید شود.
2. یک دادهٔ آزمایشی با شناسهٔ مشخص نوشته شود.
3. همان داده از Dropbox دوباره بازیابی شود.
4. محتوای بازیابی‌شده با دادهٔ نوشته‌شده تطبیق داده شود.
5. مسیر، زمان قابل اثبات، نتیجه و شاهد آزمون ثبت شود.
6. در صورت شکست یا نبود اتصال، مانع و اقدام بعدی ثبت شود و پرونده بسته نشود.

## 7. معیار تکمیل خاک‌برداری
یک اجرای خاک‌برداری تنها وقتی «کامل» اعلام می‌شود که همهٔ پرونده‌های کشف‌شده تعیین تکلیف مستند شده باشند، کارهای قابل‌اجرا واقعاً اجرا شده باشند، هر مقصد با شواهد مستقل بررسی شده باشد، اسناد مادر/صف/نمایه لازم بازخوانی و تطبیق شده باشند و هیچ مورد باز پنهان یا حذف نشده باشد. اگر مقصدی در دسترس نیست یا کار باقی مانده، نتیجهٔ کلی باید PARTIAL / PENDING باشد و نقطهٔ ادامهٔ روشن ثبت شود.

## 8. مرزهای صداقت اجرایی
- صف بودن ≠ انجام شدن.
- نوشتن موفق ≠ بازخوانی موفق.
- پیدا شدن ≠ اعتبارسنجی ≠ احیا ≠ یکپارچه‌سازی ≠ تأیید نهایی.
- وجود سند در مخزن ≠ ثبت در کتابخانهٔ مستقل، بافر، حافظهٔ پایدار یا Dropbox.
- تعریف قاعده ≠ اجرای خودکار اثبات‌شده.
- محدودیت ابزار یا دسترسی نباید به ادعای موفقیت یا شکست نهایی بدون شاهد تبدیل شود.
- پاسخ نهایی، عملیات انجام‌نشده را با برچسب «در انتظار/تأییدنشده» مشخص می‌کند و مسیر ادامه را حفظ می‌کند.
