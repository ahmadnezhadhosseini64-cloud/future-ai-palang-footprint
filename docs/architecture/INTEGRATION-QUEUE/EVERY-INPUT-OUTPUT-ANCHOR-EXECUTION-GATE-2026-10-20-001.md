## 3. تغییر معماری موردنیاز
قاعده باید به چرخهٔ اجرایی قابل‌آزمون تبدیل شود:
1. Capture input/output — دریافت ورودی و خروجیِ قابل‌مشاهده.
2. Assign anchor/event ID — تخصیص شناسهٔ یکتا یا پیوند به لنگر فعال بدون بازنویسی لنگرهای قبلی.
3. Record provenance and time — ثبت منشأ، زمان پیام و زمان اقدام به‌صورت جدا؛ زمان دقیق نامعلوم UNKNOWN / UNVERIFIED می‌ماند.
4. Classify — تفکیک پیام عادی از تصمیم، اصلاح، اقدام، قاعده و خروجی بادوام.
5. Persist durable record — ثبت رکورد فشرده یا سند مرجع کامل متناسب با اهمیت رویداد.
6. Read-back and match — بازخوانی مقصد واقعی و تطبیق محتوای مورد انتظار.
7. Reconcile destination status — ثبت وضعیت مستقل هر مقصد.
8. Resume on interruption — حفظ آخرین گام، شاهد، مانع و اقدام بعدی؛ تکرار باید idempotent (بدون ساخت رکورد تکراری) باشد.
9. Report only evidenced state — فقط وضعیت اثبات‌شده اعلام شود.

## 4. معیارهای پذیرش اجرایی

- [ ] تکرار اجرای ثبت باعث رکورد canonical تکراری نمی‌شود.
- [ ] اجرای واقعی، نتیجهٔ قابل مشاهده و ردپای مستقل (مثلاً workflow run، commit یا artifact) برای همین قابلیت وجود دارد.
