## 1. Purpose

Permanent Registration Matrix converts the principle "Trace is not durable registration" into an executable cross-layer architecture. A production is not considered complete merely because an observable trace exists.

## 2. Registration chain

`Production → Reference → Architecture → Repository → Memory → Runtime/Playground → Checkpoint/Anchor → Recovery → Evidence → Verification → Final Status`

Each layer has its own state. State must never be inferred from silence or from another layer's success.

## 3. Allowed layer states

Each applicable layer MUST explicitly carry one of:

- `SUCCESS`
- `PENDING`
- `FAILED`
- `UNAVAILABLE`
- `NOT_APPLICABLE`

## 4. Completion gate

`COMPLETED / PROVEN` is permitted only when every required layer is `SUCCESS` and independently recoverable evidence exists. A non-required layer MUST be explicitly marked `NOT_APPLICABLE`.

## 5. Failure-safe path

When a required layer cannot be completed:

`PENDING / UNAVAILABLE / FAILED → Recovery → First Valid Opportunity → Reconcile → Verify → Close`

If no durable writable destination exists:

`UNREGISTERED / RECOVERY REQUIRED`

No silent conversion to `COMPLETED` is permitted.

## 6. Cross-layer identity

The shared production identifier is the correlation key. Related records must preserve links among the Production ID, Reference ID, Architecture ID, repository path/commit, memory state, runtime state, checkpoint/anchor, recovery record, evidence, verification, and final status.

## 7. Idempotency and duplicate prevention

A retry reconciles the same production identity. It must not create a second canonical production for the same event unless an explicit superseding relationship is recorded.

## 8. Evidence integrity

A trace proves existence of an observable artifact or event. Durable registration proves maintained project state only when the relevant destination and verification evidence exist.

> **Trace is evidence of existence; durable registration is evidence of maintained project state.**

## 9. Runtime and checkpoint continuity

When Runtime/Playground or Checkpoint/Anchor is applicable, its state is recorded independently. Context changes, new chats, `00`, or `0.0` must not silently reset registration state. A checkpoint is not final closure unless the required completion evidence exists.

## 10. Recovery and reconciliation

Pending or unavailable registrations remain discoverable through the production registry and recovery path until reconciled. Reconciliation must update the affected layer state and capture verification evidence.

## 11. Scope

This architecture applies to formal productions under Future AI / Palang Footprint and integrates with Finalization Gate, Evidence Gate, Connection Chain, Continuation Path Preservation & Recovery, Durable Registration Failure & Recovery, Execution Claim Integrity, and Production Registry.
