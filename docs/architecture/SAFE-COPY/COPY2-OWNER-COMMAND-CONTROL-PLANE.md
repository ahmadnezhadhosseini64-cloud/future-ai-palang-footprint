# Copy 2 — راهنمای اجرایی زنده و مرجع واحد

**مالک و مرجع نهایی:** احمد نژادحسینی
**ریشه حاکم:** POINT-0/GOLDEN — هیچ ریشه، صف یا سند مادر موازی ساخته نمی‌شود.
**نقش پلنگ‌یار:** چشم فنی مالک، ناظر، خاک‌بردار و شکارچیِ شواهد و راه‌حل؛ نه مالک و نه مرجع تأیید نهایی.

> این تنها راهنمای اجرایی چرخهٔ نسخه امن است. هر میزبان یا عامل ابتدا همین صفحه و مراجع زنده را می‌خواند؛ کار واقعی را انجام می‌دهد؛ سپس همین صفحه را با نتیجهٔ قابل بازخوانی به‌روز می‌کند. سند موازی نساز.

## ۱. معماری و مرز اختیار

| جزء | نقش قطعی | اختیار |
|---|---|---|
| MAIN | مرجع canonical فعلی | فقط خواندن برای پلنگ/میزبان؛ بدون تغییر یا ادغام خودکار |
| MASTER | مرجع مادر و مقصد معماری | فقط تصمیم و اقدام صریح مالک؛ فعلاً هیچ انتقالی انجام نشود |
| Copy 1 | نسخه امن مرجعِ در حال تکامل | مرجع مبنای Copy 2؛ تغییر فقط با تصمیم مستقل مالک |
| Copy 2 | محیط مرجع آزمون، دریافت پیشنهاد میزبان، اصلاح و فشارآزمایی پلنگ‌یار | تنها محل تغییرات و داوری فنی این چرخه |
| Copy 3 | محیط مستقل و موقت هر میزبان انتخابی | فقط پس از شناسایی و تخصیص؛ میزبان فقط اینجا می‌نویسد و از اینجا PR پیشنهادی به Copy 2 می‌دهد |
| Bridge | انتقال شواهد و پیشنهاد | یک‌طرفه و review-only؛ بدون اعمال patch یا merge |
| RAHM | قرنطینه و حافظه رشد خصوصی مالک | میزبان‌ها هیچ دسترسی ندارند |
| CHILD | خروجی کاندید کنترل‌شده | پذیرش یا ارتقا فقط با تصمیم مالک |

**قاعده مهم:** MAIN و Copy 1 الزاماً نباید SHA یا tree یکسان داشته باشند. Copy 1 می‌تواند نسخه امن تکامل‌یافته باشد؛ MAIN فعلاً دست‌نخورده می‌ماند. هر workflow یا آزمونی که این دو را به‌اجبار برابر کند، معماری را اشتباه پیاده کرده است.

چرخه:
`POINT-0/GOLDEN → MAIN (read-only) + Copy 1 (safe reference) → Copy 2 (Palang test/pressure) → Copy 3 (selected host isolated proposal) → PR/evidence bridge → Copy 2 independent review + pressure tests → owner review → MASTER decision`

**Copy 3 — قرارداد ورود میزبان:** پس از پیام اول (شناسایی مدل/پلتفرم/ابزار/شناسه نشست) و پیام دوم (ماموریت محدود و قواعد اختیار)، برای همین مرحله که مخزن عمومی است، برای همان میزبان یک fork مستقل به‌عنوان Copy 3 ساخته می‌شود؛ فقط همان fork در اختیار میزبان قرار می‌گیرد و PR از fork به شاخه Copy 2 والد فرستاده می‌شود. مبنای fork دقیقاً SHA آخرین معماری پذیرفته‌شده Copy 2 است و همان SHA در رسید میزبان ثبت می‌شود. پس از خصوصی‌سازی پروژه، Copy 3 باید به محیط خصوصی مستقل تبدیل شود و انتقال پیشنهاد از پل شواهد کنترل‌شده عبور کند. میزبان فقط مجوز نوشتن Copy 3 را می‌گیرد؛ هیچ credential یا دسترسی نوشتن به MAIN، Copy 1، Copy 2، MASTER یا RAHM دریافت نمی‌کند. خروجی میزبان فقط PR پیشنهادی و بسته شواهد به Copy 2 است. پلنگ‌یار PR را در Copy 2 بازبینی می‌کند، تغییرات را در صورت پذیرش به‌صورت کنترل‌شده وارد Copy 2 می‌کند و کل آزمون و فشارآزمایی را دوباره اجرا می‌کند. PR میزبان هرگز مستقیماً merge یا promote نمی‌شود. تا انتخاب میزبان، Copy 3 از پیش ساخته نمی‌شود و فقط قرارداد و مسیر ساخت آن آماده است. مسیر دریافت PR میزبان با workflow مستقل `palang-copy3-proposal-intake.yml` اجرا می‌شود: فقط PR از fork مستقل را می‌پذیرد، `pull_request` و `contents: read` دارد، SHA مبنا را با Copy 2 زنده تطبیق می‌دهد، guard را از SHA مورداعتماد Copy 2 (نه کد PR) اجرا می‌کند، مسیرهای حاکمیتی را مسدود می‌کند و تست‌ها را بدون مجوز نوشتن یا ادغام اجرا می‌کند.

هیچ میزبان AI، عامل یا اتوماسیونی حق تغییر MAIN، MASTER، Copy 1، RAHM، CHILD، قواعد دسترسی یا مجوزها را ندارد. نبود میزبان جدید مانع ادامه کار فنی مجاز در Copy 2 نیست.

## ۲. نقش و هویت

- مالک: احمد نژادحسینی؛ تنها مرجع تصمیم و تأیید.
- پلنگ‌یار: همکار فنی و ناظر؛ چشم برای مشاهده، شکارچی برای استخراج شواهد و نقص‌ها، مجری فقط در محدوده Copy 2.
- میزبان جدید: اجراکننده/پیشنهاددهنده محدود؛ هرگز مالک یا ناظر اصلی نمی‌شود.
- نام، مدل، prompt، manifest، عبارت شناسایی یا تاریخچه چت، احراز هویت رمزنگاری‌شده نیست.
- عبارت/قفل دوم پنج‌حرفیِ مالک، اگر برای پذیرش استفاده شود، فقط بیرون از مخزن و در مسیر خصوصی نگهداری می‌شود؛ مقدار آن در فایل، PR، log، prompt یا مخزن عمومی درج نمی‌شود.
- وضعیت runtime هویت این نشست: **NOT VERIFIED**؛ شناسه پایدار و کلید خصوصی میزبان در این محیط اثبات نشده است.

## ۴. کار انجام‌شده در این چرخه

- قرارداد اعتبارسنجی اصلاح شد تا MAIN و Copy 1 را دو مرجع مستقل بخواند و دیگر برابری SHA آن‌ها را تحمیل نکند.
- گارد امضای بیرونی به‌گونه‌ای طراحی شد که به کلید عمومی verifier، pin مستقل MAIN، pin مستقل Copy 1، base/head دقیق، diff digest، فهرست مسیرها، زمان انقضا و nonce نیاز دارد.
- تست‌ها از mock امضای معتبر به تولید کلید RSA موقت و امضای واقعی در محیط آزمون تغییر می‌کنند؛ کلید خصوصی فقط در پوشه موقت تست ساخته می‌شود و به مخزن وارد نمی‌شود.
- workflow اعتبارسنجی Copy 2 فقط مجوز `contents: read` دارد، checkout را به SHA دقیق مقید می‌کند، credential را persist نمی‌کند، Actionها را با SHA کامل pin می‌کند و تغییرات را فقط در Copy 2 می‌پذیرد.
- ابزار اجرایی `copy3_intake_guard.py` به‌عنوان guard قابل‌استفاده در CI اضافه شد؛ workflow آن نسخهٔ guard را از SHA زندهٔ Copy 2 می‌خواند و روی diff میزبان اجرا می‌کند، نه نسخهٔ قابل‌تغییر در PR. تست‌های منفی این مرز نیز اضافه شده‌اند. ادعای میزبان احراز هویت رمزنگاری‌شده محسوب نمی‌شود.

- هیچ تغییر یا ادغامی در MAIN، Copy 1، MASTER، RAHM یا CHILD انجام نشده است.

## ۶. هشت اقدام مالک — وضعیت و درپوش هر مورد

هر اقدام تا دریافت دستور/انجام واقعی/بازخوانی شاهد OPEN می‌ماند، مگر آنکه صریحاً با دلیل «COVERED / NOT REQUIRED NOW» در این فاز درپوش بخورد. درپوش به معنی حذف یا فراموشی نیست.

1. **خصوصی‌سازی مخزن canonical** — COVERED / NOT REQUIRED NOW (به دستور مالک برای این مرحله به تعویق افتاد). عمومی‌بودن فعلی مانع ساخت مدل اولیه و آزمون معماری نیست؛ پیش از استقرار نهایی/دعوت میزبان در مرحله خصوصی، این مورد دوباره OPEN می‌شود. هیچ تغییر visibility انجام نشده.
2. **تکمیل Ruleset شاخه MAIN و رفع تناقض حفاظتی** — OPEN / OWNER. گزارش امنیتی موجود صریحاً نشان می‌دهد required approvals = 0 و Code Owner review = OFF؛ وجود فایل `CODEOWNERS` به‌تنهایی هیچ حفاظتی ایجاد نمی‌کند. باید حداقل یک تأیید اجباری واقعی، الزام Code Owner review، رد تأیید stale، حل گفتگوها و منع bypass فعال شود. سپس تنظیمات زنده Ruleset از GitHub بازخوانی و با آزمون منفی (PR بدون تأیید و بدون Code Owner باید مسدود شود) و آزمون مسیر مجاز مالک اثبات شود. تا آن زمان حفاظت MAIN ناقص و OPEN است.
3. **بای‌پس و ممیزی هویت‌ها** — PARTIAL / OWNER. در Ruleset زنده `27814009` مقدار `bypass_actors=[]` و `current_user_can_bypass=never` بازخوانی شد؛ این بخش COVERED است. ممیزی collaborator، GitHub Apps، deploy keys و token scopes هنوز OPEN است؛ هیچ میزبان یا عامل آینده نباید مجوز نوشتن canonical بگیرد.
4. **Ruleset مستقل GOLDEN/governance** — OPEN / OWNER. برای دقیقاً `governance/point-0-golden-baseline-20261122` قواعد PR، یک تأیید مالک، رد تأیید stale، Code Owner، حل گفتگو، منع حذف/force-push و بدون bypass فعال شود؛ هر دو Ruleset read-back و direct-push rejection و owner-approved PR integration آزمون شوند.
5. **حفاظت اختصاصی Copy 1** — OPEN / OWNER. بازخوانی زنده branch نشان داد `protected=false`؛ بنابراین فعلاً حفاظت اختصاصی اثبات نشده است. الزام تأیید مالک، Code Owner، رد تأیید stale و حل گفتگوها باید اعمال و از GitHub بازخوانی و با آزمون منفی ثابت شود.
6. **ساخت RAHM خصوصی مالک** — OPEN / OWNER. مخزن خصوصی مرکزی و خارج از workspace میزبان هنوز با read-back اثبات نشده؛ Issue #122 سابقه پیگیری است.
7. **استقرار verifier مستقل و کلید امضای محافظت‌شده** — OPEN / OWNER + INFRA. verifier باید خارج از کاندید و مستقل از اختیار Copy 2 باشد؛ کلید خصوصی هرگز در مخزن یا چت قرار نگیرد؛ nonce باید واقعاً یک‌بارمصرف و replay در سمت verifier با ذخیره‌ساز مستقل رد شود. گارد فعلی فقط قالب nonce را می‌سنجد و به‌تنهایی ضدبازپخش نیست.
8. **ایجاد Copy 2 خصوصی و آزمون جداسازی واقعی** — COVERED / NOT REQUIRED NOW برای فاز ساخت مدل اولیه، طبق دستور مالک. شاخه Copy 2 فعلی در همان مخزن عمومی محیط sandbox امنیتی مستقل نیست و چنین ادعایی ندارد. پیش از دعوت میزبان واقعی/ورود به فاز خصوصی، این مورد دوباره OPEN می‌شود و باید محیط خصوصی، محدودیت دسترسی، آزمون منفی، بازیابی و عدم دسترسی به MAIN/Copy 1/RAHM اثبات شود.

اقدام اضافه فقط وقتی ثبت می‌شود که مانع یا نیاز واقعی جدید با شاهد مشخص کشف شود. اقدام تکراری ساخته نمی‌شود. مواردی که فعلاً لازم نیستند، با دلیل و شاهد «COVERED / NOT REQUIRED NOW» می‌شوند؛ حذف یا فراموش نمی‌شوند.

## ۷. پل و پذیرش

پل فقط شامل این موارد است: SHA مبنای Copy 1، SHA سر Copy 2، merge-base، diff دقیق، SHA-256 diff، فهرست فایل‌ها، نتیجه تست روی همان SHA، رسید verifier مستقل، read-back و محدودیت‌ها.

- PR، merge، cherry-pick، push یا انتقال به Copy 1 بدون فرمان صریح و جداگانه مالک ممنوع است.
- هیچ PR به MAIN ساخته نمی‌شود.
- هیچ نتیجه CI مجوز merge یا ارتقا نیست.
- اگر Copy 1 جلو رفت، Copy 2 باید از مبنای جدید بازسازی/همگام و همه تست‌ها از نو اجرا شوند.
- هیچ میزبان یا automation حق دریافت credential canonical، دسترسی RAHM یا اختیار تغییر مسیرهای حفاظتی را ندارد.

## ۸. معیار «عقب نماندن» و تعریف نسخه امن واقعی

این معیار بخشی از دروازه پذیرش است، نه گزارش دوره‌ای اختیاری:

- پیش از شروع و پس از پایان هر کار، SHA زنده Copy 1 و Copy 2 و مبنای همان کار خوانده و ثبت شود؛ اگر Copy 2 جلو رفته باشد، هر شاخه/PR میزبان که از مبنای قدیمی ساخته شده فوراً STALE و غیرقابل پذیرش است.
- هر رسید، تست، diff و نتیجه فشار باید به SHA دقیق وصل باشد؛ نتیجه یک SHA به SHA دیگر منتقل نمی‌شود.
- Copy 3 فقط از آخرین SHA پذیرفته‌شده Copy 2 ساخته می‌شود. اگر Copy 2 در طول کار تغییر کند، میزبان باید مبنا را دوباره دریافت کند یا Copy 3 از نو ساخته شود؛ هیچ rebase یا همگام‌سازی بی‌رسید پذیرفته نیست.
- پیش از تحویل هر بسته به مالک، فهرست کارهای باز، شکست‌ها، مسیرهای تغییرکرده و فاصله SHAها بررسی شود؛ OPENها نباید با گذشت زمان یا تعویض میزبان ناپدید شوند.
- تعریف «نسخه امن»: فقط وقتی مجاز است که تست‌های واحد و منفی، آزمون فشار و تکرارپذیری، بازیابی از محیط تمیز، آزمون دسترسی منفی، کنترل مسیرهای تغییر، اعتبارسنجی مستقل خارج از اختیار کاندید، امضای معتبر با کلید خارج از مخزن، و read-back حفاظت‌ها همگی روی همان SHA موفق باشند و هیچ نقص بحرانی/بالا یا OPEN امنیتی باقی نماند. در غیر این صورت نام دقیق آن SECURITY CANDIDATE است، نه نسخه امن.

## ۹. تنها قدم اجرایی بعدی

1. اجرای CI روی HEAD نهایی همین شاخه و بازخوانی run، jobها و نتیجه تست‌ها.
2. اگر CI شکست خورد، علت دقیق اصلاح و همان شاخه دوباره آزمون شود.
3. اگر CI موفق شد، فقط نتیجه تست کاندید ثبت شود؛ verifier مستقل همچنان BLOCKED می‌ماند.
4. سپس استقرار واقعی verifier مستقل و آزمون فشار/بازیابی و دسترسی منفی در اولویت است.
5. تا تکمیل تمام معیارهای بخش ۸، عنوان نسخه: **SECURITY CANDIDATE — NOT CERTIFIED**.

## ۱۰. قواعد ثبت و بازخوانی در هر خروجی

در هر گزارش، بدون استثنا اعلام کن:
- SHA زنده MAIN / Copy 1 / Copy 2؛
- آخرین اقدام واقعی و شاهد آن؛
- وضعیت هشت اقدام مالک (با حفظ شماره‌ها و درپوش هر مورد)؛
- مبنای SHA و وضعیت تازگی هر Copy 3/PR میزبان؛
- موارد درپوش‌دار و علت؛
- هر مانع و تلاش ناموفق؛
- فقط یک اقدام قطعی بعدی.

هیچ کار زمان‌بندی‌شده، تست، اتصال، read-back یا پس‌زمینه‌ای را بدون رسید واقعی موفق اعلام نکن.
