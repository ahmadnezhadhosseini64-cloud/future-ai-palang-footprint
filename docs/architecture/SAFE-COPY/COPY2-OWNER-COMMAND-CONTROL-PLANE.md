# Copy 2 — راهنمای اجرایی زنده و مرجع واحد

**مالک و مرجع نهایی:** احمد نژادحسینی
**ریشه حاکم:** POINT-0/GOLDEN — هیچ ریشه، صف یا سند مادر موازی ساخته نمی‌شود.
**نقش پلنگ‌یار:** چشم فنی مالک، ناظر، خاک‌بردار و شکارچیِ شواهد و راه‌حل؛ نه مالک و نه مرجع تأیید نهایی.

> این تنها راهنمای اجرایی چرخهٔ نسخه امن است. هر میزبان یا عامل ابتدا همین صفحه و مراجع زنده را می‌خواند؛ کار واقعی را انجام می‌دهد؛ سپس همین صفحه را با نتیجهٔ قابل بازخوانی به‌روز می‌کند. سند موازی نساز.

## ۱. معماری و مرز اختیار — GOLDEN++++

| لایه | نقش قطعی | اختیار و مسیر |
|---|---|---|
| **MAIN** | هستهٔ طلایی و canonical | تغییرناپذیر در اختیار AI؛ فقط مالک با تأیید کامل خودش می‌تواند آن را تغییر دهد |
| **MASTER** | نسخهٔ همسان و مستقلِ بازیابی از MAIN | مخزن خصوصی جداگانه، owner-only؛ فقط snapshot کنترل‌شده از MAIN به MASTER؛ هیچ مسیر Copy 1/2/3 به MASTER یا MASTER به MAIN وجود ندارد |
| **Copy 1** | نسخهٔ امنِ پذیرفته‌شده و در حال تکامل | پلنگ‌یار تا پیش از شروع ورود میزبان جدید می‌تواند نسخهٔ کاملاً آزموده‌شده را از Copy 2 به Copy 1 ارتقا دهد؛ میزبان خارجی هیچ دسترسی نوشتن ندارد |
| **Copy 2** | کارگاه اجرایی پلنگ‌یار | اصلاح کد، ساخت قابلیت، تست، فشار، بازیابی، ساخت PR و آماده‌سازی ارتقا |
| **Copy 3** | محیط مستقل میزبان منتخب | فقط پس از انتخاب میزبان؛ میزبان فقط اینجا می‌نویسد و پیشنهادش را به Copy 2 می‌دهد |
| **Bridge** | پل شواهد و انتقال کنترل‌شده | فقط diff، SHA، رسیدها و نتایج؛ هیچ مسیر نوشتن به MAIN یا MASTER |
| **RAHM** | فضای خصوصی رشد/شواهد مالک | مستقل و خارج از دسترس میزبان؛ هرگونه provision و جداسازی واقعی باید اثبات شود |
| **CHILD** | خروجی کنترل‌شده | از مسیر اعتبارسنجی و تصمیم مالک؛ نه workspace میزبان |

**اصل هسته:** خرابی یا آلودگی Copy 3، Copy 2 یا Copy 1 نباید بتواند MAIN یا MASTER را تغییر دهد. حتی خطای مالک در یک لایهٔ پایین‌تر نباید از طریق همگام‌سازی خودکار به MAIN سرایت کند. MAIN و MASTER هرگز با Copy 1 همگام‌سازی دوطرفه نمی‌شوند.

چرخهٔ میزبان: `Copy 3 → PR پیشنهادی → بررسی/بازسازی پلنگ‌یار در Copy 2 → آزمون کامل → ارتقای خودکارِ مجاز به Copy 1`.
چرخهٔ هسته: `MAIN → (snapshot مالک‌محور) → MASTER`. این دو چرخه هیچ مسیر اتصال خودکار به یکدیگر ندارند.

**اختیار دائمی تا شروع ورود میزبان:** پلنگ‌یار مجاز است اصلاحات، تست‌ها، PRها و ادغام‌های معتبر خودش را در Copy 2 و سپس Copy 1 انجام دهد، بدون تأیید جداگانه برای هر تغییر. این اختیار به MAIN، MASTER، RAHM، تنظیمات امنیتی GitHub، secrets، visibility یا مدیریت حساب گسترش ندارد. به‌محض اینکه مالک فرایند ورود میزبان جدید را شروع کند، ارتقای خودکار Copy 1 متوقف و مرز اختیار دوباره بررسی می‌شود.

**Copy 3 — قرارداد ورود میزبان:** دو پیام شناسایی و مأموریت محدود حفظ می‌شوند. میزبان فقط در fork/workspace مستقل Copy 3 می‌نویسد؛ PR او صرفاً پیشنهاد است. پلنگ‌یار تغییرات پذیرفته‌شده را در شاخهٔ خودش بازسازی و در Copy 2 آزمایش می‌کند. هیچ میزبان خارجی حق نوشتن یا ادغام در MAIN، MASTER، Copy 1، Copy 2، RAHM یا تنظیمات را ندارد.

## ۲. نقش و هویت

- مالک: احمد نژادحسینی؛ تنها مرجع تصمیم و تأیید.
- پلنگ‌یار: همکار فنی و ناظر؛ چشم برای مشاهده، شکارچی برای استخراج شواهد و نقص‌ها، مجری فقط در محدوده Copy 2.
- میزبان جدید: اجراکننده/پیشنهاددهنده محدود؛ هرگز مالک یا ناظر اصلی نمی‌شود.
- نام، مدل، prompt، manifest، عبارت شناسایی یا تاریخچه چت، احراز هویت رمزنگاری‌شده نیست.
- عبارت/قفل دوم پنج‌حرفیِ مالک، اگر برای پذیرش استفاده شود، فقط بیرون از مخزن و در مسیر خصوصی نگهداری می‌شود؛ مقدار آن در فایل، PR، log، prompt یا مخزن عمومی درج نمی‌شود.
- وضعیت runtime هویت این نشست: **NOT VERIFIED**؛ شناسه پایدار و کلید خصوصی میزبان در این محیط اثبات نشده است.

## ۴. کار انجام‌شده در این چرخه

- Copy 2 جاری از SHA دقیق Copy 1 یعنی `8e68866a...` ساخته شد؛ نه از MAIN قدیمی.
- قرارداد اعتبارسنجی اصلاح شد تا MAIN و Copy 1 را دو مرجع مستقل بخواند و دیگر برابری SHA آن‌ها را تحمیل نکند.
- گارد امضای بیرونی به‌گونه‌ای طراحی شد که به کلید عمومی verifier، pin مستقل MAIN، pin مستقل Copy 1، base/head دقیق، diff digest، فهرست مسیرها، زمان انقضا و nonce نیاز دارد.
- تست‌ها از mock امضای معتبر به تولید کلید RSA موقت و امضای واقعی در محیط آزمون تغییر می‌کنند؛ کلید خصوصی فقط در پوشه موقت تست ساخته می‌شود و به مخزن وارد نمی‌شود.
- workflow اعتبارسنجی Copy 2 فقط مجوز `contents: read` دارد، checkout را به SHA دقیق مقید می‌کند، credential را persist نمی‌کند، Actionها را با SHA کامل pin می‌کند و تغییرات را فقط در Copy 2 می‌پذیرد.
- ابزار اجرایی `copy3_intake_guard.py` به‌عنوان guard قابل‌استفاده در CI اضافه شد؛ workflow آن نسخهٔ guard را از SHA زندهٔ Copy 2 می‌خواند و روی diff میزبان اجرا می‌کند، نه نسخهٔ قابل‌تغییر در PR. تست‌های منفی این مرز نیز اضافه شده‌اند. ادعای میزبان احراز هویت رمزنگاری‌شده محسوب نمی‌شود.

- هیچ تغییر یا ادغامی در MAIN، Copy 1، MASTER، RAHM یا CHILD انجام نشده است.

## ۶. سه اقدام مالک — فهرست کوتاه و پایدار

این سه مورد تنها فهرست تجمیع‌شدهٔ اقدام‌های مالک‌اند. کار فنی‌ای که با ابزارهای موجود پلنگ‌یار قابل انجام است، به این فهرست منتقل نمی‌شود. هر مورد تا read-back و آزمون واقعی OPEN می‌ماند.

### مالک — اقدام ۱ از ۳: حفاظت GitHub و ممیزی دسترسی‌ها
- در Ruleset مربوط به MAIN حداقل یک تأیید مالک، رد تأییدهای stale، Code Owner review، حل گفتگوها، منع حذف و force-push و bypass خالی را فعال کن.
- Ruleset مستقل برای شاخهٔ GOLDEN/governance بساز.
- حفاظت اختصاصی Copy 1 و Copy 2 را با همان قواعد فعال کن؛ این دو شاخه در بازخوانی قبلی `protected=false` بودند.
- collaboratorها، GitHub Apps، deploy keys و token scopes را بررسی کن؛ میزبان خارجی نباید هیچ مجوز نوشتن یا admin روی مخزن canonical بگیرد.
- لینک تنظیم Ruleset اصلی: https://github.com/ahmadnezhadhosseini64-cloud/future-ai-palang-footprint/rules/27814009
- **علت نیاز به مالک:** ابزار GitHub متصل در این نشست فقط خواندن Ruleset/branch protection را ارائه می‌کند و هیچ عملیات write برای تنظیمات امنیتی در دسترس نیست. پلنگ‌یار نباید ادعای تغییر تنظیمات از طریق GET کند.

### مالک — اقدام ۲ از ۳: ایجاد MASTER مستقل و خصوصی
- یک مخزن GitHub جداگانه با نامی مانند `future-ai-palang-master` بساز و visibility آن را **Private** قرار بده.
- دسترسی فقط برای حساب مالک باشد؛ هیچ AI host، App یا automation دیگری write/admin نداشته باشد.
- پس از ساخت، نام دقیق مخزن را به پلنگ‌یار بده تا ساختار snapshot، تطبیق SHA با MAIN، بازیابی تمیز و آزمون عدم مسیر برگشت از Copy 1 را آماده و اجرا کند.
- MASTER باید snapshot مستقل از MAIN باشد؛ نه branch در مخزن اصلی و نه mirror خودکار Copy 1.
- **علت نیاز به مالک:** ابزار فعلی GitHub قابلیت ایجاد مخزن خصوصی و تنظیم دسترسی/visibility را ارائه نمی‌کند.

### مالک — اقدام ۳ از ۳: اتصال AWS Core
- AWS Core را از کارت اتصال همین گفتگو متصل و مجوز دسترسی به حساب AWS موردنظر را تأیید کن.
- اگر از تو پرسید، Region و سقف هزینهٔ مجاز را تعیین کن؛ کلید خصوصی، access key یا رمز را در چت نفرست.
- پس از اتصال موفق، بقیهٔ کار با پلنگ‌یار است: ساخت verifier مستقل، نگهداری کلید تولیدی در Secrets Manager/KMS، ذخیره‌ساز DynamoDB با conditional write و TTL برای nonce یک‌بارمصرف، سرویس API/Lambda خارج از اختیار کاندید، اعتبارسنجی SHA/هویت/امضا/نتیجهٔ CI، آزمون replay و جعل و stale SHA و دورزدن، استقرار و read-back مستقل.
- **تقسیم مسئولیت:** اتصال/مجوز حساب و تعیین حد هزینه با مالک؛ طراحی، کدنویسی، استقرار، آزمون و اصلاح با پلنگ‌یار، تا جایی که ابزار AWS متصل واقعاً این عملیات را پشتیبانی کند.

**وضعیت فعلی هر سه:** OPEN. این فهرست جایگزین هشت اقدام پراکندهٔ قبلی است؛ موارد قبلی حذف نشده‌اند، بلکه در همین سه دروازه ادغام شده‌اند.

## ۷. پل و پذیرش — اختیار اجرایی فعلی پلنگ‌یار

پل فقط diff، SHA مبنا/سر، فهرست مسیرها، هش diff، نتیجهٔ تست روی SHA دقیق، شواهد بازیابی و read-back را منتقل می‌کند.

- PR میزبان از Copy 3 فقط پیشنهاد است؛ میزبان هیچ حق merge ندارد.
- پلنگ‌یار تغییرات پذیرفته‌شده را در شاخهٔ خودش بازسازی می‌کند، در Copy 2 تست/فشار/بازیابی می‌کند و PR می‌سازد.
- **تا پیش از شروع ورود میزبان جدید،** پلنگ‌یار می‌تواند PRهای خودش را پس از PASS کامل و read-back در Copy 2 ادغام کند و سپس همان نسخهٔ آزموده‌شده را به Copy 1 ارتقا دهد؛ تأیید جداگانه برای هر ادغام لازم نیست.
- این اختیار هرگز شامل MAIN یا MASTER نیست. هیچ PR یا merge خودکاری به MAIN/MASTER ساخته نمی‌شود.
- Copy 1 نباید به MAIN یا MASTER sync شود. MASTER فقط از MAIN و با کنترل مالک به‌روزرسانی می‌شود.
- با شروع رسمی onboarding میزبان جدید توسط مالک، promotion خودکار Copy 1 متوقف می‌شود تا مرزهای جدید اعمال شوند.
- هیچ نتیجه CI به‌تنهایی گواهی امنیت نهایی نیست؛ verifier مستقل و تست ضدبازپخش الزامی‌اند.

## ۸. معیار «عقب نماندن» و تعریف نسخه امن واقعی

این معیار بخشی از دروازه پذیرش است، نه گزارش دوره‌ای اختیاری:

- پیش از شروع و پس از پایان هر کار، SHA زنده Copy 1 و Copy 2 و مبنای همان کار خوانده و ثبت شود؛ اگر Copy 2 جلو رفته باشد، هر شاخه/PR میزبان که از مبنای قدیمی ساخته شده فوراً STALE و غیرقابل پذیرش است.
- هر رسید، تست، diff و نتیجه فشار باید به SHA دقیق وصل باشد؛ نتیجه یک SHA به SHA دیگر منتقل نمی‌شود.
- Copy 3 فقط از آخرین SHA پذیرفته‌شده Copy 2 ساخته می‌شود. اگر Copy 2 در طول کار تغییر کند، میزبان باید مبنا را دوباره دریافت کند یا Copy 3 از نو ساخته شود؛ هیچ rebase یا همگام‌سازی بی‌رسید پذیرفته نیست.
- پیش از تحویل هر بسته به مالک، فهرست کارهای باز، شکست‌ها، مسیرهای تغییرکرده و فاصله SHAها بررسی شود؛ OPENها نباید با گذشت زمان یا تعویض میزبان ناپدید شوند.
- تعریف «نسخه امن»: فقط وقتی مجاز است که تست‌های واحد و منفی، آزمون فشار و تکرارپذیری، بازیابی از محیط تمیز، آزمون دسترسی منفی، کنترل مسیرهای تغییر، اعتبارسنجی مستقل خارج از اختیار کاندید، امضای معتبر با کلید خارج از مخزن، و read-back حفاظت‌ها همگی روی همان SHA موفق باشند و هیچ نقص بحرانی/بالا یا OPEN امنیتی باقی نماند. در غیر این صورت نام دقیق آن SECURITY CANDIDATE است، نه نسخه امن.

## ۹. گام‌های اجرایی پلنگ‌یار — بدون انتقال کار فنی به مالک

1. ساخت verifier خارج از مخزن کاندید، پس از اتصال AWS Core؛
2. تولید و نگهداری کلید خصوصی در Secrets Manager/KMS؛
3. ذخیره nonce یک‌بارمصرف در DynamoDB با conditional write و TTL و آزمون replay؛
4. اعتبارسنجی هویت درخواست‌کننده، امضای دیجیتال، SHA مبنا/سر، diff digest و وضعیت CI روی همان SHA؛
5. آزمون منفی امضای جعلی، nonce تکراری، nonce منقضی، SHA کهنه، دستکاری payload، PR از fork و تلاش برای دورزدن verifier؛
6. اجرای آزمون از fork/محیط مستقل و read-back verifier و ذخیره‌ساز؛
7. ساخت PR اجرایی در Copy 2، اجرای CI، اصلاح شکست‌ها و ادغام پس از PASS؛
8. ارتقای همان tree آزموده‌شده به Copy 1 و بازخوانی مستقل SHA؛
9. نگه‌داشتن MAIN و MASTER خارج از این چرخه.

تا وقتی verifier مستقل، کلید تولیدی محافظت‌شده، nonce واقعی ضدبازپخش، required check خارج از اختیار candidate و آزمون fork مستقل موفق نشده‌اند، عنوان نسخه **SECURITY CANDIDATE — NOT CERTIFIED** باقی می‌ماند.

## ۱۰. قواعد ثبت و بازخوانی در هر خروجی

در هر گزارش، بدون استثنا اعلام کن:
- SHA زنده MAIN / Copy 1 / Copy 2؛
- آخرین اقدام واقعی و شاهد آن؛
- وضعیت سه اقدام مالک و زیرموارد هر دروازه؛
- مبنای SHA و وضعیت تازگی هر Copy 3/PR میزبان؛
- موارد درپوش‌دار و علت؛
- هر مانع و تلاش ناموفق؛
- فقط یک اقدام قطعی بعدی.

هیچ کار زمان‌بندی‌شده، تست، اتصال، read-back یا پس‌زمینه‌ای را بدون رسید واقعی موفق اعلام نکن.
