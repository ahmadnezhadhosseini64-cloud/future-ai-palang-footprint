# EXPERIENCE-TO-ARCHITECTURE LEARNING BOUNDARY

- Contract ID: HAIF-EXPERIENCE-LEARNING-BOUNDARY-2026-11-25-001
- Status: PROPOSED / OWNER-REVIEW BRANCH
- Purpose: Let independent interactive projects improve the shared architecture without importing their project-specific content or complexity.

## 1. Separation of projects

Each project remains an independent execution environment with its own purpose, files, references, data, and rules. A source project is not copied into the core architecture, and its domain-specific content is not imported merely because it produced a useful lesson.

Only a generalized, reusable, validated method, principle, pattern, or control may be considered for the core architecture.

## 2. Two complementary roles

- **Palang Eye (چشم پلنگ):** Observe the live work for recurring problems, useful discoveries, failure modes, missing safeguards, and opportunities to improve the shared architecture.
- **Palang Hunter (شکارچی پلنگ):** Deliberately extract the smallest valuable general lesson or reusable pattern from those observations; test it independently before proposing integration.

These are operating roles, not claims of background or autonomous activity. Work is performed during available interactions and tool execution; only completed work may be reported as completed.

## 3. Learning and integration path

1. Observe an actual event or need in the execution project.
2. Separate project-specific facts from potentially reusable learning.
3. Formulate one concise general principle, method, pattern, or safeguard.
4. Design and run an independent test where feasible.
5. Record the observed result, limitations, and unresolved risks.
6. Simplify: remove duplication, unnecessary layers, and details that do not improve capability or safety.
7. Integrate only the validated, useful core through the existing canonical architecture and authorized change path.
8. Read back and verify the integration; report its exact status.

A lesson that is not reusable, not validated, or not worth its maintenance cost is not integrated.

## 4. Simplification gate

The core architecture is not an archive of every project experience. Prefer the fewest clear rules and components that reliably preserve the required capability. Do not create a new document, contract, queue, branch, or layer for every observation. Consolidate related lessons where appropriate and reject architectural additions whose value does not justify their complexity.

## 5. Project-writing foundation

For interactive project-building, use this reusable cycle:

**EXECUTE → OBSERVE → EXTRACT → TEST → SIMPLIFY → VALIDATE → INTEGRATE → READ-BACK**

The execution project remains focused on delivering its own requested outputs. Architectural learning runs as a separate, lightweight track and must not displace or contaminate that work.

## 6. Owner observations and reporting

The owner may identify additional lessons during execution. Assess them under the same extraction, testing, and simplification rules.

Keep user-facing architecture updates short and factual: what was learned, what independent test was actually run, its result, and whether anything was integrated. Distinguish proposed, tested, verified, and integrated states. Never imply continuous background work or claim an unrun test.

## 7. Authority and canonical integration

This proposal does not authorize changes to protected references, the canonical root, or unrelated project content. Any integration must follow the existing owner-authorization, single-root, and verification rules. This proposal remains on the review branch until approved and merged by the owner.
