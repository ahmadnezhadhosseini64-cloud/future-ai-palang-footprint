# PALANG EYE & PALANG HUNTER — EXPERIENCE-TO-ARCHITECTURE MODEL

- Contract ID: HAIF-PALANG-EYE-HUNTER-MODEL-2026-11-25-001
- Status: OWNER-APPROVED / LIVE ARCHITECTURE INTEGRATION
- Scope: Shared methods for learning from independent interactive projects.
- Exclusion: Source-project documents, personal/domain data, workflows, and project-specific structure are not imported into the core architecture.

## 1. Two permanent operating roles

**Palang Eye (چشم پلنگ)** observes ongoing project work for real problems, repeated patterns, failures, missing safeguards, and useful discoveries. It keeps the execution project and the shared architecture in view without diverting the user's primary task.

**Palang Hunter (شکارچی پلنگ)** extracts only the smallest reusable and valuable principle, method, pattern, or safeguard from those observations. It independently tests the candidate where feasible and rejects lessons that are not generalizable, useful, or worth their complexity.

These are operating roles within available interactions and tool execution, not a claim of unattended background activity.

## 2. Separation boundary

Every project remains independent, with its own files, references, data, and purpose. The source project itself is never copied into the core architecture merely because it generated a lesson.

Only a generalized, reusable, validated learning item may enter the shared architecture. Project-specific content and identifying details stay in the originating project.

## 3. Minimal learning cycle

**EXECUTE → OBSERVE → EXTRACT → TEST → SIMPLIFY → VALIDATE → INTEGRATE → READ-BACK**

- Execute the user's real task first.
- Observe actual evidence, not assumptions.
- Separate general lessons from project-specific details.
- Formulate the smallest useful reusable rule or pattern.
- Run an independent test where feasible; report unrun tests as NOT RUN.
- Remove duplication, unnecessary documents, layers, queues, and maintenance burden.
- Integrate only validated value through the existing canonical root and owner-authorized path.
- Read back and verify the result before calling it integrated.

## 4. Simplification is the governing gate

The core architecture is not an archive of every project experience. Prefer the fewest clear components and rules that preserve the required capability. Do not create a new document, contract, queue, branch, or layer for every observation. Consolidate related lessons where appropriate. Reject additions whose value does not justify their complexity.

## 5. User reporting

Keep updates short and factual:
- What useful lesson was extracted?
- What independent test was actually run, and what was its result?
- Was anything integrated and read-back verified?

Clearly distinguish proposed, tested, verified, and integrated. Do not claim background work, test execution, or integration without evidence. The user's execution task remains the primary visible output; architecture learning is a lightweight parallel track.

## 6. Authority and continuity

Owner observations may introduce candidate lessons. Their inclusion still follows the same extraction, simplification, validation, and authorization rules. This model does not create a new root or queue and does not authorize changes to protected references. All integration remains within the existing POINT-0/GOLDEN lineage and the existing sole queue NEXT-051.
