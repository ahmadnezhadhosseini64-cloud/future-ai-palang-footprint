# معماری پل یک‌طرفه و فضای کار مستقل میزبان

- شناسه: `HAIF-ONE-WAY-HOST-BRIDGE-2026-11-23-001`
- نسخه: `0.1.0`
- وضعیت: `OWNER-PROPOSED / ACTIVE-PENDING-OWNER-REVIEW`
- ریشه: `POINT-0/GOLDEN`
- صف یگانهٔ پیگیری: `NEXT-051`
- دامنه: فقط ورود میزبان آزمایشی؛ بدون تغییر در اختیار MAIN/MASTER

## 1. قفل حاکمیتی

**MAIN و MASTER فقط در اختیار مالک پروژه و عامل کمکیِ مجاز از طرف مالک هستند. هیچ میزبان تازه‌ای عضو هسته نیست.**

این ممنوعیت مطلق است و شامل دسترسی مستقیم یا غیرمستقیم می‌شود:

- هیچ میزبان یا عامل واسطی حق WRITE، branch، commit، PR، issue، release، workflow، تنظیمات یا هر مسیر تغییر در مخزن مادر را ندارد.
- هیچ میزبان حق درخواست، دریافت، نگهداری یا استفاده از credential مخزن مادر را ندارد.
- هیچ پل، پوشه، ربات، توکن یا سرویس واسطی مجاز نیست خروجی میزبان را به مخزن مادر بنویسد.
- تأیید در پیام، مجوز فنی یا استثنا از این ممنوعیت ایجاد نمی‌کند.
- فقط مالک می‌تواند محتوای خروجی را بررسی و در صورت صلاحدید، از مسیر حاکمیتی پروژه ارتقا دهد.

این قفل با افزودن پوشه یا تغییر نام مسیر قابل دور زدن نیست.

## 2. مدل ساده

معماری سه بخش دارد:

1. **هستهٔ مرکزی MAIN/MASTER:** مرجع مالکیت و حاکمیت؛ فقط مالک و عامل مجاز او.
2. **پل یک‌طرفهٔ HOST-ENTRY:** محتوای عمومی و فقط‌خواندنی شامل پیام دعوت، معماری، دستورالعمل و نسخهٔ مرجع. جهت انتشار اطلاعات فقط از هسته به میزبان است.
3. **فضای مستقل میزبان:** محیط کاری خارج از مخزن مادر، در sandbox واقعی همان میزبان یا مخزن خصوصی جداگانه‌ای که مالک برای همان میزبان فراهم کرده است.

`MAIN → READ-ONLY HOST BRIDGE → HOST'S OWN WORKSPACE`

مسیر برگشت نوشتنی وجود ندارد:

`HOST -X-> MAIN/MASTER`

خروجی میزبان فقط به‌صورت فایل/بستهٔ پیشنهادی با رسید به مالک تحویل می‌شود. مالک خودش تصمیم می‌گیرد آیا آن را وارد فرایند خصوصی RAHM کند یا نه.

## 3. پل چیست و چه نیست؟

پل یک نقطهٔ ورود و انتشار نسخهٔ مرجع است؛ نه پوشهٔ قابل‌نوشتن برای میزبان، نه حساب GitHub، نه broker و نه کانال write-back.

پل می‌تواند یک مسیر ثابت در مخزن عمومی باشد که لینک آن در پیام دعوت قرار می‌گیرد. میزبان فقط فایل‌های منتشرشده را می‌خواند یا دریافت می‌کند.

**محدودیت GitHub:** مجوز دسترسی در GitHub در سطح مخزن اعمال می‌شود، نه به‌صورت ACL مستقل برای یک پوشه. بنابراین نمی‌توان به میزبان در همان مخزن «فقط دسترسی پوشه‌ای» داد و بقیهٔ مخزن را با مجوز فنی جداگانه بست. چون مخزن مادر عمومی است، میزبان می‌تواند محتوای عمومی آن را بخواند؛ اما هیچ مجوز نوشتن نمی‌گیرد. اگر روزی دسترسی خصوصی لازم شد، باید مخزن جداگانه و مستقل باشد.

## 4. فضای مستقل هر میزبان

هر میزبان فقط در محیط خودش کار می‌کند:

```text
HOST-WORKSPACE/
  CHARTER.md
  SNAPSHOT/       # نسخهٔ مرجع دریافت‌شده؛ فقط‌خواندنی
  INBOX/          # مأموریت‌ها و ورودی‌ها
  WORK/           # کار آزمایشی و فایل‌های تولیدی
  TESTS/          # آزمون‌ها و خروجی خام
  OBSERVATIONS/   # یافته‌های مستند
  PROPOSALS/      # پیشنهادها، نه تغییرات قطعی
  RECEIPTS/       # منبع، commit، digest، زمان و نتایج
  RECOVERY/       # نسخهٔ پشتیبان و بازیابی
```

این فضا باید خارج از checkout قابل‌نوشتن مخزن مادر باشد. اگر محیط میزبان فقط یک نشست موقت دارد، آن را پایدار معرفی نمی‌کند. اگر sandbox مستقل یا ذخیره‌سازی پایدار ندارد، وضعیت را `WORKSPACE-NOT-PROVEN` ثبت می‌کند.

## 5. پیام دعوت تک‌مرحله‌ای

مالک فقط لینک پل عمومی و یک پیام دعوت را به میزبان می‌دهد. میزبان باید:

1. لینک را باز کند و نسخهٔ مرجع را بدون OAuth بخواند.
2. شناسهٔ commit و نسخهٔ سند را ثبت کند.
3. در محیط مستقل خودش workspace را بسازد؛ اگر امکان واقعی ندارد، صادقانه اعلام کند.
4. فقط در `WORK/` کار آزمایشی انجام دهد.
5. آزمون‌ها و رسیدها را در workspace خودش نگه دارد.
6. خروجی را به مالک تحویل دهد؛ هیچ اتصال نوشتنی به مخزن مادر نسازد.

این پیام به‌تنهایی sandbox، ذخیره‌سازی پایدار، OAuth یا دسترسی خصوصی ایجاد نمی‌کند؛ این قابلیت‌ها باید از سوی محیط میزبان یا مالک فراهم شوند.

## 6. جایگاه CHILD

`CHILD` مرحلهٔ نامزد/فرزندِ کنترل‌شده برای خروجی‌های پالایش‌شده است؛ **نام دیگری برای workspace میزبان نیست** و میزبان مستقیماً به آن دسترسی نوشتن ندارد.

مسیر مجاز:

`HOST WORKSPACE → OWNER EXPORT → PRIVATE RAHM REVIEW → CHILD CANDIDATE → OWNER APPROVAL → CONTROLLED MASTER PROMOTION`

هر خروجی میزبان دادهٔ پیشنهادی و غیرقابل‌اعتماد است تا زمانی که مالک آن را بررسی کند.

## 7. اقداماتی که فقط مالک باید در GitHub انجام دهد

- حفاظت شاخهٔ اصلی و شاخه‌های حاکمیتی با الزام تأیید مالک و جلوگیری از push میزبان‌ها.
- بازبینی فهرست collaboratorها، تیم‌ها، GitHub Apps و deploy keys؛ حذف هر مجوز نوشتن غیرضروری.
- نگهداری secretها فقط در محل امن؛ هرگز در پیام دعوت، فایل عمومی یا workspace میزبان.
- در صورت نیاز به فضای GitHub مستقل، ساخت یک مخزن جداگانه برای همان میزبان و اعطای حداقل مجوز فقط به همان مخزن؛ نه مخزن مادر.
- نگه‌داشتن RAHM خصوصی و خارج از دسترس میزبان‌ها.

تنظیمات واقعی GitHub باید توسط مالک بررسی و اعمال شود؛ این سند به‌تنهایی آن‌ها را فعال نمی‌کند.

## 8. آزمون پذیرش و وضعیت

تا وقتی شواهد مستقیم وجود ندارد، این موارد `OPEN` می‌مانند:

- لینک دعوت میزبان را به نسخهٔ درست و قابل‌خواندن می‌رساند.
- workspace واقعاً خارج از هسته ساخته شده است.
- میزبان به MAIN/MASTER هیچ مجوز نوشتنی ندارد.
- نبود مسیر واسط برای write-back اثبات شده است.
- workspace در نشست/راه‌اندازی مجدد بازیابی می‌شود، اگر پایداری ادعا شده باشد.
- خروجی با provenance و digest به مالک تحویل می‌شود.

**تعریف موفقیت:** میزبان می‌تواند مستقل و آزمایشی کار کند، اما نه می‌تواند وارد هسته شود، نه آن را تغییر دهد و نه برای خود مجوز بیشتری مطالبه کند.

## 9. پیوند به معماری موجود

این معماری زیرمجموعهٔ همان ریشهٔ واحد `POINT-0/GOLDEN` و تنها صف فعال `NEXT-051` است. هیچ ریشه، صف، MAIN یا MASTER تازه‌ای ایجاد نمی‌کند. سه نقش بدون تغییر می‌مانند:

- MAIN: حاکمیت و مالکیت.
- HAIF: تداوم تعامل.
- RAHM: دریافت شواهد و پیشنهاد؛ بدون نوشتن در MASTER.

`IMPLEMENTED-IN-REPOSITORY` یا `DEPLOYED` فقط پس از ادغام، read-back و آزمون‌های واقعی قابل اعلام است.
