## Permanent rule

Every explicit registration command and every new official production MUST follow the project's traceable cross-layer registration workflow for its entire lifecycle. This rule remains active for future conversations and productions and is not a one-time checklist.

## No-loss lifecycle

`PRODUCTION → ID + FULL METADATA → CLASSIFY/APPLICABILITY → ROUTE → ACTUAL DESTINATION OPERATIONS → EVIDENCE → VERIFY → RECONCILE → LIVE PROJECT INTEGRATION → LIVING DOCUMENTATION → FINAL STATE`

If a required destination is unavailable, the production MUST enter durable Pending/Recovery with its identity, content/reference, intended destinations, reason, timestamps/provenance, and continuation/reconciliation path. The pending state remains active until verified reconciliation succeeds.

## Recovery is a bridge

When a destination becomes available, reconciliation MUST NOT stop at writing a recovery/reference file. It MUST re-evaluate applicability and propagate the same Production ID into every required live project structure, including applicable Reference, Architecture, Production Registry, living documentation, Checkpoint/Continuation, Runtime/Playground, Persistent Memory, Evidence, and Verification layers.

A recovery/archive file may remain as provenance, but it is never sufficient evidence of integration by itself.

## Claim and closure gate

- No actual write/execution → no success claim for that destination.
- No evidence → no verification claim.
- No verified integration → no FINAL/PROVEN closure.
- Any failed/unavailable required layer keeps the production PENDING/INCOMPLETE and preserves its recovery path.
- Each destination must have an explicit state: VERIFIED/REGISTERED, PENDING, FAILED, UNAVAILABLE, UNVERIFIED, or NOT APPLICABLE.
- Unknown metadata is never invented.

## Registration metadata

Applicable official records preserve: unique ID, date, exact local time, timezone, city/country when genuinely known, project, title, status, version, type, trigger/request, origin, method, architecture placement, applicable destinations, per-destination state, evidence, verification, result, checkpoint/recovery, continuation path, and next action.

## Operational requirement

This rule governs future registration behavior. It requires the workflow to treat registration as a lifecycle and integration operation, not as file archiving. A future execution must create its own evidence; the existence of this rule does not itself prove every future operation.

## Verification boundary

This record is a permanent architectural/operational rule. It does not fabricate persistent-memory success or future execution success. Those states require their own real evidence.
