## 1. هدف

حفظ تداوم هوشمندی و تداوم کار در رفت‌وآمد میان میزبان‌های مختلف هوش مصنوعی؛ به‌گونه‌ای که میزبان تازه مجبور نباشد به حافظهٔ پنهان گفت‌وگوهای قبلی تکیه کند و بتواند با دریافت یک بستهٔ معتبر، وضعیت کار، تصمیم‌ها، ورودی‌ها، خروجی‌ها و گام بعدی را بازیابی کند.

اصل طراحی: **سادگی اجرایی، شواهد واقعی، حریم خصوصی، و یک مرجع مرکزی واحد.** این سند زیرساخت تازه یا صف موازی ایجاد نمی‌کند.

## 2. معماری حداقلی

```text
HUMAN ↔ AI HOST
       │
       └─ explicit capture / owner-authorized connector
                    │
                    ▼
          INT / IN / OUT interaction ledger
                    │
                    ▼
        schema + provenance + integrity validation
                    │
                    ▼
       HOST PRIVATE WORKSPACE (isolated, scoped)
                    │
          owner-commanded export only
                    ▼
             PRIVATE RAHM (owner-only)
                    │
          cross-host reconciliation
                    ▼
        sanitized CHILD candidate / PR
                    │
             OWNER APPROVAL
                    ▼
                  MASTER
```

- هر میزبان فقط در فضای کاری خصوصی و محدود خودش کار می‌کند.
- هیچ میزبان، مستقیم یا غیرمستقیم، مجوز نوشتن به MASTER یا RAHM ندارد.
- میزبان می‌تواند پیشنهاد، تحلیل، تغییر پیشنهادی یا بستهٔ CHILD تولید کند؛ پیشنهاد به‌تنهایی مجوز ارتقا نیست.
- ارتقا به MASTER فقط پس از کنترل و تأیید مالک انجام می‌شود. پیشنهاد می‌تواند از مالک، دستیار هوش مصنوعی یا میزبان دیگر آمده باشد.
- RAHM خصوصی، مرکزی و خارج از workspace همهٔ میزبان‌هاست. تنها پل انتقال، خروجی‌ای است که مالک فرمان داده و کنترل کرده باشد.

## 3. قرارداد دفتر تعاملات

هر تعامل قابل‌ثبت، یک رکورد append-only با سه شناسهٔ پایدار دارد:

- `INT-YYYYMMDD-NNN` — شناسهٔ تعامل
- `IN-YYYYMMDD-NNN` — شناسهٔ ورودی
- `OUT-YYYYMMDD-NNN` — شناسهٔ خروجی

حداقل داده‌ها:
- ورودی و خروجی یا ارجاع امن به آن‌ها؛
- زمان عملیات UTC؛ زمان تهران فقط تبدیل مشتق‌شده از همان لحظه؛
- زمان پیام اصلی و زمان commit فقط در صورت وجود شاهد؛ در غیر این صورت `UNKNOWN / NOT_EXPOSED`؛
- وضعیت، lineage، ارجاع شواهد و وضعیت راستی‌آزمایی؛
- `behavior_analysis` به‌صورت اختیاری و خالی تا زمانی که تحلیل مستند و قابل دفاع وجود داشته باشد.

جست‌وجوی معکوس باید از شناسهٔ IN یا OUT به کل رکورد تعامل برسد. تغییر رکورد ثبت‌شده ممنوع است؛ اصلاح باید با رویداد جدید و پیوند به سابقه انجام شود.

## 4. وضعیت اجرایی واقعی

<text>این بخش مرز میان طراحی و اجرای اثبات‌شده را حفظ می‌کند.</text>

- Runtime محلی در `scripts/haif-runtime/` اکنون شناسه‌های INT/IN/OUT روزانه، lookup از IN یا OUT، زنجیرهٔ hash و read-back محلی را پیاده می‌کند.
- آزمون‌های Runtime و تطبیق رکورد واقعی با JSON Schema در اجرای Portable RAHM روی Golden SHA `934a9ce43de48fe368c5cdf13f93a504415015e5` موفق بوده‌اند؛ run `45019122233`.
- این Runtime فقط ورودی و خروجی‌ای را ثبت می‌کند که صریحاً به CLI داده شده باشد. **گرفتن خودکار گفت‌وگو از میزبان هنوز پیاده‌سازی نشده است.**
- تحلیل خودکار رفتار، ترجیحات و قصد کاربر هنوز فعال نیست؛ `behavior_analysis` خالی می‌ماند تا شواهد و معیارهای آن مشخص شوند.
- GitHub App، OAuth Broker، Remote MCP، OpenAI API runtime، میزبانی مستقل و clean-host recovery هنوز provision/verified نشده‌اند؛ پرونده‌های #114 تا #123 باز می‌مانند.

## 5. حافظه، آینه و مقصدهای جانبی

- **ChatGPT Persistent Memory:** زمینهٔ کمکی برای بازیابی ترجیحات و تداوم گفت‌وگو؛ مرجع قطعی پروژه یا دفتر مستقل با read-back تضمین‌شده نیست.
- **Library / ثبت آینه‌ای:** اختیاری و رویدادمحور؛ برای بازیابی و دسترسی دوم مفید است، اما لازم نیست پس از هر تغییر یا به‌صورت روزانه تکرار شود. مخزن GitHub مرجع اصلی می‌ماند.
- **Buffer:** `WAITING / DEFERRED / OPTIONAL`؛ تا زمانی که مزیت اجرایی مستقل و قابل‌اندازه‌گیری نشان ندهد، وارد مسیر اصلی نمی‌شود.
- **Dropbox:** `WAITING / DEFERRED / OPTIONAL`؛ برای هدف معماری فعلی وابستگی لازم نیست و تا اثبات مزیت، از مسیر اصلی کنار می‌ماند.
- هیچ‌یک از مقصدهای جانبی نباید به‌عنوان تکمیل‌شده گزارش شوند مگر اینکه همان مقصد، شاهد نوشتن، خواندن مجدد و تطبیق مستقل ارائه کند.

## 6. اصول حریم خصوصی و اعتماد

1. هیچ secret، token، کلید API، OAuth credential یا دادهٔ خام خصوصی در مخزن عمومی یا متن قابل‌مشاهدهٔ میزبان ثبت نمی‌شود.
2. میزبان فقط به محدودهٔ خصوصی خودش دسترسی دارد؛ هیچ مسیر نوشتن به MASTER یا RAHM ندارد.
3. دادهٔ خام خصوصی فقط در فضای خصوصی و تحت کنترل مالک می‌ماند؛ مخزن عمومی فقط policy، schema، کد و CHILD پاک‌سازی‌شده را نگه می‌دارد.
4. هر خروجی انتقالی باید provenance، hash، schema validation، وضعیت read-back و زمان UTC واقعی داشته باشد.
5. «مستند شده»، «در مخزن موجود»، «قابل استخراج»، «بازیابی مستقل» و «میزبان فعال» وضعیت‌های جداگانه‌اند.

## 7. مسیر آینده‌پژوهی بدون پیچیده‌سازی

هدف بلندمدت، هوش مصنوعی‌ای است که رفتار کاری، قصد، ترجیحات پایدار و زمینهٔ پروژه را بهتر بفهمد؛ اما نباید از ابتدا یک موتور پیچیدهٔ روان‌شناختی یا پایگاه دادهٔ موازی ساخت.

مسیر کم‌ریسک:
1. ثبت دقیق تعامل با INT/IN/OUT و provenance؛
2. استخراج الگوهای تکرارشونده فقط از شواهد واقعی و در صورت لزوم با تأیید مالک؛
3. جداکردن «ترجیح پایدار»، «دستور موردی»، «فرضیهٔ دستیار» و «نتیجهٔ تأییدشده»؛
4. ارزیابی اینکه هر الگو واقعاً کیفیت تعامل یا تداوم کار را بهتر می‌کند یا نه؛
5. انتقال فقط قواعد ارزشمند و تأییدشده به مرجع زنده.

هیچ برچسب حساس، حدس دربارهٔ شخصیت یا ادعای فهم رفتار بدون شواهد و مجوز مناسب تولید نمی‌شود.

## 8. معیار پذیرش و وضعیت

این سند یک قرارداد طراحی است، نه گواهی اجرای کامل. پذیرش عملی معماری نیازمند:
- ثبت و reverse lookup پایدار؛
- اعتبارسنجی رکوردهای واقعی با JSON Schema؛
- capture از میزبان واقعی با مجوز محدود؛
- export مالک‌محور و کنترل‌شده به RAHM؛
- آزمون منفی برای جلوگیری از دسترسی میزبان به MASTER/RAHM/secrets؛
- بازیابی مستقل روی میزبان پاک و read-back کامل؛
- تأیید مالک برای هر ارتقا به MASTER.

**وضعیت فعلی:** بخش دفتر محلی INT/IN/OUT پیاده‌سازی و آزموده شده؛ capture خودکار، اتصال سرویس مستقل، RAHM واقعی و بازیابی مستقل همچنان OPEN هستند. ادامه فقط در همان `POINT-0/GOLDEN` و `NEXT-051` انجام می‌شود.
