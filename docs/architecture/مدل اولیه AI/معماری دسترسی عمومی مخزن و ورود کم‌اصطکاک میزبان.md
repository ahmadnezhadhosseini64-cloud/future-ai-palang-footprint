## 1. تصمیم اصلی

مخزن عمومی GitHub می‌تواند بدون OAuth و بدون ورود به حساب GitHub، توسط هر میزبان سازگار به‌صورت ناشناس خوانده و clone شود. بنابراین OAuth نباید پیش‌شرط خواندن مخزن عمومی یا آغاز بازیابی منبع باشد.

مالکیت و حاکمیت معماری با مالک پروژه باقی می‌ماند. میزبان AI فقط عامل اجرایی موقت و قابل‌تعویض است؛ مدل، شرکت، رابط چت یا نشست میزبان مالک MASTER، تاریخچه، شاخهٔ اصلی یا سیاست‌های پروژه نمی‌شود.

Public بودن مخزن به معنی عمومی بودن محتوای آن است. این ویژگی برای دسترسی آسان مفید است، اما محرمانگی ایجاد نمی‌کند. هیچ راز، token، کلید خصوصی، اطلاعات حساس یا داده‌ای که نباید عمومی شود نباید در مخزن قرار گیرد. عمومی‌بودن مخزن همچنین دسترسی به workspace خصوصی، حافظهٔ میزبان یا حساب GitHub مالک را ایجاد نمی‌کند.

## 2. تفکیک چهار اختیار مستقل

| قابلیت | برای مخزن Public | نیاز به OAuth / GitHub login |
|---|---|---|
| مشاهدهٔ صفحات و فایل‌ها | بله، ناشناس | خیر |
| دریافت ZIP و clone/fetch عمومی | بله، ناشناس | خیر |
| اجرای کد در محیط میزبان | وابسته به ابزار و sandbox میزبان | خیر؛ اما محیط اجرا لازم است |
| ایجاد workspace خصوصی و پایدار | وابسته به امکانات میزبان | خیر؛ اما باید خود محیط آن را پشتیبانی کند |
| push، ایجاد branch از طریق API احراز‌شده، نوشتن فایل یا PR با هویت مالک | فقط با مجوز نوشتن | بله، یا credential امن معادل |
| تغییر تنظیمات خصوصی مخزن، secrets یا branch protection | فقط با سطح مجوز مناسب | بله |

نکته: GitHub CLI، API احراز‌شده و connectorهای حساب‌محور ممکن است برای عملیات نوشتن یا خواندن منابع خصوصی به احراز هویت نیاز داشته باشند. این الزام را نباید به خواندن عمومی مخزن تعمیم داد.

## 3. مسیر آغاز میزبان — بدون مانع OAuth برای خواندن

1. میزبان URL مخزن canonical را دریافت می‌کند.
2. ابتدا تلاش می‌کند با HTTPS عمومی، صفحهٔ مخزن، شاخهٔ main و آخرین commit را بخواند.
3. اگر ابزار Git در محیط موجود است، مخزن را بدون credential clone/fetch می‌کند؛ در غیر این صورت فایل‌ها و ZIP عمومی را از مسیر قابل‌دسترسی می‌خواند.
4. exact HEAD SHA را ثبت می‌کند و Reference Index، سند مادر، CURRENT، NEXT، manifest و receipt را از همان snapshot بازیابی می‌کند.
5. فایل‌ها و بسته را در workspace/sandbox مستقل میزبان استخراج و آزمون می‌کند؛ مخزن مرجع را read-only نگه می‌دارد.
6. اگر محیط میزبان امکان اجرای کد یا ذخیرهٔ پایدار ندارد، فقط همان قابلیت را OPEN / NOT AVAILABLE ثبت می‌کند؛ این محدودیت مانع READ عمومی نیست.
7. هیچ میزبان تازه‌ای برای شروع READ عمومی نباید منتظر OAuth بماند.

## 4. مسیر نوشتن — جدا و اختیاری

خواندن عمومی، مجوز نوشتن ایجاد نمی‌کند. اگر میزبان بخواهد تغییری را به GitHub برگرداند:

- ابتدا patch را در workspace خودش آماده و آزمون می‌کند.
- اگر ابزار میزبان امکان نوشتن احراز‌شده ندارد، patch، فایل‌ها و دستورهای قابل‌اعمال را به مالک تحویل می‌دهد؛ این حالت WRITE_NOT_GRANTED است، نه شکست بازیابی.
- اگر مالک بخواهد میزبان مستقیماً روی GitHub بنویسد، یک اتصال امن و احراز‌شده با حداقل مجوز لازم است؛ ترجیحاً فقط دسترسی Contents:write روی مخزن مشخص و بدون admin.
- میزبان فقط روی branch اختصاصی خود می‌نویسد و Pull Request می‌سازد.
- ورود تغییر به main، Release، workflowهای حساس یا تغییرات حاکمیتی تابع بررسی و تأیید مالک است. هیچ میزبان عادی حق push مستقیم به main یا تغییر حفاظت شاخه ندارد.
- token یا credential هرگز در prompt، فایل، log، receipt یا ZIP ذخیره نمی‌شود.

## 5. ماتریس مجوز و وضعیت‌ها

هر میزبان باید چهار قابلیت را جداگانه گزارش کند:

- READ: PUBLIC_ANONYMOUS / AUTHENTICATED / UNAVAILABLE
- EXECUTE: AVAILABLE / UNAVAILABLE
- WORKSPACE: EPHEMERAL / PERSISTENT_AND_ISOLATED / NOT_PROVEN
- WRITE: NONE / OWNER_MEDIATED_PATCH / AUTHENTICATED_BRANCH_ONLY / EXPLICITLY_GRANTED

وضعیت کلی نباید این قابلیت‌ها را در یک واژهٔ مبهم «متصل» ادغام کند. برای مثال:
- PUBLIC_SOURCE_RECOVERED: مخزن عمومی و فایل‌های مرجع خوانده شده‌اند.
- LOCAL_EXECUTION_VERIFIED: آزمون‌ها واقعاً در sandbox میزبان اجرا شده‌اند.
- WORKSPACE_READY: جداسازی و پایداری workspace با آزمون ثابت شده‌اند.
- WRITE_ENABLED: فقط پس از اثبات credential و مجوز واقعی.
- HOST_RECOVERED: فقط پس از بازیابی مستقل، read-back و آزمون restart با رسید مستقیم میزبان.

## 6. حاکمیت و مرز اعتماد

- مالک پروژه مرجع نهایی معماری، ارتقا و ادغام است.
- میزبان‌ها قابل‌تعویض‌اند و نباید به حافظهٔ یک نشست یا مدل خاص وابسته شوند.
- سند مادر و main مرجع canonical هستند؛ snapshot محلی یا ZIP فقط نسخهٔ pin‌شده با SHA و receipt است.
- ورودی‌های میزبان نامطمئن‌اند و ابتدا در proposal/quarantine قرار می‌گیرند.
- مسیر رشد: HOST → OBSERVATION/PROPOSAL → QUARANTINE → VALIDATION/RAHM → CHILD CANDIDATE → OWNER APPROVAL → MASTER.
- public بودن repo به معنی اجازهٔ ویرایش معماری نیست.
- تأیید مالک در گفتگو، قصد و اجازهٔ انجام مراحل مجاز را مشخص می‌کند؛ اما credential فنی، نشست OAuth یا قابلیت ابزار مقصد را به‌صورت جادویی ایجاد نمی‌کند.
- اگر ابزار همین محیط بتواند مخزن عمومی را بخواند، READ باید بی‌درنگ انجام شود و نباید به بهانهٔ OAuth متوقف شود.
