## Automatic promotion rule — without requiring a repeated user command

A material project output that is already present in an authorized project source or repository workflow must be evaluated for promotion as part of the normal verification lifecycle. The user does not need to repeat «ثبت کن» or separately request architectural registration for every eligible output.

If, and only if, all applicable gates pass, the verified result is promoted automatically into the relevant living architecture records and package source:
1. Provenance and project relevance are clear.
2. The output is a durable advance, not transient conversation, speculation, duplicate, unapproved personal detail, or an isolated example.
3. It is compatible with governing contracts and does not overwrite protected user-approved source text.
4. Identifiers, parent links, time source, references and cross-file consistency are valid.
5. Required tests, security checks, schema/link checks and package conformance pass on the exact tested source SHA.
6. The living master, applicable indexes/registries, runtime/specification and package source are reconciled.
7. The result is read back and compared with the intended content; evidence and test receipts are retained.
8. Only then may status advance to VERIFIED / PROMOTED and the canonical package be rebuilt/published.

No extra user prompt is required for this evidence-gated promotion once the eligible result is in the authorized repository/automation path.

## Quarantine and approval gates

Do not auto-promote uncertain, contradictory, sensitive, private, legally consequential, externally sourced but unlicensed, destructive, security-sensitive, cost-incurring, or permission-expanding changes. Keep them PROPOSED / QUARANTINED / NEEDS REVIEW until the necessary human authorization or clarification is obtained. Never infer consent to publish personal data or modify external services.

A failed or missing test is not a pass. A document entry is not proof of implementation. A green workflow on a parent SHA is not proof for a newer HEAD. Preserve failed runs and open gaps; do not silently close them.

## Execution boundary
