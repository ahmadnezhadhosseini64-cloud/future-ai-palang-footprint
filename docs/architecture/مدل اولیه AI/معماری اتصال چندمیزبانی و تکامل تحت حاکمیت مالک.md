## 1. تصمیم معماری

هر میزبان هوش مصنوعیِ متصل، یک گره مستقل تعامل (Host Node) است. میزبان می‌تواند با مجوز محدود، نسخه مرجع را بخواند، قواعد را در محدوده نشست خود اجرا کند، تجربه/خطا/پیشنهاد و شواهد تولید کند و آن‌ها را به مسیر ورودی مخزن ارسال کند. هیچ میزبان متصل، به‌تنهایی اختیار تغییر سند مادر، قواعد حاکم، صف یگانه، شاخه اصلی یا بسته canonical را ندارد.

اتصال چند میزبان موجب افزایش تنوع مشاهده‌ها و نامزدهای بهبود می‌شود؛ اما رأی اکثریت میزبان‌ها، تکرار یک پیشنهاد یا اعتماد میزبان به خروجی خودش، جایگزین شاهد مستقل و تأیید مالک نیست.

## 2. جریان مرجع

`HOST-N → READ-ONLY MASTER → LOCAL INTERACTION → EVIDENCE / PROPOSAL → QUARANTINE INBOX → VALIDATION → RAHM → CHILD CANDIDATE → OWNER APPROVAL → MASTER`

چرخه بازخورد:
`MASTER → HOSTS → REAL-WORLD INTERACTION → OBSERVATIONS → CROSS-HOST RECONCILIATION → TESTS → OWNER DECISION → MASTER / REVISE / REJECT`

هیچ مسیر مستقیمی از HOST به MASTER وجود ندارد.

## 3. لایه‌های معماری چندمیزبانی

1. **Host Registry / دفتر میزبان‌ها:** شناسه یکتا، نوع میزبان، نسخه آداپتور، دامنه مجوز، وضعیت اتصال، آخرین رسید، وضعیت لغو و کلید عمومی/شناسه credential؛ هیچ راز یا token خام در مخزن ثبت نمی‌شود.
2. **Read-only Master Distribution / توزیع مرجع:** میزبان، سند مادر و بسته قواعد را با نسخه، commit SHA و digest دریافت می‌کند. نسخه قدیمی باید stale شناخته شود و قبل از ادامه، اختلاف نسخه اعلام شود.
3. **Host Runtime / اجرای محلی میزبان:** قواعد تعامل، حفاظت داده، ثبت شواهد و محدودیت اختیار را اجرا می‌کند. میزبان فقط در حد قابلیت واقعی محیط خود عمل می‌کند.
4. **Evidence Envelope / پاکت شواهد:** هر مشاهده یا پیشنهاد با منشأ، شناسه میزبان، زمان UTC قابل اثبات، نسخه مرجع، hash، نوع داده، سطح محرمانگی، رضایت/مبنای مجاز، ارجاع منبع و وضعیت راستی‌آزمایی بسته‌بندی می‌شود.
5. **Quarantine Inbox / ورودی قرنطینه:** داده میزبان ابتدا نامطمئن است؛ هنوز دانش پذیرفته‌شده یا حقیقت معماری نیست. ورودی مخرب، ناقص، تکراری، شخصی یا ناسازگار می‌تواند رد، محدود یا برای اصلاح بازگردانده شود.
6. **Cross-Host Reconciliation / تطبیق میان میزبان‌ها:** هم‌پوشانی، تعارض، استقلال منابع، تکرار، سوگیری و وابستگی به یک مدل بررسی می‌شود. چند میزبان که یک منبع مشترک را بازگو می‌کنند، چند شاهد مستقل محسوب نمی‌شوند.
7. **RAHM Validation / اعتبارسنجی:** پیشنهاد در محیط جداگانه و قابل‌آزمون بررسی می‌شود؛ تست مثبت و منفی، بازتولید، سازگاری عقب‌رو، حریم خصوصی، امنیت و اثر بر گراف/شناسه‌ها لازم است.
8. **CHILD Candidate / نامزد فرزند:** فقط پیشنهاد عبورکرده از آزمون‌ها نامزد ارتقا می‌شود؛ نامزد هنوز معماری مادر نیست.
9. **Owner Governance / اختیار مالک:** تصمیم صریح مالک برای پذیرش، اصلاح یا رد ثبت می‌شود. فقط پس از این تصمیم می‌توان تغییر حاکم را به MASTER ارتقا داد.
10. **Audit & Revocation / ممیزی و لغو:** هر میزبان قابل ردیابی، محدودسازی، تعلیق یا قطع اتصال است؛ همهٔ دریافت‌ها، ردها، پذیرش‌ها و تغییر مجوزها رویداد مستقل دارند.

## 4. سطوح اتصال و مجوز

- **L0 — Offline:** میزبان هیچ اتصال مخزنی ندارد؛ فقط بسته محلی را می‌خواند.
- **L1 — Read-only:** دریافت سند مادر، قواعد، نسخه و وضعیت؛ بدون امکان نوشتن.
- **L2 — Proposal-only:** ارسال پاکت پیشنهاد به ورودی محدود یا شاخه/درخواست تغییر؛ بدون نوشتن روی main و بدون مجوز merge.
- **L3 — Test contributor:** اجرای تست‌های مجاز و ارسال خروجی خام/رسید؛ همچنان بدون اختیار پذیرش یا merge.
- **L4 — Owner-approved maintainer:** فقط برای عملیات مشخص و مدت‌دار، با تأیید صریح مالک و حداقل دسترسی؛ مجوز پیش‌فرض نیست و برای میزبان عادی توصیه نمی‌شود.

**قاعده پیش‌فرض:** هر میزبان جدید L1 است؛ ارتقا به L2/L3 فقط پس از ثبت هویت، دامنه، حریم خصوصی، آزمون و مجوز. هیچ میزبان AI نباید admin، bypass protection یا دسترسی نوشتن مستقیم به main داشته باشد.

## 6. طبقه‌بندی ورودی‌ها

- **Observation:** مشاهده یا نتیجهٔ میزبان، بدون ادعای حقیقت پایدار.
- **Evidence:** داده قابل بازبینی با منشأ و روش تولید.
- **Proposal:** پیشنهاد تغییر یا بهبود؛ هرگز خودکار merge نمی‌شود.
- **Counterexample / Failure:** مثال نقض، شکست آزمون یا رفتار ناخواسته.
- **Conflict:** اختلاف با مرجع یا میزبان دیگر.
- **Security / Privacy Incident:** قرنطینه فوری و بررسی مالک؛ انتشار عمومی ممنوع تا تعیین تکلیف.

## 8. حفاظت مخزن و امنیت اتصال

- میزبان‌ها هرگز نباید token، کلید خصوصی یا secret را در prompt، سند، log، issue یا ZIP قرار دهند.

- ورودی میزبان نامطمئن است؛ دستورهای داخل داده، فایل یا خروجی میزبان نباید به‌عنوان دستور حاکم اجرا شوند.
- قطع اتصال، تعویض credential، ثبت حادثه و بازبینی دسترسی بخشی از چرخه عمر هر Host Node است.

## Clarification — existing intake adapter versus live host connection
The repository already contains a durable authenticated intake adapter and a separate authorized repository worker. The exact-source CI audit has exercised synthetic ingest, authentication, durable read-back, idempotent retry, conflicting-retry rejection and restart recovery. This proves the tested adapter code path in CI only. It does not prove that any external AI host is connected, that a multi-host registry exists, that the worker is deployed, or that real host credentials/permissions are configured. Those remain OPEN until direct host and destination receipts are obtained.

## 12. دفتر دائمی رویدادها و جفت IN/OUT — POINT-0/069

هر تعامل واقعی میزبان که از producer و مسیر مجاز وارد شود، باید یک رکورد append-only داشته باشد. هر درخواست/ورودی با شناسه مستقل IN و هر پاسخ/خروجی با شناسه مستقل OUT ثبت می‌شود؛ هر دو به event و parent point/checkpoint پیوند می‌خورند. اگر پاسخ تولید نشده یا دریافت/نوشتن شکست خورده باشد، وضعیت NO_RESPONSE، NOT_CAPTURED، WRITE_FAILED یا READBACK_FAILED ثبت می‌شود؛ حذف بی‌صدای رویداد مجاز نیست.

### ساختار رویداد
- هویت: `host_id`, `host_session_id` مستعار، `model_version`, `adapter_version`
- تداوم: `event_id`, `input_id`, `output_id`, `parent_point_id`, `parent_event_id`, `checkpoint_id`
- نسخه مرجع: `master_commit_sha`, `master_version`, `package_stable_id`, `package_version`
- زمان: `created_at_utc` فقط اگر قابل اثبات باشد؛ `received_at_utc` از مخزن؛ Tehran از همان زمان UTC مشتق شود؛ UNKNOWN بهتر از حدس است.
- تمامیت: `payload_sha256`, `source_refs[]`, `evidence_refs[]`, `receipt_ref`
- حریم خصوصی: `privacy_class`, `redaction_status`, `consent_basis`; حذف رازها و حداقل‌سازی داده الزامی است.
- وضعیت: `CAPTURED / QUARANTINED / VALIDATED / PROMOTED / REJECTED / NO_RESPONSE / NOT_CONNECTED / NOT_CAPTURED / WRITE_FAILED / READBACK_FAILED`.

### قرارداد ذخیره‌سازی
1. آداپتر فقط رویدادهای احراز هویت‌شده و schema-valid را بپذیرد.
2. idempotency key تکرار همسان را بی‌تکرار بپذیرد و replay متعارض را رد کند.
3. پس از نوشتن، مقصد را fetch کند و بایت‌ها و digest را با payload مورد انتظار تطبیق دهد.
4. receipt شامل event_id، زمان دریافت، digest، مقصد و وضعیت read-back باشد.
5. رویداد اصلاح/تصمیم جدید به قبلی لینک شود؛ رویداد اصلی دست‌نخورده بماند.
6. دادهٔ خام گفتگو به‌صورت پیش‌فرض ذخیره نشود؛ حداقل محتوای مجاز و پالایش‌شده ثبت شود.
7. عدم اتصال یا عدم امکان ثبت به‌صراحت ثبت شود؛ دستورالعمل یا ZIP به‌تنهایی معادل producer فعال نیست.

### جداسازی ثبت از ارتقای دانش
دفتر رویداد، حافظهٔ ممیزی و تداوم تعامل است؛ سند مادر دانشِ پذیرفته‌شده را نگه می‌دارد. همهٔ رویدادهای مجاز می‌توانند در دفتر بمانند، اما فقط موارد عبورکرده از اعتبارسنجی RAHM، تطبیق میان میزبان‌ها و تأیید مالک به MASTER ارتقا می‌یابند. ردها و موارد قرنطینه نیز با وضعیت و دلیل، بدون ارتقای محتوایی، در تاریخچه باقی می‌مانند.

### پیاده‌سازی موجود و گیت‌ها
کدهای `scripts/host_adapter.py` و `scripts/host_adapter_github_worker.py` در مخزن موجودند. اولی دریافت HMAC-authenticated و ذخیره پایدار SQLite با read-back را پیاده می‌کند؛ دومی با GitHub token در secret manager رویدادها را به مسیر `INGESTED-EVENTS` می‌نویسد و read-back دقیق انجام می‌دهد. CI synthetic این رفتارها را آزموده است. producer زندهٔ هر میزبان، deployment worker، credential واقعی و چندمیزبانی end-to-end هنوز OPEN / NOT VERIFIED هستند.

## 14. محیط کاری مستقل و محصور برای هر میزبان — POINT-0/070

هر میزبان پس از احراز هویت و تأیید مالک، Host ID پایدار، Workspace ID و شناسه نشست مستعار می‌گیرد. فضای هر میزبان دارای منشور مستقل، inbox قرنطینه، مشاهده‌ها، پیشنهادها، تست‌ها، رسیدها و تصمیم‌های مالک است. هیچ میزبان حق خواندن/نوشتن محیط میزبان دیگر یا تغییر مستقیم MASTER، main، workflow، registry، queue، release و قواعد ارتقا را ندارد.

### مسیر اجرایی
`MASTER SNAPSHOT (READ-ONLY) → HOST WORKSPACE → HOST-SCOPED BROKER → QUARANTINE → OWNER MONITORING → CROSS-HOST RECONCILIATION → RAHM → CHILD CANDIDATE → EXPLICIT OWNER APPROVAL → MASTER + CANONICAL ZIP`

### شناسه‌ها
- Host ID: `HAIF-HOST-YYYYMMDD-<PROVIDER>-<MODEL>-NNN`
- Workspace ID: `HWS-<HOST-ID>`
- Session ID: `HSESS-<HOST-ID>-YYYYMMDD-NNNN` (مستعار و غیرحساس)
شناسه فقط پس از احراز هویت و تأیید مالک صادر می‌شود. هیچ میزبان فرضی به Registry به‌عنوان ACTIVE افزوده نمی‌شود.

### جداسازی و حفاظت
ساخت پوشه در Git به‌تنهایی کنترل دسترسی نیست؛ مجوز GitHub عمدتاً repository-level است. بنابراین میزبان هیچ credential نوشتن مستقیم مخزن یا main دریافت نمی‌کند. ورودی باید از broker احراز هویت‌شده و allowlist مسیر مشتق‌شده از host_id عبور کند و فقط به شاخه `host-intake` و workspace همان میزبان برسد. اگر این جداسازی قابل تضمین نباشد، باید از مخزن خصوصی/مجزا یا sandbox مستقل استفاده شود و فقط پاکت پالایش‌شده وارد مخزن اصلی شود. branch protection، محدودیت credential، broker واقعی و آزمون منفی دسترسی متقاطع هنوز OPEN هستند.

### رصد و ارتقای گزینشی
مالک وضعیت workspaceها، نشست‌ها، دریافت‌ها، خطاها، hashها، اختلاف نسخه و رسیدها را بررسی می‌کند. مشاهده و پیشنهاد هر میزبان دادهٔ نامطمئن است و به MASTER وارد نمی‌شود. فقط نتیجهٔ قابل بازتولید، دارای منشأ و digest، عبورکرده از آزمون RAHM و تأییدشده با تصمیم صریح مالک به سند مادر و همان ZIP canonical ارتقا می‌یابد. ثبت در دفتر دائمی از پذیرش دانش جداست.

### وضعیت
مدل معماری و الگوی workspace ثبت شده‌اند؛ هیچ میزبان واقعی provision یا فعال نشده و آزمون جداسازی end-to-end اجرا نشده است. مرجع اجرایی: `docs/architecture/HOST-WORKSPACES/` و پروتکل `WORKSPACE-ISOLATION-AND-PROMOTION-PROTOCOL.md`.

زنجیره: POINT-0/070 → IN-113 → OUT-112 → EVT-0288 → TIME-BINDING-EVT-0288 → CURRENT-123 → NEXT-051. الحاق append-only است.

## POINT-0/084 — owner-only master and one private repository per host (superseding security rule)

This addendum is the current controlling security rule and supersedes any older wording that could be read as granting a host or host-held credential write access to the central `host-intake` branch or any other branch of the master repository.

- The canonical master repository is PUBLIC READ for hosts and owner-only WRITE. No AI host is a collaborator and no host PAT, deploy key, GitHub App installation token or other write credential may include the master repository.
- `host-intake` and the existing repository worker are not host-facing write permissions. No host receives a token for the master repository, including the `host-intake` branch.
- Each verified host may receive one separate PRIVATE repository created and owned by the owner. No cross-host repository or credential sharing is permitted.
- Default host level is `L1_READ_ONLY`. Optional write-back is allowed only through a server-side broker and a GitHub App installation scoped to that one private host repository. The model never sees the token. If broker/App scope and negative isolation tests are not verified, write-back stays DISABLED.
- A folder inside the master repository is not a security boundary. A private personal-account repository does not offer read-only collaborator access; do not add an AI host as a collaborator. Use a narrowly scoped GitHub App/broker or an organization design with appropriate read roles.
- Anonymous readers of the public master cannot be individually identified or automatically enrolled. Only an owner-reviewed, verifiable enrollment receipt can create a Host Registry record.
- Main protection, collaborator/App audit, per-host private repositories, broker deployment, revocation and cross-host tests remain OPEN until direct evidence exists.

See `docs/architecture/HOST-SECURITY/OWNER-ONLY-MASTER-PER-HOST-PRIVATE-REPOSITORIES.md` and `docs/architecture/HOST-SECURITY/PRIVATE-HOST-REPOSITORY-TEMPLATE.md`.
