# سند مرجع مادر — رشد افزایشی معماری رفتارشناسی و آینده‌نگری

## 1. اصل حاکم و تغییرناپذیر
**معماری اولیه تغییر و بازنویسی نمی‌شود؛ فقط رشد می‌کند.**

این اصل یعنی:
- معماری اولیه، خط مبنای محفوظ و مرجع مقایسه است.
- هر قابلیت، مدل رفتاری، قرارداد، قاعده، آزمون یا کشف جدید به‌صورت افزودهٔ نسخه‌دار ثبت می‌شود.
- تاریخچه و نسخه‌های پیشین حذف یا بی‌صدا بازنویسی نمی‌شوند.
- اگر تصحیحی ضروری باشد، با الحاقیهٔ روشن شامل دلیل، منشأ، شاهد، نسخه، آزمون و پیوند به نسخهٔ قبلی ثبت می‌شود.
- «رشد معماری» با «تغییر خاموش خط مبنا» یکی نیست.
- این سند مادر حاکمیت رشد را تعیین می‌کند؛ خودش نیز فقط با نسخه‌ها و الحاقیه‌های قابل ردیابی تکامل می‌یابد.

## 3. هدف
این سند مرجع مادر تضمین می‌کند که رفتارشناسی ورودی‌های کاربر و خروجی‌های قابل مشاهدهٔ دستیار، مدل‌های تعامل، قواعد شماره‌گذاری، تصمیم‌ها، شواهد و پیش‌بینی‌های معماری به ساختاری انباشتی و بازیابی‌پذیر تبدیل شوند. هدف حفظ تداوم هوشمندی و کار است، نه جایگزین‌کردن معماری موجود با طرحی تازه.

## 4. قرارداد ثبت تعامل
- `INT-YYYYMMDD-NNN`: شناسهٔ زوج تعامل.
- `IN-YYYYMMDD-NNN`: ورودی کاربر.
- `OUT-YYYYMMDD-NNN`: خروجی قابل مشاهدهٔ دستیار.
- سه شناسه در هر زوج شمارهٔ مشترک دارند.
- شمارهٔ واقعی فقط پس از بررسی یکتایی تخصیص داده می‌شود. تا زمان وجود شمارندهٔ اجرایی معتبر، نباید ادعای شماره‌گذاری خودکار کرد.
- رویداد معماری با `EVT-NNNN-SLUG-YYYY-MM-DD` ثبت می‌شود؛ پیش از تخصیص شماره، مخزن جست‌وجو می‌شود.
- هر زوج باید به رویداد یا وضعیت «هنوز رویداد مستقل ندارد» پیوند داشته باشد و دارای منشأ، نسخه، وضعیت شواهد و اقدام بعدی باشد.

## 5. رفتارشناسی: مشاهده در برابر تفسیر
هر پرونده باید بخش‌های جداگانه داشته باشد:
1. ورودی مشاهده‌شده و نیاز صریح کاربر.
2. خروجی قابل مشاهدهٔ دستیار و اقدامات ابزار که واقعاً اجرا شده‌اند.
3. تفسیر رفتاری یا فرضیه، با برچسب «استنباط».
4. تصمیم معماری و دلیل آن.
5. شواهد: شناسهٔ فایل، commit، بازخوانی و آزمون.
6. شکاف‌ها، محدودیت‌ها و اقدام بعدی.

این روش زنجیرهٔ تفکر پنهان را ثبت یا بازسازی نمی‌کند؛ فقط رفتار قابل مشاهده، شواهد و استدلال‌های ثبت‌پذیر را مستند می‌کند.

## 6. معماری افزایشی
هر افزوده باید شامل موارد زیر باشد:
- شناسهٔ پایدار و شناسهٔ تولید؛ نسخه؛ تاریخ و منشأ.
- مسئله/نیاز و دلیل افزودن.
- پیوند به خط مبنای معماری و عناصر والد.
- مدل یا قاعدهٔ تازه، داده‌ها و قراردادها.
- معیارهای پذیرش و آزمون.
- نتیجهٔ واقعی آزمون و شاهد بازخوانی.
- اثر بر اجزای موجود، سازگاری و روش بازگشت.
- شکاف‌ها و گام بعدی.

**قاعدهٔ نسخه:** تغییرات افزایشی با نسخهٔ جدید یا فایل الحاقی ثبت می‌شوند. محتوای قبلی باید قابل بازیابی بماند. اصلاح فایل نمایه برای افزودن پیوند مجاز است، اما بازنویسی محتوای تاریخی به‌عنوان اینکه هرگز وجود نداشته، مجاز نیست.

## 7. خط لولهٔ چرخهٔ رفتار و ثبت
`CAPTURE → CLASSIFY → PAIR → PROVENANCE → MODEL → APPEND-ONLY CHANGE → VERSION → TEST → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → LINK → RESUME → LEARN`

ترجمه: دریافت → دسته‌بندی → زوج‌سازی → منشأ → مدل‌سازی → تغییر افزایشی → نسخه‌بندی → آزمون → نوشتن → بازخوانی → تطبیق → راستی‌آزمایی → رفع تعارض → پیونددهی → ادامه → یادگیری.

## 8. لنگر زمانی و شواهد
- زمان ثبت مخزن: زمان واقعی commit تغییر فایل در UTC.
- زمان تهران: تبدیل همان لحظهٔ UTC به Asia/Tehran.
- زمان پیام کاربر، زمان رخداد و زمان اجرای آزمون فیلدهای مستقل‌اند؛ فقط با شاهد منبع خود ثبت می‌شوند.
- زمان پیام یا تولید خروجی اگر در دسترس نباشد، `UNKNOWN / NOT CAPTURED` می‌ماند.
- زمان commit را نباید به‌جای زمان پیام یا مدت تفکر داخلی نشان داد.
- `WRITE ≠ READ-BACK ≠ MATCH ≠ VERIFIED`.
- هر مقصد جداگانه ثبت می‌شود: Repository، Library، Gmail، Buffer، Persistent Memory و Dropbox.

## 9. معماری آینده‌نگر: مسیر رشد پیشنهادی
### لایهٔ A — دفتر تعامل
دفتر تعامل با ورودی/خروجی‌های زوجی، شناسه‌ها، منشأ، نسخه و پیوندهای رویدادی. شکاف باز: تعریف JSON Schema و اعتبارسنجی داده.

### لایهٔ B — تحلیل رفتار
برچسب‌های رفتاری، نیاز، تصمیم، اصلاح، ابهام، خطا، ترجیح کاربر و نتیجهٔ مشاهده‌شده. برچسب‌ها باید قابل گسترش و نسخه‌دار باشند.

### لایهٔ C — گراف شواهد و منشأ
پیوند میان INT/IN/OUT، EVT، سند مرجع، لنگر ۰.۰، commit، آزمون، GAP و اقدام بعدی. هر یال باید نوع رابطه و شاهد داشته باشد.

### لایهٔ D — نسخه‌بندی معماری
ثبت هر افزوده با نسخه، دلیل، آزمون سازگاری، اثر، روش بازگشت و پیوند به نسخهٔ قبلی؛ خط مبنا محفوظ می‌ماند.

### لایهٔ E — بازیابی و ادامه
از لنگر ۰.۰ شروع کن؛ سند مادر و رویداد را بخوان؛ زوج تعامل، شاهدها، تغییرات و شکاف‌ها را دنبال کن؛ سپس آخرین اقدام معتبر را انتخاب کن. بازیابی پس از شروع مجدد هنوز باید با آزمون عملی اثبات شود.

### لایهٔ F — خودکارسازی اجرایی
جمع‌آوری خودکار ورودی/خروجی و تخصیص شمارنده فقط یک هدف طراحی است تا زمانی که در runtime پیاده‌سازی و آزموده شود. سند به‌تنهایی آن را فعال نمی‌کند.

- A3: معماری اولیه با افزوده رشد کرده باشد، بدون حذف محتوای تاریخی.
- A4: مدل FIOBAM در معماری و نمایه‌ها قابل بازیابی باشد.
- A5: فایل‌ها پس از نوشتن دوباره خوانده شوند و شناسه‌ها/پیوندها تطبیق داده شوند.
- A6: زمان commit واقعی UTC و معادل تهران ثبت شوند.
- A7: مقصدهای خارجی فقط با شاهد مستقل تأیید شوند.
- A8: ادعا، مشاهده، استنباط و پیش‌بینی از هم جدا باشند.
- A9: قابلیت‌های پیاده‌سازی‌نشده صریحاً در صف آینده باقی بمانند.

## 11. مقصدها و محدودیت‌های فعلی
- Repository: مقصد این ثبت؛ باید با read-back واقعی تأیید شود.
- Gmail: وضعیت اخیر BLOCKED / NOT SENT؛ هیچ ایمیلی از این ثبت ارسال نمی‌شود.
- Library / Buffer / Persistent Memory: نیازمند شاهد مستقل برای این ثبت.
- Dropbox: OPEN / NOT VERIFIED.
- Runtime خودکار: NOT IMPLEMENTED / NOT VERIFIED تا آزمون عملی.
- زمان دقیق پیام و مدت تفکر داخلی: UNKNOWN / NOT CAPTURED در صورت نبود فرادادهٔ مستقل.

## 12. برنامهٔ ادامه
1. دفتر زوج‌های تعامل و JSON Schema را بساز.
2. آزمون یکتایی شناسه و اعتبارسنجی پیوندها اضافه کن.
3. آزمون بازیابی پس از شروع مجدد را اجرا و نتیجه را به رویداد مستقل وصل کن.
4. ثبت append-only را با آزمون سازگاری و حفظ نسخهٔ قبلی اعتبارسنجی کن.
5. Dropbox و مقصدهای دیگر را جداگانه آزمایش کن؛ هیچ وضعیت ناموفق یا تأییدنشده را PASS نکن.
6. هر کشف تازه را به این سند مادر با الحاقیهٔ نسخه‌دار متصل کن.

## 13. زمان ثبت این نسخه
زمان مرجع این سند، commit واقعی ایجاد/آخرین تغییر همین فایل در UTC است. زمان متناظر تهران باید از همان instant مشتق شود. زمان پیام اصلی و زمان تولید پاسخ در صورت نبود فرادادهٔ مستقل، نامعلوم می‌مانند.
