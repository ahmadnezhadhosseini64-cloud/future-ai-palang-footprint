## 1. هدف عملیاتی و تعهد کاربر

این سند باید یک مسیر بازیابی واحد فراهم کند تا در مراجعهٔ بعدی کاربر مجبور نباشد تاریخچه را از نو تعریف یا چندین گزارش را کنار هم جمع کند. سند باید تا حد شواهد موجود نگه دارد:
- خواسته و مسئله‌ای که باعث تغییر شد؛
- مسیر قابل مشاهدهٔ تعامل و تصمیم؛
- تغییرهای معماری و چرایی آن‌ها؛
- شناسه‌ها، نسخه‌ها، منشأ، زمان‌ها و پیوندها؛
- کارهای انجام‌شده و شواهد پذیرش؛
- کارهای ناقص، در انتظار، مسدود یا دنبال‌نشده؛
- مقصدهایی که واقعاً ثبت و بازخوانی شده‌اند در برابر مقصدهای اثبات‌نشده؛
- اقدام بعدی دقیق، معیار بسته‌شدن و نقطهٔ توقف؛
- روش ادامه بدون پاک‌کردن تاریخچه یا ساختن ادعای بی‌شاهد.

این سند **بستهٔ اجرایی و مرجع حاکم** است، نه صرفاً گزارش وضعیت. بااین‌حال، هیچ سندی نمی‌تواند تعامل‌های قدیمیِ بازیابی‌نشده را عیناً بازسازی کند. هر محدودیت پوشش باید آشکار بماند.

## 2. قواعد حاکمِ غیرقابل‌تخطی

1. **NO CLAIM WITHOUT EVIDENCE — بدون شاهد، ادعا نکن.**
2. **WRITE ≠ READ-BACK ≠ MATCH ≠ VERIFY — نوشتن، بازخوانی، تطبیق و تأیید چهار مرحلهٔ جدا هستند.**
3. **INCOMPLETE ≠ LOST — ناقص به معنی گم‌شده نیست.**
4. **PENDING ≠ BURIED — در انتظار به معنی دفن‌شده یا قابل حذف نیست.**
5. **INTERRUPTED ≠ FAILED — توقف به معنی شکست نهایی نیست.**
6. **FOUND ≠ RETRIEVED ≠ VALIDATED ≠ REVIVED ≠ VERIFIED ≠ ACTIVE** — پیدا شدن، بازیابی، اعتبارسنجی، زنده‌سازی، تأیید و فعال بودن وضعیت‌های جدا هستند.
7. **CONNECTED ≠ TESTED ≠ VERIFIED** — اتصال به‌تنهایی آزمون یا تأیید نیست.
8. هر مقصد ذخیره‌سازی جداگانه ارزیابی می‌شود. موفقیت مخزن GitHub به معنی موفقیت Buffer (بافر)، Library (کتابخانه)، Persistent Memory (حافظهٔ پایدار) یا Dropbox نیست.
9. زمان پیام، مشاهده، اقدام، commit (ثبت تغییر در مخزن)، بازخوانی، تطبیق و تأیید جدا هستند. مهر زمانی commit فقط زمان commit را اثبات می‌کند.
10. زمان دقیقِ در دسترس‌نبوده باید `UNKNOWN / UNVERIFIED` بماند؛ هرگز از زمان commit برای حدس‌زدن زمان پیام استفاده نکن.
11. فقط کاربر می‌تواند یک نقطهٔ تازه را به‌عنوان ۰.۰ تعیین کند. این سند خودش ۰.۰ جدید نیست.
12. لنگرهای مستقل قبلی حفظ می‌شوند. پیوند دادن به معنی ادغام، بستن، جایگزین‌کردن یا تکمیل آن‌ها نیست.
13. سند مرجع باید مسیر ادامه و معیار اجرایی داشته باشد؛ خلاصهٔ گفت‌وگو یا لینک به‌تنهایی جای محتوای لازم برای بازیابی را نمی‌گیرد.
14. اگر نیاز به مجوز یا اقدام کاربر است، اقدام بعدی را مشخص کن و تا پیش از شاهد واقعی وضعیت را باز نگه دار.
15. هیچ مورد صف یا شکاف معماری فقط به علت ساختن سند جدید یا افزودن پیوند بسته نمی‌شود.

## 3. چرخهٔ کامل «ثبت کن» — قرارداد اجرایی

برای هر خروجی مهم یا تغییر معماری، این چرخه را اجرا کن و هر مرحله را با شاهد/وضعیت خودش ثبت کن:

`PRESERVE → IDENTIFY → CLASSIFY → CAPTURE ORIGIN → ASSIGN IDs → VERSION → ANCHOR → DOCUMENT → LINK → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → UPDATE QUEUES → STATUS → RESUME POINTER`

معنی فارسی:
حفظ → شناسایی → دسته‌بندی → ثبت منشأ → تعیین شناسه‌ها → نسخه‌بندی → لنگرگذاری → مستندسازی → پیونددهی → نوشتن → بازخوانی → تطبیق → تأیید → رفع تعارض و سازگار‌سازی → به‌روزرسانی صف‌ها → اعلام وضعیت → ثبت مسیر ادامه.

### 3.1 شناسنامهٔ اجباری هر خروجی مهم
- Stable ID (شناسهٔ پایدار)
- Production ID (شناسهٔ تولید)
- Version (نسخه)
- عنوان و نوع مورد
- تاریخ؛ ساعت دقیق فقط در صورت وجود شاهد
- منطقهٔ زمانی و منشأ مهر زمانی
- کاربر/مالک، پروژه و منشأ
- درخواست اصلی و دلیل ثبت
- زمینه، مسئله، GAP یا مشاهده
- فرضیه‌ها در برابر یافته‌های اثبات‌شده
- آزمون‌ها، نتیجه‌ها، شواهد و روش تطبیق
- تصمیم و دلیل انتخاب؛ گزینه‌های ردشده و دلیل
- ارتباط با والد، موارد مرتبط و مسیر قبلی/فعلی/بعدی
- اثر معماری و محل معنایی ادغام
- مسیر و پیوند بازیابی
- وضعیت مستقل هر مقصد
- آخرین مرحلهٔ موفق، آخرین شاهد، مانع و اقدام بعدی
- معیار پذیرش و شرایط بسته‌شدن

اگر داده‌ای وجود ندارد، آن را با `UNKNOWN`, `UNVERIFIED`, `N/A` یا وضعیت مناسب صریح ثبت کن؛ بخش لازم را بی‌صدا حذف نکن.

### 3.2 چرخهٔ محتوایی کامل
`ORIGIN → CONTEXT → QUESTION/PROBLEM/GAP → OBSERVATION → HYPOTHESIS → TEST → EVIDENCE → ANALYSIS → FINDING → ALTERNATIVES → DECISION + RATIONALE → SOLUTION/RULE → RESULT → ARCHITECTURAL IMPACT → REGISTRATION → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS`

### 3.3 چرخهٔ اثبات مقصد
برای هر مقصد به‌صورت مستقل:
1. بررسی قابلیت و مجوز واقعی؛
2. نوشتن محتوای کامل؛
3. بازیابی دوباره از همان مقصد؛
4. تطبیق محتوای بازخوانی‌شده با محتوای مورد انتظار؛
5. ثبت شاهد، نسخه/شناسه/مهر زمانی در صورت ارائه‌شدن؛
6. تعیین وضعیت دقیق همان مقصد.
اگر هر مرحله اجرا نشده، همان مرحله و مقصد باز می‌ماند.

## 4. نقشهٔ معماری و مسیر واحد

### 4.1 مسیر اصلی
`USER INTENT → INTERACTION TRACE → EVIDENCE/DECISION LINEAGE → ARCHITECTURE QUEUE → MASTER/LIVING REFERENCE → 0.0 ANCHOR (only when user-designated) → REPOSITORY WRITE → READ-BACK → MATCH → VERIFY → DESTINATION RECONCILIATION → RESUME`

مسیر فارسی:
قصد کاربر → دفتر تعامل → زنجیرهٔ شواهد و تصمیم → صف معماری → سند مرجع مادر/زنده → نقطهٔ ۰.۰ فقط در صورت تعیین کاربر → ثبت در مخزن → بازخوانی → تطبیق → تأیید → تطبیق مقصدها → ادامه.

### 4.2 لایه‌ها و نقش‌ها
- **Human / انسان:** تعیین هدف، اولویت، رضایت برای اقداماتی که نیازمند تصمیم یا مجوز او هستند، و تعیین انحصاری نقطهٔ ۰.۰.
- **AI Host / محیط میزبان AI:** ابزارها و قابلیت‌های اجرایی موجود؛ نباید محدودیت میزبان را به‌عنوان نقص یا موفقیت معماری جا بزند.
- **HAIF / معماری تعامل آیندهٔ انسان و AI:** مسیر مشاهده‌پذیر، پیوستگی کار، منشأ، تصمیم و بازگشت‌پذیری.
- **Master Reference / سند مرجع مادر:** قراردادها و قواعد حاکم؛ مرجع اجرا، نه جایگزین شواهد عملیاتی مقصدها.
- **Architecture Integration Queue / صف یکپارچه‌سازی معماری:** موارد ثبت‌شده‌ای که هنوز مقصد نهایی/ادغام یا آزمون‌های لازم را ندارند.
- **0.0 Registry / دفتر نقاط ادامه:** فهرست لنگرهای ۰.۰ مستقل و مسیرهای ازسرگیری.
- **Behavior Trace / دفتر رفتار:** رویدادهای متوالی و تغییرهای مشاهده‌پذیر.
- **Repository / مخزن:** مقصد مرجع کد/اسناد در این عملیات.
- **Buffer, Library, Persistent Memory, Dropbox:** سطوح مستقل؛ فقط با شواهد مختص خودشان تأیید می‌شوند.

### 4.3 جایگاه معماری این سند
این فایل در پوشهٔ اختصاصی زیر قرار می‌گیرد تا یک نقطهٔ ورود قابل حفظ و بازیابی داشته باشیم:

**D. Persistent Memory / حافظهٔ پایدار — UNVERIFIED**
- کار باقی‌مانده: از قابلیت واقعی حافظه و شواهدی که قابل بازیابی هستند استفاده کن؛ در غیر این صورت آن را به‌عنوان مانع باز ثبت کن.

## 8. دو قفل اجباری و مدیریت صف

### قفل حفظ — PRESERVATION LOCK
هیچ تغییر یا مورد کشف‌شده‌ای که هنوز ادغام نشده، حذف یا فراموش نشود. حداقل شناسه، منشأ، نسخه، وضعیت، مقصد، آخرین شاهد، مانع، اقدام بعدی و مسیر ادامه حفظ شوند.

### قفل تأیید ادغام — INTEGRATION VERIFICATION LOCK
هیچ موردی بدون تغییر واقعی مقصد، بازخوانی مستقل مقصد، تطبیق محتوای مورد انتظار و ثبت شاهد/نسخه/commit، `INTEGRATED / VERIFIED` اعلام نشود. صف و سند مقصد جداگانه بازخوانی شوند.

### حداقل نشانگر ادامه برای هر مورد باز
- Last completed step — آخرین مرحلهٔ تکمیل‌شده
- Last verified evidence — آخرین شاهد تأییدشده
- Pending destinations — مقصدهای باقی‌مانده
- Blocking constraint — مانع
- Next action — اقدام بعدی
- Acceptance criteria — معیار بسته‌شدن
- Resume pointer — مسیر دقیق ادامه
- Per-destination status — وضعیت مستقل هر مقصد
