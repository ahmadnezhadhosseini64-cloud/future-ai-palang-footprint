## 2. قانون قطعی ثبت دو زمان
برای هر تعامل/رویداد ثبت‌شونده، دو زمان مستقل بررسی و ثبت می‌شوند:

### A. User Message Time / زمان پیام کاربر
- زمان واقعی ارسال پیام کاربر، فقط اگر منبع قابل اتکا آن را نشان دهد.
- اگر در دسترس نیست: `UNKNOWN / UNVERIFIED — زمان پیام کاربر از شواهد در دسترس تعیین نشد`.
- هرگز زمان سیستم، زمان شروع پردازش، زمان commit یا زمان پاسخ را به‌جای زمان پیام کاربر ثبت نکن.

### B. Assistant Processing Time / زمان پردازش دستیار
- هنگام اقدام، ثبت، تصمیم مهم یا تولید سند مرجع، زمان واقعی محیط اجرا ثبت شود، اگر ابزار/محیط امکان خواندن ساعت دارد.
- قالب استاندارد: `YYYY-MM-DDTHH:mm:ss±HH:MM` همراه نام منطقه زمانی.
- در صورت امکان همان لحظه با UTC نیز ثبت شود تا مقایسه و تطبیق ممکن باشد.
- اگر ساعت محیط اجرا در دسترس نیست، صریحاً `UNKNOWN / UNAVAILABLE` ثبت کن؛ ساعت را حدس نزن.
- این زمان زمان پردازش است، نه زمان پیام کاربر.

### C. Event/Commit/Read-back Time / زمان رویداد، ثبت مخزن و بازخوانی
- در صورت ارائهٔ شاهد، زمان commit، زمان نوشتن، زمان بازخوانی و زمان آزمون به‌صورت رخدادهای جدا ثبت شوند.
- زمان پردازش دستیار نباید بدون شاهد به‌عنوان زمان commit یا بازخوانی معرفی شود.
- اگر زمان هر رخداد ثبت نشده، فیلد آن جداگانه نامعلوم بماند.

**قالب الزامی در اسناد مهم:**
- User message time / زمان پیام کاربر: [زمان معتبر یا UNKNOWN / UNVERIFIED]
- Assistant processing time / زمان پردازش دستیار: [زمان محیط اجرا یا UNKNOWN / UNAVAILABLE]
- Repository write/commit time / زمان ثبت مخزن: [شاهد واقعی یا UNKNOWN]
- Read-back verification time / زمان بازخوانی و تأیید: [شاهد واقعی یا UNKNOWN]
- Timezone / منطقه زمانی: نام منطقه و اختلاف UTC

این قاعده، نقص ثبت قبلی را اصلاح می‌کند: نامعلوم‌بودن زمان پیام کاربر دلیل حذف زمان پردازش دستیار نیست.

## 3. قانون لنگر برای ورودی و خروجی
برای هر ورودی کاربر و خروجی دستیار، ابتدا تشخیص بده آیا تعامل بر پروژه، قواعد، معماری، تصمیم، وضعیت یا تعهدهای باز اثر می‌گذارد. برای هر مورد اثرگذار:
1. یک Interaction Anchor / لنگر تعامل با شناسهٔ یکتا بساز یا آن را به لنگر درست پیوند بده.
2. ورودی و خروجی را از هم تفکیک و با رابطهٔ پاسخ/تصمیم/اصلاح به هم متصل کن.
3. شناسهٔ پایدار، شناسهٔ تولید، نسخه، منشأ، دو زمان، منطقهٔ زمانی، هدف، طبقه‌بندی و وضعیت را ثبت کن.
4. مسیر قبل و بعد، سند والد، نقطهٔ ۰.۰ مربوط و اقدام بعدی را حفظ کن.
5. سند مرجع کامل و قابل‌بازیابی بساز یا سند موجود را با نسخه/تاریخچه اصلاح کن.
6. اتصال به نمایه، دفتر ۰.۰، دفتر رفتار، صف یکپارچه‌سازی و سند مادر را واقعاً انجام بده یا به‌عنوان کار باز ثبت کن.
7. پس از نوشتن، همان مقصد را بازخوانی کن، محتوا/شناسه/پیوندها را تطبیق بده و شواهد را ثبت کن.
8. اگر ورودی/خروجی کم‌اهمیت و غیرمعماری است، لزوماً سند مستقل نساز؛ اما پیوستگی مکالمه را نگه دار و اگر طبقه‌بندی نامطمئن است آن را در صف بگذار. قاعده به معنی تولید بی‌رویهٔ فایل نیست.

## 4. چرخهٔ اجباری ثبت و اثبات
PRESERVE → ANCHOR → CLASSIFY → TRACE → DOCUMENT → CONNECT → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS → CONTINUE
(حفظ → لنگرگذاری → طبقه‌بندی → ردیابی مسیر → مستندسازی → اتصال → نوشتن → بازخوانی → تطبیق → راستی‌آزمایی → تطبیق نهایی → اعلام وضعیت → ادامه).

نوشتن موفق به معنی اثبات بازخوانی نیست. ثبت در مخزن به معنی ثبت در بافر، حافظه پایدار، کتابخانه یا Dropbox نیست. سند ثبت‌شده لزوماً به معماری مادر ادغام نشده است. وضعیت هر کدام باید مستقل باشد.

## 5. پیوستگی و اتصال همهٔ نقاط ۰.۰
- تمام نقاط ۰.۰ تاریخی حفظ می‌شوند؛ هیچ شمارش، نام‌گذاری یا «چهارتایی‌کردن» مجوز حذف، بازنویسی یا ادغام مخرب نیست.
- چهار گرهٔ پیمایش مرجع، فقط یک نمای مسیر هستند؛ محدودیت تعداد کل نقاط پروژه نیستند.
- دفتر مرکزی ۰.۰، هر نقطهٔ مستقل، لنگر والد/فرزند، شاخهٔ موضوعی، وضعیت باز/بسته، وابستگی و سند بازیابی را فهرست می‌کند.
- نقاط فقط پس از شناسایی، اعتبارسنجی، رفع تکرار با حفظ منشأ، تطبیق و اتصال واقعی در گراف به هم مرتبط می‌شوند.
- لنگر مستقل Dropbox با شناسهٔ `PALANG-DROPBOX-FAILOVER-RESUME-0.0-2026-10-12-001` تا وقتی اتصال، ذخیره و بازیابی مستقل آزموده نشده OPEN / WAITING می‌ماند؛ نباید به‌عنوان گام حل‌شده در زنجیرهٔ اصلی نمایش داده شود.
- نقطهٔ اصلی جاری در ۲۰۲۶-۱۰-۲۰، لنگرهای قبلی را جایگزین نمی‌کند.
- هر گره باید شناسه، مسیر سند، زمان‌ها، آخرین گام تأییدشده، موارد باز، اقدام بعدی و پیوند والد/فرزند داشته باشد.
- شمارش کامل تاریخی تا وقتی تمام منابع مرتبط بررسی نشده‌اند ادعا نمی‌شود.

## 6. دروازهٔ کشف رفتاری پیش از ارتقای معماری
CAPTURE → CLASSIFY → COMPARE → EVIDENCE → HYPOTHESIS → TEST → RECONCILE → PROMOTE OR KEEP IN QUEUE
(ثبت → طبقه‌بندی → مقایسه → شواهد → فرضیه → آزمون → تطبیق → ارتقا یا نگهداری در صف).

رفتار مشاهده‌شده با تفسیر دستیار یکی نیست؛ فرضیه با کشف تأییدشده یکی نیست. هر الگو باید شواهد، نمونه‌های نقض، شرایط، محدودیت میزبان، درجه اطمینان و نتیجه آزمون داشته باشد. فقط پس از بررسی و اعتبارسنجی می‌تواند به معماری مادر ارتقا یابد. در غیر این صورت OPEN / PENDING باقی می‌ماند.

طبقه‌ها: Noise / نویز؛ Local Bug / خطای محلی؛ Host Limitation / محدودیت میزبان؛ Architectural GAP / شکاف معماری؛ Valuable Idea / ایده ارزشمند؛ Fundamental Discovery / کشف بنیادی؛ Decision / تصمیم؛ Rule / قاعده؛ Evidence/Test / شاهد و آزمون؛ Open Obligation / تعهد باز.
