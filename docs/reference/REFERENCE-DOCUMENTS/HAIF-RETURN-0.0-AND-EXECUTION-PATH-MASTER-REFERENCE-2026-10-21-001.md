## 4. ترتیب اجرایی بازگشت

### مرحله A — بازیابی و راستی‌آزمایی مخزن
1. همین سند و لنگر ۰.۰ پیوندشده را از شاخهٔ اصلی مخزن بازخوانی کن.

3. وضعیت واقعی آخرین commit و اجرای گردش‌کارها/آزمون‌ها را از منبع زنده بررسی کن؛ برای هر اجرا شناسه، commit، نتیجه، هشدار و زمان واقعی را جداگانه ثبت کن.
4. اجرای موفق قبلی را بی‌دلیل تکرار نکن؛ آزمون فقط در صورت تغییر مرتبط، نتیجهٔ نامعلوم، رگرسیون محتمل یا نیاز اثباتی انجام شود.
5. پیوندهای خراب، اختلاف نسخه، شکست ثبت یا خواندن مجدد و مواردی را که هنوز اثبات نشده‌اند در صف باز نگه دار.

### مرحله B — قاعدهٔ زمان و لنگرها
برای هر ورودی و خروجی، تا جایی که شواهد واقعی در دسترس است، زمان‌ها را جدا ثبت کن:
- زمان واقعی پیام کاربر؛
- زمان وقوع رویداد، اگر مستقل و مستند باشد؛
- زمان commit هر فایل؛
- زمان بازخوانی پس از ثبت؛
- زمان لنگر نهایی زنجیره، مطابق commit نهایی واقعی.

قاعدهٔ نمایش: ابتدا UTC، سپس معادل دقیق تهران. اگر فقط زمان تهران موجود است، با اختلاف منطقهٔ زمانی آن را به UTC تبدیل کن و منبع و فرض تبدیل را ثبت کن. اگر زمان اصلاً موجود نیست، آن را «ثبت‌نشده/نامعلوم» بگذار؛ زمان commit مخزن را فقط به‌عنوان `repository_registration_anchor` (لنگر ثبت مخزن) ثبت کن، نه زمان پیام. زمان ساخت چند فایل را یکی نکن؛ هر commit زمان خودش را دارد.

### مرحله C — بازیابی شش سند واقعی پس از شروع مجدد
این آزمون باز است تا زمانی که شواهد کامل برای هر شش سند وجود داشته باشد:
1. شش سند واقعی را پیش از توقف و پس از شروع مجدد شناسایی کن.
2. برای هر سند، شناسه، مسیر مبدأ، نسخه، commit/تبار، و hash (هش/اثر انگشت محتوایی) را ثبت کن.
3. پس از شروع مجدد هر شش مورد را واقعاً بازیابی کن؛ صرف بازیابی یک سند اثبات شش‌سندی نیست.
4. تطبیق موردبه‌مورد را انجام بده؛ اختلاف، نبودن، hash نامطابق یا تبار نامشخص باید شکست/شکاف ثبت‌شده باشد، نه قبولی ضمنی.
5. آزمون‌های شکست برای write/read-back (نوشتن/بازخوانی) و hash mismatch (عدم تطابق هش) را بررسی یا اضافه کن؛ فقط پس از ثبت شواهد، نتیجه را تأیید کن.
6. نتایج را به رویداد و سند مرجع متصل کن و فقط شکاف‌هایی را ببند که شواهد بسته‌شدنشان موجود است.

2. یک فایل آزمونِ بی‌خطر با شناسه و نسخهٔ مشخص ذخیره کن.
3. همان فایل را از Dropbox بازخوانی و محتوا/هش را تطبیق بده.
4. بازیابی پس از شروع مجدد و مسیر جایگزین را آزمایش کن.
5. نتیجهٔ هر مرحله و محدودیت‌های اتصال را ثبت کن؛ صرف بازشدن صفحه یا موفقیت نوشتن، اثبات بازیابی نیست.

## 5. قاعدهٔ ثبت و اثبات

برای هر اقدام از این چرخه پیروی کن:

`PRESERVE → IDENTIFY → VERIFY → RECONCILE → REGISTER → PROMOTE`

یعنی: حفظ → شناسایی → راستی‌آزمایی → تطبیق/رفع تعارض → ثبت → ارتقا به مرجع.

چرخهٔ پذیرش نوشتن:

`WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS`

یعنی: نوشتن → بازخوانی → تطبیق → تأیید → رفع تعارض → اعلام وضعیت.

- موفقیت نوشتن به‌تنهایی اثبات بازخوانی نیست.
- «یافت شد»، «بازیابی شد»، «اعتبارسنجی شد»، «احیا شد»، «تأیید شد» و «فعال شد» وضعیت‌های متفاوت‌اند.
- ناقص به معنی گم‌شده نیست؛ در انتظار به معنی دفن‌شده نیست؛ وقفه به معنی شکست نهایی نیست.
- هیچ مقصدی را موفق اعلام نکن مگر شواهد همان مقصد وجود داشته باشد.
- اگر دسترسی مخزن/ابزار مسدود شد، ادعای نوشتن نکن؛ متن کامل قابل‌بازیابی را ارائه و محدودیت را ثبت کن.
