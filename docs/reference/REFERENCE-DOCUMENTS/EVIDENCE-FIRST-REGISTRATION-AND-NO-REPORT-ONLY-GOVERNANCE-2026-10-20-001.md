## 1. مسئله و تصمیم حاکم

کاربر صریحاً خواست که پاسخ صرفاً «گزارش» نباشد: دستیار باید واقعاً منبع را بررسی کند، از شواهد مطمئن شود و ادعای ساختگی یا تأییدنشده ندهد؛ سپس این الزام باید به‌صورت مستند، جامع، کامل، زمان‌مند و تا حد امکان زنده و فعال در معماری پروژه ثبت شود.

**تصمیم حاکم:** برای هر فرمان «ثبت کن»، گزارش وضعیت به‌تنهایی خروجی قابل‌قبول نیست. کار واقعی باید تا حد دسترسی و توان ابزار اجرا شود؛ هر ادعا باید به شاهد واقعی و قابل‌بازیابی متصل باشد. اگر بخشی قابل اجرا نیست، آن بخش باید با مانع، آخرین گام اثبات‌شده و اقدام بعدی به‌صورت OPEN / PENDING / BLOCKED حفظ شود. ثبت این قاعده در مخزن، به‌تنهایی اثبات ثبت در مقصدهای دیگر یا فعال‌شدن خودکار در هر محیط آینده نیست.

## 2. قرارداد الزام‌آور اجرا

چرخهٔ پایه:

`PRESERVE → FETCH CURRENT → CLASSIFY → TRACE ORIGIN → DEDUPLICATE → REGISTER → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS → RESUME`

معنی فارسی: حفظ ← بازیابی نسخهٔ جاری ← طبقه‌بندی ← ردیابی منشأ ← رفع تکرار ← ثبت ← بازخوانی ← تطبیق ← تأیید ← رفع مغایرت ← تعیین وضعیت ← ادامه.

1. **حفظ و منشأ:** درخواست اصلی، زمینه، تصمیم، دلیل، شواهد، محدودیت‌ها و مسیر بازیابی را نگه دار؛ مشاهده را از تفسیر جدا کن.
2. **بازیابی قبل از سؤال دوباره:** پیش از درخواست از کاربر برای تکرار اطلاعات، اسناد و سوابق قابل‌بازیابی را واقعاً بررسی کن.
3. **هویت و تبار:** Stable ID، Production ID، نسخه، والد، پیوندهای مرتبط و سابقه را حفظ کن. برای تلاش مجدد بی‌دلیل شناسهٔ جدید نساز و هیچ لنگر قبلی را بی‌اجازه بازنویسی یا ببند.
4. **ثبت کامل:** برای تغییر یا قاعدهٔ معماری، سند مرجع قابل‌بازیابی شامل مسئله، منشأ، شواهد، چرایی، تصمیم، اثر معماری، وابستگی‌ها، آزمون پذیرش، وضعیت هر مقصد و گام بعدی بساز یا نسخه‌دار به‌روزرسانی کن.
5. **نوشتن واقعی:** متن آماده‌شده یا پاسخ موفق ابزار به‌تنهایی ثبت تأییدشده نیست. مسیر، شاخه، نسخه و شناسهٔ commit/blob را در صورت وجود ثبت کن.
6. **بازخوانی واقعی:** پس از هر نوشتن، همان فایل را دوباره از مقصد هدف بخوان؛ محتوای بازخوانی‌شده را با محتوای مورد انتظار تطبیق بده.
7. **دامنهٔ تطبیق:** روشن کن چه چیزی بررسی شد. تطبیق عنوان یا شناسه را به‌جای تطبیق کل محتوا جا نزن؛ تطبیق محتوایی را «تطبیق رمزنگاری‌شدهٔ بایت‌به‌بایت» ننام مگر واقعاً انجام شده باشد.
8. **تأیید و رفع مغایرت:** تنها پس از وجود شاهد مناسب، همان مرحله را VERIFIED اعلام کن. اختلاف نسخه، پیوند ناقص یا مقصد ناتمام را آشکار و باز نگه دار.
9. **معماری:** فایل را در جای معنایی مناسب قرار بده و به سند مادر، دفتر ۰.۰، صف معماری و ردپای رفتار مرتبط وصل کن. پیوند دادن صرف، ادغام محتوایی را اثبات نمی‌کند.
10. **ادامه:** آخرین گام اثبات‌شده، کار باز، مانع، اقدام بعدی و نشانی بازیابی را ثبت کن تا ادامه به حدس یا حافظهٔ شفاهی وابسته نباشد.

## 3. قفل‌های حاکمیتی

- **Evidence Lock — قفل شاهد:** هیچ ادعای «انجام شد»، «کامل»، «فعال»، «دائمی» یا «تأیید شد» بدون شاهد متناسب با همان ادعا.
- **Destination Lock — قفل مقصد:** مخزن، کتابخانه، بافر، حافظهٔ پایدار و Dropbox مستقل‌اند؛ وضعیت یکی به دیگری سرایت نمی‌کند.
- **Time Lock — قفل زمان:** زمان دقیق پیام، اقدام، commit، بازخوانی و تأیید رویدادهای جدا هستند. زمان ناموجود باید UNKNOWN / UNVERIFIED بماند.
- **Lineage Lock — قفل تبار:** نسخه‌های قبلی، لنگرهای ۰.۰ و کارهای باز بدون اجازه حذف، ادغام یا بسته نمی‌شوند.
- **Integration Lock — قفل ادغام:** قرارگرفتن در صف یا داشتن پیوند به‌تنهایی ادغام در سند مادر نیست.
- **Recovery Lock — قفل بازیابی:** هر ثبت مهم باید شناسه، مسیر canonical، آخرین گام معتبر و دستور ادامه داشته باشد.
- **No-report-only Lock — قفل ممنوعیت گزارش صرف:** پاسخ نهایی باید حاصل اقدام و بررسی واقعی باشد. اگر ابزار اجازهٔ اقدام یا اثبات نداد، این محدودیت باید دقیق گفته شود و کار ناتمام حفظ شود؛ نباید جای اقدام را با نثر مطمئن‌نما پر کرد.

قواعد وضعیت:
- `WRITE ≠ VERIFIED` — نوشتن مساوی تأیید نیست.
- `INCOMPLETE ≠ LOST` — ناقص مساوی ازدست‌رفته نیست.
- `PENDING ≠ BURIED` — در انتظار مساوی مدفون‌شده نیست.
- `INTENDED ≠ EXECUTED` — قصد اجرا مساوی اجرای واقعی نیست.
- `LINKED ≠ INTEGRATED` — پیوندخورده مساوی ادغام‌شده نیست.
- `REPOSITORY VERIFIED ≠ ALL DESTINATIONS VERIFIED` — تأیید مخزن مساوی تأیید همهٔ مقصدها نیست.

## 4. ثبت زمانی و منشأ هر زمان

زمان‌ها باید جداگانه نگهداری شوند:

1. **Message/request time — زمان پیام/درخواست:** زمان ثبت‌شده توسط سامانهٔ پیام، اگر در دسترس باشد.
2. **Action time — زمان اقدام:** زمان واقعی اجرای ابزار، اگر شاهد معتبر داشته باشد.
3. **Repository registration time — زمان ثبت در مخزن:** مهر زمانی commit واقعی، نه زمان پیام.
4. **Read-back time — زمان بازخوانی:** زمان واقعی دریافت مجدد فایل.
5. **Verification time — زمان تأیید:** زمان واقعی بررسی تطبیق؛ با زمان نوشتن یکی فرض نشود.
6. **Last modified time — زمان آخرین تغییر:** از تاریخچهٔ واقعی همان مقصد، در صورت دسترسی.

هر زمان باید منبع، منطقهٔ زمانی و دقت داشته باشد. اگر دقیق نیست، سطح دقت (مثلاً فقط تاریخ یا دقیقه) اعلام شود. هیچ زمان ساختگی یا استنتاج‌شده‌ای به‌عنوان زمان دقیق رویداد ثبت نشود. زمان commit فقط شاهد زمان commit است. اگر شواهد فقط بازه‌ای را پشتیبانی می‌کنند، بازه با دو کران مستند و منطقهٔ زمانی ثبت شود؛ در غیر این صورت UNKNOWN / UNVERIFIED باقی بماند.

## 5. معیار «زنده»، «فعال»، «دائمی» و «کامل»

این واژه‌ها وضعیت واقعی مقصدها را جایگزین نمی‌کنند:

- **Repository-present / موجود در مخزن:** فایل در مسیر canonical قابل دریافت است.
- **Read-back matched / بازخوانی و تطبیق‌شده:** نسخهٔ نوشته‌شده دوباره دریافت و محتوای مورد انتظار در دامنهٔ مشخص بررسی شده است.
- **Architecturally integrated / ادغام‌شده در معماری:** محتوای لازم در محل حاکم مقصد واقعاً درج/به‌روزرسانی شده، بازخوانی و تطبیق شده و ارتباطات و اثر آن مستند است.
- **Active/Living / فعال و زنده:** مرجع جاری و نسخه‌دار است و قواعد فعال‌سازی/بازنگری آن روشن است؛ صرف درج عبارت ACTIVE/LIVING اثبات این وضعیت نیست.
- **Permanent / دائمی:** فقط می‌تواند به معنای نگهداری نسخه‌دار و قابل‌بازیابی در مقصد مشخص باشد؛ تضمین مطلق ماندگاری ابدی یا دسترسی خودکار در هر گفت‌وگوی آینده مجاز نیست.
- **Complete / کامل:** فقط در محدوده‌ای گفته شود که تمام مراحل الزامی همان محدوده شواهد دارند. تا وقتی هر مرحلهٔ الزامی یا مقصد لازم باز است، وضعیت کلی `PARTIAL / OPEN` باقی می‌ماند.

## 6. ثبت مستقل وضعیت مقصدها

برای هر اجرا این وضعیت‌ها جداگانه تعیین شوند:

- Repository / مخزن: وضعیت نوشتن، بازخوانی، تطبیق، تأیید و ادغام.
- Library / کتابخانه: فقط با شاهد مستقل ثبت و بازخوانی کتابخانه.
- Buffer / بافر: فقط با شاهد مستقیم همان بافر.
- Persistent Memory / حافظهٔ پایدار: فقط با شاهد مستقل ثبت/بازیابی حافظه.
- Dropbox / دراپ‌باکس: اتصال، نوشتن فایل آزمایشی، بازخوانی و تطبیق باید واقعاً انجام شوند.

اگر ابزار یا مجوز مقصدی موجود نیست، وضعیت آن UNKNOWN / UNVERIFIED یا BLOCKED / PENDING است. هیچ‌یک از این وضعیت‌ها از روی موفقیت مخزن حدس زده نمی‌شود.

### Evidence ledger — دفتر شواهد این ثبت

- **Pre-write fetch:** انجام شد برای پنج فایل فهرست‌شده در بالا؛ SHAهای دقیق پیش از تغییر در خروجی ابزار ثبت شده‌اند. این‌ها شواهد نسخهٔ پیش از تغییرند، نه شاهد نهایی ثبت این سند.
- **Write:** وضعیت تا پیش از عملیات نوشتن: انجام‌نشده؛ باید با پاسخ واقعی GitHub ثبت شود.
- **Read-back:** باید پس از نوشتن، فایل همین مسیر دوباره از مخزن خوانده شود.
- **Match:** باید شناسنامه، شناسه‌ها، نسخه، منشأ، قواعد شاهد/زمان، وضعیت مقصدها و اقدام بعدی در محتوای بازخوانی‌شده بررسی شوند.
- **Commit SHA / repository timestamp:** تا دریافت نتیجهٔ واقعی عملیات نوشتن/commit، UNKNOWN / UNVERIFIED.
- **Read-back / verification timestamp:** تا اجرای واقعی بازخوانی پس از نوشتن، UNKNOWN / UNVERIFIED.
- **Buffer / Library / Persistent Memory / Dropbox:** مستقل تأیید نشده‌اند؛ OPEN / PENDING / UNVERIFIED طبق شواهد موجود.

### Recovery procedure — روش بازیابی

1. این سند را از مسیر canonical بازخوانی کن و Stable ID، Production ID و Version را بررسی کن.
2. سپس سند حاکم فرمان و MRV را از مخزن بازیابی کن؛ هر دو باید واقعاً خوانده شوند.
3. همهٔ مقصدها را مستقل ارزیابی کن؛ از شواهد قدیمی به‌عنوان شاهد اجرای تازه استفاده نکن.
4. اگر فایل/پیوند/محتوا تغییر کرده، نسخهٔ جاری را fetch کن، تبار را تطبیق بده و سپس تغییر را ثبت کن.
5. پس از هر نوشتن، read-back و match انجام بده و شاهد commit/نسخه را ثبت کن.
6. تا زمان اثبات همهٔ مراحل الزامی، وضعیت کلی را `PARTIAL / OPEN` نگه دار.
7. Dropbox را خودکار آزمایش یا نقطهٔ باز آن را نبند؛ تا دستور ادامه و امکان واقعی اتصال، `OPEN / WAITING` باقی بماند.
