## 1. هدف و مسئله
این معماری برای نگهداری چندین نقطهٔ مستقل «۰.۰» ساخته شده است. کاربر ممکن است در زمان‌های مختلف چند جریان کار را به‌عنوان نقطهٔ ادامه تعیین کند؛ برخی کامل و برخی باز، ناقص، مسدود یا در انتظار باشند. عبارت «۰.۰» به‌تنهایی به معنی یک نقطهٔ یگانه نیست. هر نقطه باید هویت مستقل، توضیح روشن و وضعیت قابل اثبات داشته باشد تا در بازگشت، محل ادامه گم یا با موضوع دیگری اشتباه نشود.

## 2. تعریف عملیاتی
وقتی احمد پلنگ می‌گوید «این نقطه را ۰.۰ در نظر بگیر»، همان زمینهٔ مشخص‌شده به یک Resume Anchor (لنگر ادامهٔ کار) تبدیل می‌شود. نباید نقطهٔ ۰.۰ را از روی آخرین موضوع مکالمه حدس زد؛ تعیین آن از سوی کاربر لازم است. نقطه‌های مختلف نباید در یک شناسه یا پرونده ادغام شوند مگر با رابطهٔ صریح و حفظ تاریخچه.

## 3. مدل دادهٔ اجباری هر نقطه
هر پرونده باید تا حدی که شواهد وجود دارد این موارد را نگه دارد:
- Anchor ID / Stable ID (شناسهٔ یکتای نقطه)
- Production ID (شناسهٔ تولید)
- Version (نسخه) و تاریخچهٔ تغییر
- توضیح فارسی کوتاه و قابل‌فهم
- Origin / Lineage (منشأ و پیوند به سابقه)
- Status (وضعیت دقیق)
- Last Verified State (آخرین وضعیت واقعاً تأییدشده)
- Completed Steps (گام‌های انجام‌شده و تأییدشده)
- Open Tasks (کارهای ناتمام)
- Blocker / Dependency (مانع یا وابستگی)
- Next Action (اقدام بعدی دقیق)
- روابط با اسناد مرجع و سایر نقاط
- Repository Path / Retrieval Pointer (مسیر مخزن و نشانی بازیابی)
- وضعیت جداگانهٔ Repository, Dropbox, Buffer, Library, Persistent Memory
- Evidence / Limitation (شواهد و محدودیت‌ها)

زمان دقیق فقط وقتی ثبت می‌شود که واقعاً ثبت شده باشد؛ هرگز حدس زده نمی‌شود.

## 5. قرارداد ثبت نقطه
هنگام تعیین یک نقطهٔ جدید:
1. زمینهٔ دقیق موردنظر کاربر را حفظ کن.
2. ابتدا دفتر و پرونده‌های موجود را بازیابی و بررسی کن؛ نقطهٔ تکراری نساز.
3. شناسهٔ یکتا تعیین کن یا شناسهٔ قبلی را با حفظ lineage ادامه بده.
4. پروندهٔ کامل و قابل بازیابی بساز یا با نسخه‌گذاری به‌روزرسانی کن.
5. دفتر مرکزی را با شرح و وضعیت کوتاه، شناسه، اقدام بعدی و پیوند پرونده به‌روزرسانی کن.
6. روابط لازم را در سند مرجع مادر و سند حاکم فرمان «ثبت کن» درج کن.
7. هر فایل را جداگانه بازخوانی کن و محتوای مورد انتظار را تطبیق بده.
8. وضعیت هر مقصد را مستقل گزارش کن. اگر ابزار یا مجوز در دسترس نیست، آن مرحله باز می‌ماند و بستهٔ قابل‌کپی بازیابی ارائه می‌شود.

## 6. بازیابی نقطه‌های ناتمام
برای درخواست‌هایی مانند «نقطهٔ ۰.۰ تکمیل‌نشده چی مونده؟»:
- دفتر مرکزی و پرونده‌های مربوط را بررسی کن.
- همهٔ نقاط OPEN / INCOMPLETE / BLOCKED / WAITING را فهرست کن.
- برای هرکدام شناسه، شرح فارسی، آخرین گام تأییدشده، کار باقی‌مانده، مانع، اقدام بعدی و پیوند پرونده را بده.
- اگر وضعیت در دفتر با پرونده ناسازگار است، اختلاف را پنهان نکن؛ وضعیت را RECONCILIATION REQUIRED (نیازمند تطبیق) گزارش کن.
- تکمیل را از روی نیت یا نوشتن فایل استنباط نکن؛ شواهد لازم است.

## 7. وضعیت‌های مجاز
- OPEN / INCOMPLETE — باز / ناقص
- BLOCKED — مسدود
- WAITING — در انتظار
- READY TO VERIFY — آمادهٔ راستی‌آزمایی
- COMPLETED / VERIFIED — تکمیل و تأییدشده، فقط با شواهد
- SUPERSEDED — جایگزین‌شده، با حفظ تاریخچه
- RECONCILIATION REQUIRED — نیازمند تطبیق بین سوابق

## 8. اصل اثبات و عدم ادعای کاذب
WRITE → READ-BACK → MATCH → VERIFY (نوشتن ← بازخوانی ← تطبیق ← تأیید) برای هر فایل و هر مقصد جداگانه است. موفقیت در مخزن، موفقیت در Dropbox یا Library یا Buffer یا Persistent Memory را اثبات نمی‌کند. اتصال ≠ آزمون موفق ≠ تأیید. نقطهٔ ناقص به معنی گم‌شده نیست؛ نقطهٔ باز باید حفظ شود تا بعداً ادامه یابد.
