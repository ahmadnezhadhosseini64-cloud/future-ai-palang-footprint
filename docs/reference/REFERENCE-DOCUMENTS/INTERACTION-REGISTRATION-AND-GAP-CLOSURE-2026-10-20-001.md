## 1. هدف و دامنه
این سند، درخواست جاری را به‌عنوان یک رویداد مستقل و قابل‌بازیابی ثبت می‌کند و وضعیت شکاف‌ها را با تفکیک «کار انجام‌شده»، «شکاف بسته‌شده با شاهد» و «شکاف باز» نگه می‌دارد. هدف نهایی پروژه، Continuity of Intelligence / Continuity of Work (تداوم هوشمندی / تداوم کار) در تعامل انسان و AI است، نه صرفاً تولید اسناد.

## 2. قاعدهٔ اجباری برای هر ورودی و خروجی
برای هر ورودی کاربر و خروجی دستیار، تا حدی که ابزارها و دسترسی‌های واقعی اجازه می‌دهند:
1. حفظ متن/معنا، منشأ و پیوند به زنجیرهٔ قبلی؛
2. ایجاد Anchor / لنگر و Event ID / شناسهٔ رویداد یکتا؛
3. ثبت Stable ID / شناسهٔ پایدار، Production ID / شناسهٔ تولید، Version / نسخه، تاریخ و زمان فقط در حد شواهد موجود، منطقهٔ زمانی، مالک، پروژه، وضعیت، مقصد و محدودیت؛
4. طبقه‌بندی و تعیین اینکه موضوع مشاهده، فرضیه، تصمیم، آزمون، شکاف یا قاعده است؛
5. تولید سند مرجع کامل و قابل‌بازیابی، نه صرفاً گزارش کوتاه؛
6. ثبت در مخزن مرجع و اتصال به دفتر ۰.۰، نمایهٔ مرجع، دفتر رفتار و صف یکپارچه‌سازی، هرجا مرتبط باشد؛
7. WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS (نوشتن → بازخوانی → تطبیق → راستی‌آزمایی → تطبیق میان‌مقصدی → اعلام وضعیت)؛
8. گزارش مستقل وضعیت Repository / مخزن، Buffer / بافر، Persistent Memory / حافظهٔ پایدار، Library / کتابخانه و Dropbox؛
9. اگر مقصدی قابل‌دسترسی یا قابل‌اثبات نیست، آن را OPEN / UNVERIFIED نگه دار و متن کامل بازیابی را ارائه کن؛ هرگز ذخیره یا بستن شکاف را جعل نکن.

این قرارداد یک قاعدهٔ اجرایی/حاکمیتی است؛ درج آن در مخزن به‌تنهایی تضمین نمی‌کند که سامانه در پس‌زمینه به‌طور خودکار تمام ورودی‌ها و خروجی‌های همهٔ نشست‌ها را دریافت می‌کند.

## 3. قاعدهٔ کشف رفتاری و ورود به معماری
CAPTURE → CLASSIFY → COMPARE → EVIDENCE → HYPOTHESIS → TEST → RECONCILE → PROMOTE OR KEEP IN QUEUE
(ثبت → طبقه‌بندی → مقایسه → شواهد → فرضیه → آزمون → تطبیق → ارتقا یا نگهداری در صف).

ثبت یک الگوی رفتاری به معنی اثبات آن یا اجازهٔ ورودش به معماری مادر نیست. باید شواهد، نمونه‌های نقض، شرایط اجرا، محدودیت میزبان، درجهٔ اطمینان و نتیجهٔ آزمون ثبت شود. موارد تأییدنشده در صف OPEN / PENDING باقی می‌مانند.

## 4. نتیجهٔ بررسی شکاف‌ها در این اجرا

### 4.1 موردی که می‌توان بست، مشروط به اثبات مخزنی
- شکاف محدود «نبودِ ثبت مستقل و قابل‌بازیابی برای همین درخواست و پاسخ در مخزن مرجع» با ایجاد این سند و رویداد EVT-0032 و بازخوانی هر فایل/نمایه قابل‌بستن است.
- دامنهٔ این بسته‌شدن فقط همین تعامل و پیوندهای مخزنی بررسی‌شده است؛ به معنی بستن شکاف اجرای خودکار عمومی نیست.

### 4.2 شکاف‌هایی که هنوز باز هستند
- G-AUTO: اثبات capture/لنگرگذاری خودکار و پایدار برای تک‌تک ورودی‌ها و خروجی‌ها در همهٔ نشست‌ها؛ این تعامل به‌تنهایی آزمون سرتاسری نیست.
- تطبیق کامل همهٔ نقاط تاریخی ۰.۰ و ایجاد گراف کامل بدون حذف یا ادغام مخرب.
- اتصال، نوشتن، بازخوانی و بازیابی مستقل Dropbox؛ شاخهٔ Dropbox همچنان OPEN / WAITING است.
- اثبات مستقل Buffer / بافر، Persistent Memory / حافظهٔ پایدار و Library / کتابخانه؛ هیچ ادعای موفقیت این مقصدها از ثبت مخزنی نتیجه نمی‌شود.
- آزمون بازیابی سرتاسری و idempotency / اجرای تکراری بدون ایجاد رکورد تکراری، با شواهد قابل‌بازخوانی.
- اجرای آزمون رفتاری واقعی و ارتقای هر کشف به معماری مادر فقط پس از اعتبارسنجی.
- بازبینی و تطبیق کامل تمام پیوندهای میان دفتر ۰.۰، دفتر رفتار، صف، نمایه و سند مادر پس از این تغییر.

### 4.3 معیار بستن هر شکاف
شکاف فقط وقتی CLOSED / VERIFIED (بسته / راستی‌آزمایی‌شده) می‌شود که: اقدام واقعی انجام شده باشد، شاهد مستقل متناسب با ادعا موجود باشد، نتیجه بازخوانی شود، محتوای مورد انتظار تطبیق یابد، پیوندهای مرتبط بررسی شوند و دامنهٔ ادعا دقیقاً با دامنهٔ آزمون برابر باشد. «ثبت شد» یا «در صف است» معادل «بسته شد» نیست.
