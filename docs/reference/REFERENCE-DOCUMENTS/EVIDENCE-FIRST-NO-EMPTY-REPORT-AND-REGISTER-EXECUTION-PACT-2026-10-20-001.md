## 1. Decision and purpose
این سند یک قرارداد اجرایی است، نه گزارش وضعیت. درخواست کاربر این است که دستیار پیش از اعلام موفقیت واقعاً منابع و شواهد در دسترس را بررسی کند؛ نتیجهٔ بررسی را به یک ثبت قابل‌بازیابی وصل کند؛ و از گزارش‌های خالی، ادعای بی‌شاهد، تکرار ادعای قبلی به‌جای آزمون و استفاده از واژه‌های «کامل»، «دائمی»، «فعال» یا «تأییدشده» بدون اثبات جلوگیری کند.

این قرارداد به چرخهٔ حاکم «ثبت کن» اضافه می‌شود؛ جایگزین MRV مادر، تاریخچه، شناسه‌های پیشین، لنگرهای مستقل ۰.۰ یا قواعد قبلی نیست. در صورت تعارض، شواهد واقعی و قرارداد مادر ملاک‌اند؛ تعارض باید ثبت و حل شود، نه پنهان.

## 2. الزام «بررسی واقعی پیش از پاسخ»
هرگاه کاربر درخواست «ثبت کن»، «خاک‌برداری»، «کامل کن»، «تأیید کن» یا بررسی وضعیت می‌دهد:
1. ابتدا مرجع مرتبط را از منبع واقعی و قابل‌دسترسی بازیابی کن؛ اگر مخزن در دسترس است، فایل‌ها و نسخهٔ جاری را مستقیماً بخوان.
2. هر ادعای مهم را به شاهد مشخص وصل کن: مسیر فایل، شناسه، نسخه/commit/blob SHA، محتوای بازخوانی‌شده، یا نتیجهٔ مستقل ابزار.
3. میان «آنچه منبع می‌گوید»، «آنچه همین اجرا مشاهده کرد»، «استنباط» و «آنچه هنوز نامعلوم است» تفکیک بگذار.
4. به نتیجهٔ ابزار نوشتن اکتفا نکن؛ همان نسخه را پس از نوشتن دوباره از مقصد بخوان و محتوای مورد انتظار را بررسی کن.
5. اگر دسترسی، ابزار، یا شاهد کافی وجود ندارد، دقیقاً همان مرحله را BLOCKED / PENDING / UNKNOWN ثبت کن؛ کاربر را با اطمینان کاذب آرام نکن.
6. از آزمون تکراریِ بدون دلیل خودداری کن؛ آزمون را فقط در صورت تغییر نسخه/محتوا/دسترسی، شکست، ناسازگاری شواهد، یا نیاز صریح به تأیید تازه تکرار کن.

## 3. چرخهٔ پذیرش و اثبات
`PRESERVE → IDENTIFY → CLASSIFY → PROVENANCE → STABLE ID / PRODUCTION ID / VERSION → ANCHOR → COMPLETE REFERENCE → ARCHITECTURE INTEGRATION → TIMESTAMP EVIDENCE → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS BY DESTINATION → NEXT ACTION → RESUME`

ترجمه: حفظ → شناسایی → طبقه‌بندی → منشأ و تبار → شناسه‌ها و نسخه → لنگر → سند مرجع کامل → ادغام معماری → شواهد زمانی → نوشتن → بازخوانی → تطبیق → تأیید → رفع تعارض → وضعیت جداگانهٔ هر مقصد → اقدام بعدی → ادامه از نقطهٔ بازیابی.

هر مرحله شاهد مستقل خود را می‌خواهد. `WRITE ≠ READ-BACK ≠ MATCH ≠ VERIFY`؛ نوشتن، بازخوانی، تطبیق و تأیید یکی نیستند. لینک‌دادن به سند، به‌تنهایی ادغام معنایی یا پذیرش معماری را اثبات نمی‌کند.

## 4. ممنوعیت گزارش خالی
پاسخ نهایی نباید فقط فهرست کارها، وعده، خلاصه، یا عبارت «ثبت شد» باشد. برای هر ثبت باید:
- سند کامل قابل‌بازیابی ساخته/به‌روزرسانی شود، اگر موضوع نیازمند ثبت مرجع است؛
- تصمیم، دلیل، منشأ، شواهد، روابط معماری، تعارض‌ها و محدودیت‌ها ثبت شوند؛
- وضعیت واقعی هر مقصد و آخرین مرحلهٔ اثبات‌شده ذکر شود؛
- مسیر بازیابی و اقدام بعدی دقیق باشد؛
- نتیجهٔ بازخوانی پس از نوشتن بررسی شود و هر اختلاف آشکار بماند.
اگر امکان نوشتن واقعی وجود ندارد، باید سند کامل و قابل‌کپی برای بازیابی ارائه شود و صریحاً گفته شود که در مخزن ثبت نشده است.

## 5. تفکیک مقصدها

## 6. قاعدهٔ زمان‌گذاری

## 7. منع ادعاهای بیش از حد
- `ACTIVE / LIVING` به‌عنوان وضعیت معماری یا قرارداد، خودبه‌خود به معنی اجرای خودکار قواعد در هر محیط و گفت‌وگوی آینده نیست.
- `PERMANENT / دائمی` یعنی مرجع نسخه‌گذاری‌شده و قابل‌بازیابی با تاریخچه تا جایی که سرویس و دسترسی اجازه می‌دهند؛ نه تضمین مطلق ماندگاری ابدی.
- `COMPLETE / کامل` فقط نسبت به معیارهای پذیرش تعریف‌شده و شواهد همان مقصد قابل اعلام است.
- `FOUND ≠ RETRIEVED ≠ VALIDATED ≠ REVIVED ≠ VERIFIED ≠ ACTIVE`.
- `INCOMPLETE ≠ LOST`; `PENDING ≠ BURIED`; `INTERRUPTED ≠ FAILED`.
- هیچ وضعیت خارج از مخزن با وجود لینک، حافظهٔ مکالمه یا ادعای قبلی اثبات نمی‌شود.
