## 3. معماری به‌ارث‌رسیده و سازگاری پروژهٔ جدید

| لایه | مسئولیت ارث‌رسیده | توسعه در پروژهٔ جدید |
|---|---|---|
| L0 تعامل انسان | قصد، ورودی، اصلاح، تصمیم و بازخورد | کنترل‌های تعاملی و ثبت زوج IN/OUT |
| L1 میزبان AI | دریافت درخواست و پاسخ | میزبان قابل‌تعویض؛ میزبان منبع حقیقت نهایی نیست |
| L2 هستهٔ تداوم | لنگرها، CURRENT/NEXT و بازیابی | هر نقطه مستقل، نسخه‌دار و قابل ادامه |
| L3 منشأ و شواهد | منبع، نسخه، زمان، hash و بازخوانی | هر ادعا دارای وضعیت شواهد و محدودهٔ راستی‌آزمایی |
| L4 گراف دانش | سند، رخداد، تصمیم، شکاف و رابطه | رابطه‌های نوع‌دار؛ نامزدها تا داوری VERIFIED نمی‌شوند |
| L5 حاکمیت و ارتقا | Master → Child → Rahm → تصمیم | تغییرات آزمایشی و ارتقای کنترل‌شده با معیار پذیرش |
| L6 برنامه و رابط | نمایش اسناد، وضعیت، گراف و صف | نمونهٔ تعاملی کوچک، سپس توسعهٔ مرحله‌ای |
| L7 آداپترهای ذخیره‌سازی | مرزبندی مقصدها و وضعیت مستقل | هر مقصد با نوشتن، بازخوانی و تطبیق جداگانه تأیید می‌شود |
| L8 رفتارشناسی و آزمایش | ثبت رفتار آشکار، خطا و بازخورد | چرخهٔ فرضیه → آزمون → داوری → پذیرش/اصلاح/رد |
| L9 بازیابی و انتقال | خروجی قابل‌حمل و بازیابی سرد | آزمون واقعی از IN یا OUT تا مادر، شواهد و صف |

این لایه‌ها چارچوب منطقی‌اند؛ وجودشان در سند به معنی پیاده‌سازی نرم‌افزاری همهٔ آن‌ها نیست.

## 4. قواعد دائمی رشد و تکامل

1. **حفظ تاریخچه:** CURRENT-037، CURRENT-038، CURRENT-039، Project Zero baseline و تمام نقاط قبلی حفظ می‌شوند. هیچ نقطه‌ای بی‌صدا جایگزین نقطهٔ دیگر نمی‌شود.
2. **UTC مرجع زمانی:** زمان canonical ثبت مخزنی از commit واقعی Git به UTC گرفته می‌شود؛ معادل تهران از همان لحظه و با UTC+03:30 محاسبه می‌شود. زمان پیام، اجرا و بازخوانی جدا هستند.
3. **ثبت شواهدمحور:** نوشتن، بازخوانی، تطبیق محتوا، آزمون معنایی و بازیابی سرد وضعیت‌های متفاوت‌اند.
4. **چرخهٔ ثبت:** حفظ منشأ → طبقه‌بندی → IN/OUT → شناسه و نسخه → لنگر/رویداد → سند مادر/صف → نوشتن → بازخوانی → تطبیق → راستی‌آزمایی → وضعیت و اقدام بعدی.
5. **دو مسیر رفتاری:** مسیر A برای تداوم زمینه، بازیابی و رشد؛ مسیر B برای کنترل انحراف از هدف، صحت ادعا و حفظ محدودیت‌ها. هر دو پیش از تصمیم بررسی می‌شوند.
6. **Master–Child–Rahm:** پیشنهاد تازه در Child می‌ماند؛ Rahm آن را با معیار پذیرش و شواهد می‌سنجد؛ فقط نتیجهٔ پذیرفته‌شده به Master ارتقا می‌یابد.
7. **درس خطا:** انحراف به مسیر نامرتبط، مانند پیگیری Dropbox هنگامی که هدف جاری توسعهٔ مدل است، به‌عنوان خطای مسیر و درس معماری ثبت می‌شود؛ علت پنهان حدس زده نمی‌شود.
8. **مقصدهای مستقل:** تأیید GitHub، Buffer، Persistent Memory، Library و Dropbox جداگانه است. «زنده» به معنی ضبط خودکار پس‌زمینه‌ای اثبات‌شده نیست.
9. **عدم تکرار بی‌دلیل:** آزمون معتبر دوباره اجرا نمی‌شود مگر تغییر واقعی، نیاز جدید، خطا/پس‌رفت یا شاهد متناقض وجود داشته باشد.
10. **حریم خصوصی:** دادهٔ حساس و غیرضروری در فایل‌های عمومی مخزن تکثیر نمی‌شود.
11. **نسخه‌پذیری:** هر تغییر، نسخه، دلیل، شاهد، وضعیت و مسیر بازگشت دارد. تغییرات ناسازگار ابتدا در Child/نسخهٔ جدید بررسی می‌شوند.
12. **قابل‌انتقال بودن:** معماری به قراردادها، شناسه‌ها و شواهد متکی است، نه به فرض دسترسی دائمی به یک میزبان خاص.

## 5. قرارداد حداقلی هر قابلیت تازه

هر قابلیت یا ماژول جدید باید پیش از ادعای تکمیل این موارد را داشته باشد:
- شناسهٔ پایدار و شناسهٔ تولید، نسخه و وضعیت؛
- هدف و مرز دامنه؛
- قرارداد ورودی/خروجی و رفتار خطا؛
- منشأ و پیوند به والد، رویداد، سند مادر و صف؛
- معیار پذیرش قابل‌مشاهده؛
- آزمون و شاهد واقعی، با تفکیک NOT RUN / PASS / FAIL / INCONCLUSIVE؛
- محدودیت‌های میزبان و مقصد ذخیره‌سازی؛
- دستور بازیابی/ادامه و مسیر برگشت؛
- بازخوانی پس از نوشتن و ثبت نتیجهٔ تطبیق.

## 6. چرخهٔ تکامل معماری

OBSERVE → CAPTURE → CLASSIFY → CHILD HYPOTHESIS → TEST → RAHM REVIEW → ACCEPT / REVISE / REJECT → MASTER VERSION

- مشاهده، دادهٔ خام یا فرضیه به‌تنهایی قانون مادر نمی‌شود.
- تغییر ردشده حذف نمی‌شود؛ دلیل رد و امکان بازنگری حفظ می‌شود.
- تعارض با قاعدهٔ موجود، پیش از ادغام به‌صورت یک مورد باز ثبت می‌شود.
- هر نسخهٔ جدید به نسخهٔ قبلی و علت تغییر پیوند دارد.
- توسعهٔ شاخهٔ GPT-6 نباید تاریخچه یا معماری مادر HAIF را بازنویسی کند؛ تغییر در مادر نیازمند تصمیم مستقل و شواهد است.
