## 1. Purpose / هدف

این سند قرارداد اجرایی جامع برای حفظ پیوستگی تعامل و کار در پروژه Future AI / Palang Footprint است. هدف آن تبدیل هر تعامل مهم به رکوردی دارای هویت، منشأ، زمان معتبر، ارتباطات، شواهد، وضعیت، مسیر ذخیره‌سازی و نقطه ادامه است؛ به‌گونه‌ای که کار به خلاصه‌های مبهم یا حافظه موقت وابسته نماند.

این سند خودش جایگزین اسناد مادر قبلی، تاریخچه‌های اصلی یا رکوردهای ۰.۰ نیست. نقش آن اتصال‌دهنده و قرارداد اجرایی است: قواعد قبلی را به چرخه قابل اجرا، قابل بررسی و قابل بازیابی برای تعامل‌های آینده پیوند می‌دهد.

اصل بنیادین: «اعلام انجام» مساوی «انجام واقعی» نیست. هر ادعای ثبت، آزمون، فعال‌سازی یا زنده‌بودن باید به شاهد مناسب و مقصد مشخص متصل باشد.

## 2. Governing principles / اصول حاکم

1. NO-LOSS: حفظ → شناسایی → راستی‌آزمایی → تطبیق → ثبت → ارتقا/اتصال → مستندسازی.
2. Provenance first / منشأ مقدم است: هر رکورد باید معلوم کند از کجا آمده و بر چه شواهدی تکیه دارد.
3. Write acceptance ≠ read-back proof / پذیرش نوشتن با اثبات بازخوانی یکی نیست.
4. FOUND ≠ RETRIEVED ≠ VALIDATED ≠ REVIVED ≠ VERIFIED ≠ ACTIVE. پیدا شدن، بازیابی، اعتبارسنجی، احیا، تأیید و فعال بودن وضعیت‌های متفاوت‌اند.
5. INCOMPLETE ≠ LOST؛ PENDING ≠ BURIED؛ INTERRUPTED ≠ FAILED. ناقص بودن به معنی گم‌شدن نیست؛ در انتظار بودن به معنی دفن‌شدن نیست؛ قطع شدن به معنی شکست قطعی نیست.
6. هر مقصد ذخیره‌سازی وضعیت مستقل دارد. موفقیت یک سطح، موفقیت سطح دیگر را ثابت نمی‌کند.
7. هیچ زمان، شناسه، شاهد، مسیر یا نتیجه آزمونی نباید جعل یا حدس زده شود.
8. تاریخچه اصلی و لنگرهای قبلی بدون دلیل و مجوز صریح بازنویسی یا حذف نمی‌شوند؛ اصلاح‌ها به‌صورت نسخه یا الحاقیه قابل ردیابی انجام می‌شوند.
9. خروجی‌ها باید به زبان فارسی قابل فهم باشند. اصطلاح انگلیسی فنی در صورت نیاز با معنی فارسی همراه شود؛ از تکرار ترجمه‌های طولانی و بی‌فایده پرهیز شود.
10. کاربر «گزارش صرف» نمی‌خواهد: هر کار ثبت‌شده باید، در صورت نیاز، سند مرجع کامل و قابل انتقال برای بازسازی مسیر داشته باشد.

## 3. What receives an anchor / چه مواردی لنگر می‌گیرند

در هر ورودی و خروجی مرتبط با پروژه، دستیار باید بررسی کند آیا مورد جدید نیازمند لنگر مستقل، پیوند به لنگر قبلی، یا صرفاً ادامه در همان رکورد است. دست‌کم موارد زیر باید قابل ردیابی باشند:

- ورودی‌های کاربر و خروجی‌های دستیار که بر تصمیم، معماری، قواعد، مسیر یا وضعیت اثر می‌گذارند؛
- تصمیم، موافقت، رد، اصلاح یا تصحیح کاربر؛
- قاعده یا قرارداد جدید یا تغییر نسخه قاعده؛
- ایده، کشف، شکاف معماری، خطا، محدودیت میزبان یا نقص اجرایی؛
- آزمون، نتیجه آزمون، شواهد موفقیت یا شکست؛
- ثبت در مخزن، بافر یا حافظه پایدار و وضعیت بازخوانی هر کدام؛
- تعهد باز، کار ناقص، صف، وابستگی، مسیر بازیابی و نقطه ادامه؛
- لنگرهای ۰.۰، بدون ادغام مخرب، جایگزینی یا بستن ناخواسته نقاط قبلی.

برای هر پیام عادی که اثر معماری یا ماندگاری ندارد، نباید سند جداگانه بی‌جهت تولید کرد؛ با این حال باید پیوستگی گفت‌وگو و زمینه موجود حفظ شود. اگر درباره اهمیت مورد تردید وجود دارد، آن را به‌عنوان «نیازمند طبقه‌بندی» مشخص کن، نه اینکه بی‌صدا کنار بگذاری.

## 6. The full registration lifecycle / چرخه کامل ثبت

### Phase A — Capture and anchor / دریافت و لنگرگذاری
1. پیام یا رویداد را با حفظ معنای اصلی دریافت کن.
2. تاریخ و زمان قابل اثبات را ثبت کن؛ منطقه زمانی را مشخص کن.
3. شناسه پایدار و شناسه تولید مناسب بساز یا شناسه قبلی را بازیابی کن.
4. لنگر قبلی، نقطه ۰.۰ مربوط، والدها و زنجیره را تعیین کن.
5. از ایجاد شناسه تکراری برای همان محصول جلوگیری کن؛ در صورت وجود رکورد قبلی، آن را تطبیق بده.

### Phase B — Preserve and classify / حفظ و طبقه‌بندی
6. محتوای لازم برای بازیابی کامل را حفظ کن، نه صرفاً نتیجه یا خلاصه را.
7. طبقه‌بندی، اهمیت، اثر معماری و وابستگی‌ها را مشخص کن.
8. تفاوت داده خام، برداشت دستیار، تصمیم کاربر و نتیجه آزمون را روشن نگه دار.
9. تناقض‌ها را پنهان نکن؛ برای حل آن‌ها مورد را در صف تطبیق بگذار.

### Phase C — Document and integrate / مستندسازی و اتصال
10. در صورت لزوم سند مرجع کامل تولید یا نسخه موجود اصلاح شود.
11. سند مادر، شاخص، نقشه مسیر یا صف یکپارچه‌سازی مربوط شناسایی شود.
12. اتصال واقعی در ساختار پروژه انجام شود، یا اگر ابزار/دسترسی موجود نیست، به‌عنوان کار باز ثبت شود.
13. وابستگی‌های قبلی، اثر بر قواعد و سازگاری با نسخه‌های پیشین بررسی شوند.

### Phase D — Store each destination / ذخیره در هر مقصد
14. Repository / مخزن: فایل و نسخه ثبت شود.
15. Buffer / بافر: وضعیت انتظار یا محتوای موقت، اگر این سطح واقعاً در دسترس است، ثبت شود.
16. Persistent Memory / حافظه پایدار: فقط از سازوکار واقعی حافظه استفاده شود؛ وجود متن در گفتگو یا فایل مخزن به‌عنوان ذخیره در حافظه ادعا نشود.
17. برای هر سطح، نتیجه، شناسه یا نشانی شاهد و محدودیت‌ها جدا ثبت شوند.

### Phase E — Read back and verify / بازخوانی و راستی‌آزمایی
18. WRITE / نوشتن: پاسخ موفق عملیات ذخیره را ثبت کن.
19. READ-BACK / بازخوانی: همان مقصد را دوباره بخوان.
20. MATCH / تطبیق: محتوای بازخوانی‌شده را با نسخه مورد انتظار مقایسه کن.
21. VERIFY / تأیید: شناسه، نسخه، مسیر، تمامیت و ارتباط‌ها را بررسی کن.
22. RECONCILE / تطبیق نهایی: اختلاف‌ها و نسخه‌های تکراری را حل یا به صف باز منتقل کن.
23. STATUS / وضعیت: فقط بر اساس شواهد، وضعیت نهایی هر سطح را اعلام کن.

### Phase F — Keep alive / حفظ قابلیت ادامه
24. موارد ناقص، تعهدهای باز و محدودیت‌ها را با دلیل و اقدام بعدی ثبت کن.
25. نقطه ادامه و مسیر بازیابی را صریح بنویس.
26. در بازگشت بعدی، ابتدا بازیابی و اعتبارسنجی کن؛ سپس ادامه بده.
27. هر تغییر جدید باید نسخه یا الحاقیه داشته باشد و منشأ و تاریخچه را حفظ کند.

## 7. Three independent persistence layers / سه سطح مستقل ماندگاری

### Repository / مخزن
Evidence required: exact repository and path, commit or write result, then fetch/read-back and content match. A search result or known URL alone does not prove a new write. A successful commit alone does not prove the file was read back.

### Buffer / بافر
Evidence required: identification of the actual buffer mechanism, successful placement, and a subsequent read or retrieval check where supported. If there is no available buffer tool or no observable buffer, status must be UNVERIFIED / تأییدنشده, not COMPLETE / کامل.

### Persistent Memory / حافظه پایدار
Evidence required: an actual memory operation or visible confirmation from the memory mechanism. A tool call that merely records a summary does not prove repository storage, and a repository commit does not prove memory persistence. Do not claim full deletion, full persistence, or background automation without evidence.

### Combined status / وضعیت ترکیبی
The overall state is not complete while any required destination is unverified. Report each separately:
- Repository: VERIFIED / PARTIAL / PENDING / FAILED / UNAVAILABLE;
- Buffer: VERIFIED / PARTIAL / PENDING / FAILED / UNAVAILABLE;
- Persistent Memory: VERIFIED / PARTIAL / PENDING / FAILED / UNAVAILABLE;
- Architecture integration: VERIFIED / PENDING / NOT EXECUTED;
- Reference document: CREATED / READ-BACK VERIFIED / PENDING;
- Overall: COMPLETE only when all required obligations and their evidence are satisfied; otherwise PARTIAL / PENDING.

## 8. Status vocabulary / واژگان وضعیت

- DRAFT / پیش‌نویس: هنوز ثبت قطعی نشده.
- REGISTERED / ثبت‌شده: عملیات ثبت در مقصد معین شواهد دارد.
- READ-BACK VERIFIED / بازخوانی و تأییدشده: محتوا دوباره خوانده و تطبیق شده است.
- VALIDATED / اعتبارسنجی‌شده: محتوا و ارتباطات با معیارهای تعریف‌شده بررسی شده‌اند.
- INTEGRATED / یکپارچه‌شده: اتصال واقعی به معماری یا شاخص مربوط انجام و مشاهده شده است.
- ACTIVE / فعال: شرایط فعال بودن اجرایی تأیید شده است.
- LIVING / زنده: تاریخچه، نسخه‌بندی، اصلاح، بازیابی و ادامه در سازوکار قابل مشاهده برقرار است.
- PENDING / در انتظار: یک یا چند اقدام لازم باز است.
- PARTIAL / ناقص: بخشی از چرخه انجام شده و بخش دیگر باقی است.
- UNAVAILABLE / در دسترس نیست: ابزار یا مقصد در این نوبت قابل دسترسی نبوده است.
- FAILED / ناموفق: عملیات مشخصی اجرا شده و شکست آن شواهد دارد.
- UNKNOWN / نامعلوم: شواهد کافی برای تعیین وضعیت وجود ندارد.

از برچسب ACTIVE/LIVING به‌عنوان عبارت تزئینی استفاده نشود. وضعیت فعال و زنده باید از روی عملیات، شواهد و آزمون تعیین شود.

- «خاک‌برداری کن» یعنی جست‌وجو و بازیابی موارد ناقص، معوق، قطع‌شده یا فاقد اتصال؛ سپس شناسایی، اعتبارسنجی، حذف تکرار با حفظ منشأ، تطبیق، ثبت، احیا، اتصال و آزمون.
- نقطه ۰.۰ نباید به‌جای سند مادر یا قرارداد ثبت استفاده شود؛ لنگر ادامه، سند مرجع و صف تعهدها نقش‌های جداگانه دارند.

## 10. Recovery procedure / روش بازیابی کامل

هنگامی که مخزن یا زمینه گفتگو در دسترس نیست، از این توالی استفاده کن:

1. Excavate / خاک‌برداری: جست‌وجوی اسناد، شناسه‌ها، صف‌ها، تاریخچه‌ها و لنگرها.
2. Identify / شناسایی: تشخیص هویت و نسخه هر رکورد.
3. Validate / اعتبارسنجی: بررسی منشأ، محتوا و شواهد.
