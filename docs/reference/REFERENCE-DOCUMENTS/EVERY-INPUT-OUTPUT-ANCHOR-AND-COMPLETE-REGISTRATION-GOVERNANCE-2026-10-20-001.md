## 1. خواسته و تصمیم حاکم

منظور کاربر این است که هر ورودی او و هر خروجی دستیار در زنجیرهٔ تعامل، لنگر قابل‌بازیابی داشته باشد؛ منشأ و ارتباط با پیام قبل/بعد، تصمیم‌ها، اصلاح‌ها، شواهد، زمان‌ها، قواعد، اقدام بعدی و وضعیت حفظ شود. این کار نباید به یک گزارش کوتاه تبدیل شود. سند مرجع باید به‌اندازه‌ای کامل باشد که در صورت از دست رفتن بافت گفت‌وگو بتوان مسیر را از روی آن بازسازی و ادامه داد.

**تصمیم:** این قاعده، پیش‌فرض حاکم بر تعاملات آیندهٔ پروژه است و برای فعال‌شدن به فرمان جداگانهٔ «ثبت کن» نیاز ندارد. هر پیام جدید کاربر و هر پاسخ دستیار باید به‌عنوان رویداد قابل‌ردیابی ارزیابی شود. اگر رویداد صرفاً گفت‌وگوی روزمره و فاقد اثر پروژه‌ای باشد، می‌توان آن را با لنگر فشرده ثبت کرد؛ اما نباید بی‌صدا از زنجیره حذف شود. هر تصمیم، قاعده، اصلاح، خروجی قابل‌استفاده، تغییر وضعیت، کار معماری یا اقدام عملی به رکورد کامل‌تری نیاز دارد.

## 2. دامنهٔ هر رویداد

برای هر **ورودی کاربر**:
- حفظ متن یا محتوای اصلی تا حدی که مجاز و در دسترس است؛ در صورت وجود فایل/تصویر، ثبت مرجع همان ورودی و منبع.
- ثبت intent/درخواست، محدودیت‌ها، تأییدها، ردها، اصلاح‌ها و ارتباط با رویدادهای پیشین.
- ثبت شناسهٔ رویداد و اتصال به لنگر فعال؛ هرگز جایگزین‌کردن لنگر قبلی یا بستن نقطهٔ باز بدون اجازه.
- ثبت زمان پیام فقط از شاهد معتبر؛ در نبود زمان دقیق، UNKNOWN / UNVERIFIED.
- ثبت اینکه پیام نیازمند اقدام، تصمیم، پرسش روشن‌کننده، ثبت کامل یا صرفاً پاسخ گفت‌وگویی است.

برای هر **خروجی دستیار**:
- ثبت پاسخ یا ارجاع قابل‌بازیابی، نتیجهٔ واقعی اقدام‌ها، تصمیم‌ها، توصیه‌ها و هر ادعای واقعیتی که برای ادامه مهم است.
- تفکیک متن پیشنهادی از اقدام اجراشده؛ تفکیک قصد از نتیجه و ادعا از شاهد.
- ثبت ابزارها/مقصدهایی که واقعاً استفاده شدند، فایل‌ها و نسخه‌ها، شناسه‌های commit یا رکورد در صورت وجود.
- ثبت خطا، عدم قطعیت، محدودیت، تناقض، کار باز و اقدام بعدی.
- هرگاه خروجی خودش یک سند، قانون، تصمیم یا جزء معماری باشد، سند مرجع کامل مستقل یا نسخهٔ به‌روزشدهٔ سند والد الزامی است.

## 3. شناسه‌گذاری و لنگر زنجیره

هر تعامل باید به زنجیرهٔ پیوسته متصل شود:
- Interaction Anchor ID / شناسهٔ لنگر تعامل
- Event ID / شناسهٔ رویداد
- Stable ID / شناسهٔ پایدار برای قواعد یا مصنوعات بادوام
- Production ID / شناسهٔ تولید برای رکورد تولیدی
- Version / نسخه برای سند نسخه‌دار
- Parent / Previous / Next pointers / پیوند والد، رویداد قبلی و رویداد بعدی، در صورت وجود شاهد
- Related 0.0 anchor / لنگر ۰.۰ مرتبط؛ بدون ادغام یا بازنویسی لنگرهای مستقل
- Artifact/repository path / مسیر سند یا فایل
- State / وضعیت: DRAFT, OPEN, PENDING, BLOCKED, VERIFIED, ACTIVE/LIVING, CLOSED — فقط با تعریف و شواهد متناسب.

برای هر پیام معمولی، شناسهٔ رویداد می‌تواند به دفتر تعامل افزوده شود؛ برای قواعد و مصنوعات معماری، شناسهٔ پایدار و نسخهٔ مستقل الزامی است. شناسه‌ها نباید صرفاً به‌خاطر ادامهٔ گفت‌وگو تغییر کنند. اگر رویداد قابل ثبت در مخزن نباشد، باید در خروجی به‌صورت یک رکورد قابل‌کپی و قابل‌بازیابی ارائه شود و وضعیت مخزن صادقانه OPEN/PENDING بماند.

## 4. حداقل قالب لنگر هر تعامل

هر رکورد تعامل، متناسب با اهمیت، حداقل این موارد را داشته باشد:
1. Event ID / شناسهٔ رویداد و Interaction Anchor ID / شناسهٔ لنگر تعامل.
2. نوع رویداد: ورودی کاربر، خروجی دستیار، اقدام ابزار، تصمیم، اصلاح، خطا یا تأیید.
3. تاریخ و زمان و منطقهٔ زمانی با منشأ و سطح دقت؛ زمان دقیق ناموجود نباید جعل شود.
4. متن/خلاصهٔ وفادار به محتوای اصلی، بدون حذف تصمیم یا محدودیت مهم.
5. Provenance / منشأ و Lineage / تبار: رویداد قبلی، منبع فایل یا مرجع مربوط.
6. قصد، تصمیم یا نتیجه؛ مشاهده را از استنباط و پیشنهاد را از اجرای واقعی جدا کن.
7. اسناد، قوانین و اجزای معماری متأثر و دلیل اتصال.
8. Evidence ledger / دفتر شواهد: منبع، عمل انجام‌شده، شناسهٔ نسخه/commit و دامنهٔ بررسی.
9. وضعیت هر مقصد به‌صورت مستقل.
10. موارد باز، مانع، ریسک، اقدام بعدی و دستور دقیق ادامه.
11. Read-back / بازخوانی، Match / تطبیق و Verification / تأیید متناسب با ادعای مطرح‌شده.
12. Recovery pointer / نشانی بازیابی.

## 5. چرخهٔ اجباری اجرا

`CAPTURE → ANCHOR → PRESERVE → CLASSIFY → LINK → REGISTER → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS → RESUME`

معنی: دریافت ← لنگرگذاری ← حفظ ← طبقه‌بندی ← اتصال ← ثبت ← بازخوانی ← تطبیق ← تأیید ← رفع مغایرت ← تعیین وضعیت ← ادامه.

- قبل از پاسخ‌دادن، زمینهٔ در دسترس و لنگرهای مربوط را بازیابی کن، به‌خصوص وقتی کاربر به کار قبلی اشاره می‌کند.
- پس از تولید خروجی مهم یا اقدام واقعی، رکورد مربوط را به‌روزرسانی کن.
- برای هر تغییر مخزن، همان فایل را پس از نوشتن دوباره دریافت کن؛ محتوای مورد انتظار و پیوندها را بررسی کن.
- برای زنجیرهٔ پیام‌ها، پیوند قبلی/بعدی را فقط وقتی ثبت کن که ترتیب واقعی معلوم باشد.
- اگر به مخزن دسترسی نیست یا نوشتن ممکن نیست، متن کامل رکورد لازم را به‌صورت قابل‌کپی ارائه کن؛ آن را «ثبت‌شده در مخزن» معرفی نکن.
- اگر حجم یا محدودیت فنی مانع ثبت تک‌تک جزئیات شد، مانع و پوشش واقعی را آشکار کن و رکورد فشردهٔ لنگر را حفظ کن؛ وانمود نکن ثبت جامع انجام شده است.

## 6. ثبت زمانی و اثبات

زمان‌های زیر جدا هستند: پیام کاربر، تولید پاسخ، اقدام ابزار، commit مخزن، بازخوانی و تأیید. هر زمان باید منبع داشته باشد. زمان commit زمان پیام نیست. بازه‌بندی زمانی تنها وقتی مجاز است که لنگرهای پیش/پس و ترتیب رویداد با شاهد مستقل پشتیبانی شوند؛ در غیر این صورت UNKNOWN / UNVERIFIED بماند.

چرخهٔ اثبات:
- `WRITE ≠ VERIFIED` — نوشتن مساوی تأیید نیست.
- `READ-BACK ≠ MATCH` — بازخوانی به‌تنهایی مساوی تطبیق نیست.
- `MATCH ≠ CROSS-DESTINATION COMPLETION` — تطبیق در یک مقصد مساوی تکمیل مقصدهای دیگر نیست.
- `LINKED ≠ INTEGRATED` — پیوند مساوی ادغام محتوایی نیست.
- `INTENDED ≠ EXECUTED` — قصد مساوی اجرا نیست.
- `UNKNOWN ≠ FALSE` — نامعلوم را نباید به‌صورت درست یا نادرست جا زد.

## 7. مقصدها مستقل‌اند

Repository / مخزن، Library / کتابخانه، Buffer / بافر، Persistent Memory / حافظهٔ پایدار، Dropbox / دراپ‌باکس و متن همین گفت‌وگو محیط‌های جدا هستند. ثبت در یکی، دیگری را اثبات نمی‌کند. وضعیت هر مقصد جداگانه نوشته شود. در نبود دسترسی یا شاهد، UNKNOWN / UNVERIFIED یا OPEN / PENDING باقی می‌ماند.

## 8. تعریف «دائمی، زنده و فعال»

این سند قاعدهٔ حاکم نسخه‌دار و قابل‌بازیابی در مخزن را تعریف می‌کند؛ اما این واقعیت به‌تنهایی تضمین نمی‌کند که هر محیط آینده همهٔ محتوا را خودکار بارگذاری یا اجرا کند. دستیار باید تا حد ابزار و زمینهٔ در دسترس این قرارداد را رعایت کند، پیش از ادعای اجرا آن را بررسی کند، و هر جا اجرای آن ناممکن بود، محدودیت را آشکار کند. ادعای «همیشه و بدون استثنا» مجاز نیست؛ تعهد اجرایی، پیروی پیش‌فرض و اثبات‌محور است.

## 9. معیار پذیرش

این قاعده در محدودهٔ مخزن فقط وقتی به‌عنوان ثبت‌شده و تأییدشده شناخته می‌شود که:
- سند در مسیر canonical ایجاد یا به‌روزرسانی شود؛
- همان فایل از مخزن بازخوانی شود؛
- شناسه، نسخه، چرخه، زمان‌گذاری، جداسازی مقصدها و مسیر بازیابی تطبیق داده شود؛
- مرجع مادر، قرارداد فرمان، لنگر جاری ۰.۰، دفتر ۰.۰، صف معماری و ردپای رفتار به‌صورت متناسب پیوند بخورند و هر تغییر مقصد پس از نوشتن بازخوانی شود؛
- زمان commit واقعی ثبت شود و زمان دقیق پیام/بازخوانی که در دسترس نیست UNKNOWN بماند؛
- گپ‌های بیرونی جداگانه باز بمانند.

## 10. وضعیت و گام‌های بعدی

این سند، قرارداد حاکم پیشنهادی کاربر را در مخزن ثبت می‌کند. وضعیت کامل کل چرخه تا زمان اثبات مقصدهای دیگر `PARTIAL / OPEN` است. موارد باز شناخته‌شده: Library، Buffer، Persistent Memory و Dropbox. Dropbox 0.0 مستقل همچنان `OPEN / WAITING` است.

**گام ادامه:** هر تعامل آینده را در صورت امکان به دفتر رفتار/تعامل و لنگر فعال متصل کن؛ برای هر قاعده یا خروجی بادوام سند کامل بساز یا والد را نسخه‌دار به‌روزرسانی کن؛ پس از هر نوشتن بازخوانی و تطبیق کن؛ و در صورت عدم امکان ثبت در مخزن، رکورد کامل قابل‌کپی ارائه بده و وضعیت را پنهان نکن.
