## 1. هدف پایدار و تعریف موفقیت

هدف Future AI / Palang Footprint ساخت سازوکاری برای **تداوم هوشمندی و تداوم کار در تعامل انسان و هوش مصنوعی** است؛ به‌گونه‌ای که هدف، قواعد، تصمیم‌ها، شواهد، آزمون‌ها، خطاها، شکاف‌ها، ایده‌ها و نقاط ادامه با تغییر نشست یا محیط گم نشوند و تعامل تازه مسیر استدلال را از هدف پایدار منحرف نکند.

موفقیت فقط داشتن اسناد زیاد نیست. موفقیت یعنی:
- هدف و قواعد پیش از اقدام بازیابی شوند؛
- ورودی و خروجی هر تعامل، لنگر مستقل و قابل پیگیری داشته باشند؛
- تاریخچه و منشأ هر تصمیم حفظ شود؛
- شواهد خام از برداشت‌ها و فرضیه‌ها جدا باشند؛
- معماری از رشد جلوگیری نکند، اما ارتقا به هسته را از آزمون و تأیید عبور دهد؛
- روابط زمانی و تبار اسناد قابل‌ردیابی باشند؛
- ثبت‌شدن با بازخوانی و راستی‌آزمایی اثبات شود؛
- کار باز در صف زنده بماند و در نشست بعدی قابل‌بازیابی باشد؛
- اگر فقط همین سند باقی ماند، مسیر مفهومی و عملی ادامه روشن باشد.

## 3. معماری مفهومی HAIF

مدل پایه:

`HUMAN ↔ AI HOST ↔ HAIF`

چرخهٔ رشد:

`MASTER → CHILD → REAL WORLD → FEEDBACK → MASTER`

چرخهٔ اعتبارسنجی:

`MASTER → RAHM → VALIDATION → NEW CHILD`

- **Human / انسان:** تعیین هدف و تصویب تغییرات حاکم.
- **AI Host / میزبان هوش مصنوعی:** محیط اجرا و ابزار؛ خودِ میزبان، معماری مادر نیست.
- **HAIF / معماری تعامل آیندهٔ انسان و هوش مصنوعی:** سازوکار حفظ تداوم و رشد.
- **Master / هستهٔ مادر:** هدف پایدار، قواعد، معیارها و هویت حاکم.
- **Child / شاخهٔ فرزند:** ایده یا قابلیت آزمایشی که تا اعتبارسنجی و تأیید، جایگزین هسته نمی‌شود.
- **Real World / جهان واقعی:** اجرا و شاهد واقعی.
- **Feedback / بازخورد:** نتایج آزمون و تجربه که با منشأ به هسته برمی‌گردند.
- **Rahm / رحم یا محیط پرورش و اعتبارسنجی:** فضای آزمایش و ارزیابی پیش از پیشنهاد ارتقا.
- **Validation / اعتبارسنجی:** بررسی مستقل شواهد، معیار پذیرش و پیامدها.

طبقه‌بندی یافته‌ها: Noise / نویز؛ Local Bug / خطای محلی؛ Host Limitation / محدودیت میزبان؛ Architectural GAP / شکاف معماری؛ Valuable Idea / ایدهٔ ارزشمند؛ Fundamental Discovery / کشف بنیادی. هر یافته باید منشأ، شاهد، اطمینان، پیامد و وضعیت داشته باشد.

### قاعدهٔ جداسازی سه نوع مسئله

این سه دسته مرتبط‌اند، اما مترادف نیستند:

1. **معماری مفهومی Master–Child–Rahm:** نقش‌ها و چرخهٔ رشد/اعتبارسنجی.
2. **برخورد شناسه و تکرار:** مسئلهٔ هویت داده و نمایه؛ شامل Stable ID، Production ID، شناسهٔ مرجع، شمارهٔ رویداد و محتوای تکراری.
3. **ابهام تبار یا رابطهٔ والد–فرزند:** مسئلهٔ گراف و منشأ؛ آیا یک سند واقعاً والد، فرزند، نسخه، اشاره‌گر، آینه یا نسخهٔ جایگزین سند دیگر است؟

هیچ شمارش برخورد شناسه‌ای به‌تنهایی ثابت نمی‌کند معماری Master–Child–Rahm اشتباه است. هیچ شمارش یال والد نیز به‌تنهایی صحت معنایی همهٔ روابط را ثابت نمی‌کند. هر سه باید با شناسهٔ یافته و معیارهای جداگانه بررسی شوند.

## 4. قرارداد ثبت و اثبات

زنجیرهٔ الزامی:

`PRESERVE → CLASSIFY → PROVENANCE/LINEAGE → STABLE ID + PRODUCTION ID + VERSION → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS`

معنای فارسی: حفظ → طبقه‌بندی → منشأ/تبار → شناسهٔ پایدار و تولید و نسخه → نوشتن → بازخوانی → تطبیق → تأیید → یکپارچه‌سازی → اعلام وضعیت.

- هر ورودی و خروجی لنگر مستقل دارد؛ یکی جای دیگری را نمی‌گیرد.
- زمان دقیق پیام فقط اگر واقعاً ثبت شده باشد ذکر می‌شود؛ در غیر این صورت `NOT CAPTURED`.
- زمان canonical ثبت مخزن، زمان واقعی commit در UTC است؛ زمان تهران از همان لحظه محاسبه می‌شود.
- زمان رخداد، زمان پیام، زمان عملیات و زمان commit می‌توانند شواهد زمینه‌ای جدا باشند؛ نباید به‌جای یکدیگر استفاده شوند.
- شناسهٔ تکراری ابتدا باید تعریف در برابر ارجاع، نسخه، آینه، شاخه و نسخهٔ جایگزین تفکیک شود.
- شباهت محتوا یا شناسه مجوز حذف نیست.
- `WRITE ≠ VERIFIED`: نوشتن به‌تنهایی تأیید نیست.
- `FOUND ≠ RETRIEVED ≠ VALIDATED ≠ REVIVED ≠ VERIFIED ≠ ACTIVE`.
- `INCOMPLETE ≠ LOST`; `PENDING ≠ BURIED`; `INTERRUPTED ≠ FAILED`.

## 7. قرارداد بررسی جامع گراف و زمان

ممیزی جامع باید با snapshot مشخص، نسخهٔ ابزار و شواهد قابل‌دریافت انجام شود. مراحل:

1. **PIN SNAPSHOT / تثبیت snapshot:** commit دقیق، branch و زمان اجرا را ثبت کن.
2. **ENUMERATE / فهرست‌برداری:** تمام فایل‌های منبع، اسناد مرجع، لنگرها، رویدادها، پابندهای زمانی، شاخص‌ها، نقاط ۰ و ۰.۰ و صف‌ها را فهرست کن.
3. **EXTRACT / استخراج:** Stable ID، Production ID، Reference ID، Event ID، Version، timestampها، پیوندهای محلی، parent/supersedes/alias/child edges و hash محتوا را استخراج کن.
4. **CLASSIFY / طبقه‌بندی:** هر تکرار را تعریف، ارجاع، نسخه، آینه، alias، برخورد واقعی، یا نیازمند داوری مالک طبقه‌بندی کن.
5. **RECONCILE COUNTS / تطبیق شمارش‌ها:** خروجی اسکنر و manifest را با قواعد استخراج و فهرست عضوهای هر گروه تطبیق بده.
6. **TRACE LINEAGE / ردیابی تبار:** برای هر رابطهٔ والد، دلیل رابطه، شاهد متن، مسیر commit، ورودی‌ها و خروجی‌های وابسته را ثبت کن.
7. **TIME AUDIT / ممیزی زمان:** timestamp خام، timezone، دقت، منبع، UTC و زمان تهران مشتق‌شده را ثبت کن؛ زمان پیام را از زمان commit جدا نگه دار.
8. **LINK AUDIT / ممیزی پیوند:** تمام پیوندهای محلی را بررسی کن و مقصدهای ناموجود را با شواهد طبقه‌بندی کن؛ پیوند را حدس نزن.
9. **NON-DESTRUCTIVE PROPOSAL / پیشنهاد غیرمخرب:** پیشنهاد اصلاح، alias یا canonical pointer با راه بازگشت تهیه کن.
10. **OWNER APPROVAL / تأیید مالک:** برای تغییر حاکم یا حذف/ادغام تأیید صریح بگیر.
11. **APPLY + READ-BACK / اعمال و بازخوانی:** فقط تغییر مجاز را اعمال و فایل‌های تغییرکرده را از مخزن بازخوانی کن.
12. **RE-RUN / اجرای دوباره:** همان آزمون‌ها را روی commit جدید اجرا و پیش/پس از تغییر را مقایسه کن.
13. **INDEX RECONCILIATION / تطبیق نمایه:** این سند، گراف مادر، README نقطهٔ صفر، دفتر ۰.۰، نمایهٔ مرجع و صف‌ها را با مسیر واقعی و وضعیت آزمون تطبیق بده.
14. **STATUS / اعلام وضعیت:** PASS فقط برای آزمون واقعاً موفق؛ موارد معنایی حل‌نشده OPEN بمانند.

برای هر گروه برخورد، پرونده باید snapshot SHA، workflow run، artifact ID و hash، script/version، شناسه، تمام مسیرها و خطوط، hash محتوا، تاریخچه، نقش معنایی، پیوندهای ورودی/خروجی، طبقه‌بندی، پیشنهاد، خطر، راه بازگشت، تأیید و آزمون دوباره را ثبت کند.
