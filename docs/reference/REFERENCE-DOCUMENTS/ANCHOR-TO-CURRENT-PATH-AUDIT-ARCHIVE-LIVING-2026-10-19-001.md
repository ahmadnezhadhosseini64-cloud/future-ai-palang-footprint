- چه مواردی دنبال نشده یا از پیگیری افتاده‌اند؛

در این نوبت، کاربر خواست موارد تکمیل‌نشده نیز تا حد امکان تکمیل شوند و سند مرجع کامل برای آرشیو ساخته، در مخزن ثبت و زنده نگه داشته شود.

## 3. قواعد معماری لازم‌الاجرا

1. **PRESERVE → IDENTIFY → CLASSIFY → ANCHOR → DOCUMENT → LINK → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS** — حفظ، شناسایی، دسته‌بندی، لنگرگذاری، مستندسازی، پیوند، نوشتن، بازخوانی، تطبیق، تأیید، سازگار‌سازی و اعلام وضعیت.
2. **WRITE ≠ READ-BACK ≠ MATCH ≠ VERIFIED** — این چهار وضعیت جدا هستند.
3. **INCOMPLETE ≠ LOST; PENDING ≠ BURIED; INTERRUPTED ≠ FAILED** — مورد ناقص یا معطل حفظ می‌شود و از دفتر حذف نمی‌شود.
4. زمان پیام، مشاهده، اقدام، commit، بازخوانی، تطبیق و تأیید، فیلدهای جدا هستند.
5. زمان commit فقط زمان commit است؛ جای زمان پیام یا بازخوانی را نمی‌گیرد.
6. فقط کاربر می‌تواند یک نقطهٔ تازه را ۰.۰ تعیین کند. هر خروجی مهم می‌تواند لنگر/رویداد داشته باشد، اما به‌طور خودکار ۰.۰ نمی‌شود.
7. سه نقطهٔ شناخته‌شده مستقل می‌مانند؛ پیوند دادن به معنی ادغام، بستن یا تکمیل آن‌ها نیست.
8. مخزن، بافر، کتابخانه، حافظهٔ پایدار و Dropbox مقصدهای جدا هستند و برای هرکدام شاهد مستقل لازم است.
9. اگر اقدامی به دسترسی کاربر یا مجوز اتصال نیاز داشته باشد، آن وابستگی باید روشن ثبت شود؛ دستیار نباید وانمود کند آن اقدام را انجام داده است.
10. سند مرجع باید کامل و قابل‌بازیابی باشد؛ گزارش به‌تنهایی کافی نیست.
