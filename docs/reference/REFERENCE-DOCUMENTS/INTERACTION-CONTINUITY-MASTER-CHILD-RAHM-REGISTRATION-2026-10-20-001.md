## 1. هدف نهایی پروژه — آنچه داریم می‌سازیم

Future AI / Palang Footprint صرفاً مجموعه‌ای از فایل‌ها یا یادداشت‌های گفتگو نیست؛ هدف، معماری مستقل و قابل‌بازیابی برای تداوم تعامل و کار انسان–هوش مصنوعی است. معماری باید بتواند تاریخچه، قواعد، تصمیم‌ها، شواهد، وابستگی‌ها، نسخه‌ها، خطاها و کارهای باز را حفظ کند تا در هر زمان بتوان یک بسته بازسازی جامع از مسیر طی‌شده و وضعیت فعلی تولید کرد و آن را در میزبان دیگری ادامه داد.

الگوی بنیادین:
`HUMAN ↔ AI HOST ↔ HAIF`

چرخه‌های معماری:
- `MASTER → CHILD → REAL WORLD → FEEDBACK → MASTER`
- `MASTER → RAHM → VALIDATION → NEW CHILD`

تعریف نقش‌ها:
- **Master (مستر ـ هسته حاکم):** هویت معماری، قواعد، نسخه‌های تأییدشده، روابط و تصمیم‌های معتبر را نگه می‌دارد.
- **Child (فرزند ـ شاخه آزمایشی):** شاخه‌ای قابل‌انتقال/آزمایشی است که در یک میزبان یا محیط جدید کار می‌کند، رفتار میزبان را مشاهده می‌کند و یافته‌ها و شکاف‌ها را با منشأ و شاهد ثبت می‌کند.
- **Rahm (رحم ـ محیط اعتبارسنجی):** یافته‌های Child را بررسی می‌کند؛ تنها یافته‌های دارای معیار پذیرش و شواهد کافی برای ارتقا به Master پیشنهاد می‌شوند.
- **AI Host (میزبان هوش مصنوعی):** محیط اجرا و منبع اطلاعات/قابلیت‌هاست؛ نباید با خود هویت HAIF یا حافظه/قواعد مستقل آن یکی فرض شود.
- **Feedback (بازخورد):** نتیجه آزمایش و تجربه واقعی است که پس از اعتبارسنجی می‌تواند مسیر Master و Child بعدی را تغییر دهد.

## 2. قرارداد ثبت هر تعامل

هر ورودی کاربر و هر خروجی دستیار باید از نظر اثر معماری ارزیابی شود و به زنجیره تعامل وصل بماند. ثبت کامل برای تصمیم، قاعده، کشف، اصلاح، خطا، آزمون، تصمیم ردشده یا خروجی بادوام الزامی است. برای پیام عادی می‌توان از رکورد فشرده استفاده کرد، اما باید لنگر، منشأ، زمانِ قابل‌اثبات، رابطه با رویداد قبلی و اشاره‌گر بازیابی را نگه دارد؛ برای رویداد معماری، این سند کامل یا سند هم‌ارز لازم است.

چرخه اجباری:
`PRESERVE → CLASSIFY → PROVENANCE/LINEAGE → ID/VERSION → REGISTER → WRITE → READ-BACK → MATCH → VERIFY → RECONCILE → STATUS`

معنی: حفظ → دسته‌بندی → منشأ و زنجیره → شناسه و نسخه → ثبت → نوشتن → بازخوانی → تطبیق → تأیید → رفع تعارض/اتصال → اعلام وضعیت.

حداقل فیلدها:
1. Stable ID / شناسه پایدار و Production ID / شناسه تولید.
2. Version / نسخه و lineage / زنجیره نسخه‌ها.
3. تاریخ و منطقه زمانی؛ زمان دقیق فقط با شاهد معتبر، وگرنه UNKNOWN / UNVERIFIED.
4. منشأ، لنگر قبلی، ورودی کاربر، خروجی دستیار و دلیل اهمیت.
5. آنچه واقعاً بررسی یا اجرا شد، شواهد و محدودیت‌ها.
6. تغییر معماری، گزینه‌های واقعاً بررسی‌شده، اثر و وابستگی‌ها.
7. آزمون پذیرش و نتیجه آن؛ نبود آزمون باید صریح باشد.
8. مقصد و وضعیت مستقل هر لایه.
9. شکاف باز، آخرین مرحله موفق، مانع، اقدام بعدی و Resume Pointer / مسیر ادامه.
10. مسیر مخزن و مرجع بازیابی.

**زمان‌گذاری:** زمان پیام، زمان اقدام، زمان commit، زمان بازخوانی و زمان تأیید پنج رویداد متفاوت‌اند. زمان commit نباید به‌جای زمان پیام ثبت شود. اگر زمان دقیق در شواهد ابزار موجود نیست، آن را جعل یا از ساعت تقریبی استنتاج نکن.

## 3. معماری مستندسازی قابل‌بازیابی

برای جلوگیری از تکرار بی‌رویه کل معماری در هر پیام، سه لایه به هم پیوند می‌خورند:
- **Master Snapshot (تصویر مرجع مستر):** آخرین معماری تأییدشده و نسخه آن.
- **Interaction Delta (تغییرِ ناشی از تعامل):** چه چیزی در این تعامل کشف، تأیید، رد یا تغییر کرد و چرا.
- **Reconstruction Package (بسته بازسازی):** سند مرجع مادر + snapshot + تغییرات + شواهد + صف باز + لنگر ادامه.

این سه لایه باید طوری پیوند بخورند که فرمان «تا اینجا هرچی از معماری رو داریم» بتواند بسته‌ای جامع، نسخه‌دار و قابل انتقال بسازد؛ نه اینکه تنها خلاصه‌ای از گفتگو تحویل دهد. اگر فایل مرجع مادر در دسترس نیست یا متن مستقل آن بازیابی نشده، این نقص باید ثبت شود و نباید ادعا شود که بازسازی کامل قبلاً آزمایش شده است.

## 9. معیار نهایی پذیرش و ضدادعای موفقیت

`WRITE ACCEPTED ≠ READ-BACK PROOF`
`DOCUMENTED ≠ IMPLEMENTED`
`IMPLEMENTED ≠ ACCEPTED`
`LINKED ≠ SEMANTICALLY INTEGRATED`
`UNKNOWN ≠ SUCCESS`
