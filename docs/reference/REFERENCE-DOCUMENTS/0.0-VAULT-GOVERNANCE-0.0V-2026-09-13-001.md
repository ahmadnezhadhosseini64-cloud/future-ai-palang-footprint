## Purpose
The 0.0 Vault is the dedicated persistent registry for every 0.0 point created in the project. A 0.0 is a recoverable continuation anchor, not a disposable checkpoint.

## Core Rule
Every 0.0 remains preserved after creation. A later 0.0 never deletes, overwrites, buries, or invalidates an earlier 0.0.

## Architectural Model
The Vault is not a simple linear chain. It is a persistent 0.0 registry plus lineage/relationship graph and continuation-recovery index.

Possible structures include:
- linear continuation;
- branching paths;
- independent paths;
- later-confirmed connections;
- unresolved/unknown relationships.

A relationship between two 0.0 points must never be inferred merely from chronology. Relationship states include:
- CONFIRMED CONNECTION
- POSSIBLE CONNECTION
- INDEPENDENT
- UNKNOWN

## 0.0 Identity
Each 0.0 receives an independent stable identity. Its original snapshot is preserved. Later understanding, reconciliation, or continuation does not rewrite history.

## Required Record Fields
Each 0.0 record should preserve, as applicable:
- 0.0 Stable ID
- creation date
- exact creation time
- timezone
- owner
- location/context (including Gonbad-e Kavus when applicable)
- origin/source
- creation context
- what was reached
- unresolved remainder
- current status
- unresolved reason
- parent/related 0.0 references
- path/track identifier
- last known state
- last continuation point
- evidence/references
- next possible continuation
- last update / last continuation timestamps
- lineage and relationship state

## Status Separation
The following distinctions are mandatory where applicable:
- OPEN != ERROR
- UNRESOLVED != LOST
- PAUSED != ABANDONED
- CONTINUATION NOT COMPLETED != FINISHED
- RESOLVED != DELETED
- UNKNOWN RELATIONSHIP != CONFIRMED RELATIONSHIP

## Lineage Operations
The architecture supports Split and Merge without deleting historical identity:
- SPLIT: one path may later be recognized as multiple distinct paths.
- MERGE: previously separate paths may later be shown to converge.

All prior records remain preserved; reconciliation records the newly established relationship.

## Retrieval / Continuation Queries
The Vault must support later retrieval of:
- all open 0.0 points;
- unresolved 0.0 points;
- 0.0 points whose continuation was never completed;
- paused/waiting points;
- points with unknown relationships;
- branches from a given 0.0;
- connected lineage paths;
- long-standing unresolved points;
- 0.0 points that were reached but never continued.

## Master Reference Boundary
The 0.0 Vault does not replace the existing Current 0.0 Master Reference. The Master Reference remains a master anchor/reference layer; the Vault preserves the complete set of 0.0 points, lineage, statuses, and continuation/recovery relationships.

## Immutability / Provenance
The original 0.0 snapshot is immutable in meaning. Later information is appended as reconciliation, continuation, or update evidence rather than silently rewriting what was known at creation time.

## Safety Against Future Misclassification
No system behavior may:
1. collapse multiple 0.0 points into one without explicit reconciliation;
2. assume chronological adjacency means lineage;
3. treat paused work as finished;
4. treat unresolved work as lost;
5. delete a 0.0 because it was resolved;
6. erase the last known continuation point;
7. replace an earlier 0.0 with a newer one.

## Integration
The 0.0 Vault belongs to the project's governance, architecture, recovery, production registry, and persistent-memory/retrieval layers. It is a dedicated storage/continuation layer, not a replacement for those layers.

## Operational Principle
When a user asks for open/unresolved/unfinished 0.0 points, the system should retrieve the Vault state before guessing or asking the user to reconstruct the history manually.
