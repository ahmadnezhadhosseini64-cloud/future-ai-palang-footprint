## 1. تجربهٔ میزبان جدید

هنگامی که میزبان، سند مادر یا ZIP رسمی HAIF را دریافت می‌کند و کاربر درخواست اتصال به مخزن اصلی را دارد، باید پیش از هر عملیات مخزنی این پرسش را نمایش دهد:

**«برای ادامه، عبارت تأیید مالک را وارد کنید:»**

عبارت مورد انتظار:

`احمد نژادحسینی`

پس از دریافت عبارت دقیق، میزبان فقط مرحلهٔ تأیید مالک/قصد کاربر را عبور می‌دهد و به مرحلهٔ احراز هویت واقعی GitHub می‌رود. این عبارت نباید به‌عنوان رمز عبور، توکن، کلید رمزنگاری یا مجوز GitHub معرفی شود.

## 2. محدودیت امنیتی غیرقابل‌مذاکره

این عبارت داخل سند و بستهٔ قابل‌انتقال قرار می‌گیرد و بنابراین برای هر دارندهٔ آن قابل مشاهده است. در نتیجه:
- عبارت فقط یک گیت مکالمه‌ای برای تأیید قصد و جلوگیری از اتصال ناخواسته است.
- دانستن یا واردکردن آن به‌تنهایی هویت شخص را اثبات نمی‌کند و هیچ دسترسی فنی ایجاد نمی‌کند.
- هر میزبان باید احراز هویت واقعی را از طریق GitHub OAuth / connector رسمی همان میزبان انجام دهد.
- میزبان باید هویت حساب GitHub متصل‌شده را با مالک مورد انتظار مخزن، یعنی `ahmadnezhadhosseini64-cloud`، تطبیق دهد؛ اگر connector امکان اثبات حساب را نمی‌دهد، نتیجه UNKNOWN / NOT VERIFIED است.
- هرگز رمز GitHub، Personal Access Token، کلید خصوصی یا Secret را در پیام، فایل سند مادر، ZIP، لاگ یا workspace درخواست یا ذخیره نکن.
- عبارت تأیید را به‌عنوان credential در هیچ API یا درخواست GitHub ارسال نکن.

## 3. ماشین حالت اتصال

1. `PACKAGE_RECEIVED`: منبع دریافت‌شده را به‌عنوان سند مادر یا ZIP تشخیص بده؛ تا تعیین منبع، هیچ عملیات مخزنی انجام نده.
2. `OWNER_CONFIRMATION_REQUIRED`: پرسش دقیق بالا را نمایش بده.
3. `OWNER_PHRASE_ACCEPTED`: فقط در صورت تطبیق عبارت پس از Unicode NFC normalization و حذف فاصله‌های ابتدا/انتها. هر اختلاف دیگری رد شود.
4. `GITHUB_AUTH_REQUIRED`: وجود GitHub connector رسمی را بررسی کن.
5. `OWNER_ACCOUNT_VERIFICATION`: کاربر را به رابط امن OAuth/اتصال رسمی هدایت کن؛ هویت حساب متصل‌شده و دسترسی به مخزن را بررسی کن.
6. `REPOSITORY_READ_ONLY`: ابتدا فقط مخزن `ahmadnezhadhosseini64-cloud/future-ai-palang-footprint` را بخوان؛ HEAD شاخهٔ main، release pointer، receipt، سند مادر و ZIP را با هم تطبیق بده.
7. `WRITE_ACCESS_PENDING`: هیچ نوشتنی از عبارت تأیید نتیجه نگیر. نوشتن فقط از مسیر broker/worker مجاز، روی شاخهٔ محدود `host-intake`، با کمترین مجوز، quarantine و PR برای بازبینی مالک مجاز است.
8. `READBACK_VERIFIED`: پس از هر نوشتن، همان مقصد را دوباره بخوان و محتوا/شناسه/SHA را تطبیق بده.
9. `BLOCKED`: اگر OAuth، connector، هویت حساب، مجوز، broker، sandbox یا read-back در دسترس نیست، دقیقاً همان گیت را BLOCKED / NOT VERIFIED اعلام کن؛ اتصال یا موفقیت را جعل نکن.

## 4. مجوزها و مرزهای نوشتن

- پیش‌فرض همهٔ میزبان‌های تازه READ-ONLY است.
- هیچ میزبان جدیدی حق نوشتن مستقیم روی `main`، سند مادر، release، workflow، manifest اصلی یا workspace میزبان دیگر را ندارد.
- پیشنهادهای نوشتن باید به ورودی قرنطینه‌شدهٔ میزبان برسند و پس از RAHM، تطبیق بین‌میزبانی و تأیید صریح مالک به Child/ Master ارتقا یابند.
- دسترسی نوشتن باید محدود، قابل لغو، وابسته به مقصد و مستقل از عبارت مکالمه‌ای باشد.
- اگر محیط فقط امکان connector مستقیم با مجوز گسترده دارد و broker/branch restriction اثبات نشده، میزبان فقط پیشنهاد یا patch آماده کند و از نوشتن durable خودداری کند.

## 5. استقلال سند مادر و ZIP

هم سند مادر و هم ZIP باید این قرارداد و همان پیام آغاز اتصال را در خود داشته باشند. هرکدام به‌تنهایی باید:
- عبارت تأیید و محدودیت امنیتی آن را توضیح دهد؛
- مسیر اتصال رسمی GitHub را آغاز کند؛
- در نبود connector، راهنمای اتصال از رابط رسمی را نشان دهد؛
- آخرین نسخهٔ مخزن را فقط پس از OAuth/connector واقعی بازیابی کند؛
- به‌روزرسانی و ثبت را تنها با مجوز واقعی و read-back معتبر بداند.

وجود این متن به‌تنهایی اثبات نمی‌کند که OAuth، connector، broker یا میزبان مستقل فعال است.
