## 1. اصل
تمام اسناد و تولیدات جدیدی که تحت ساختار معماری جدید ایجاد می‌شوند، باید تا حد متناسب با ماهیت خود، هویت، منشأ، وضعیت، نتیجه و قابلیت ردیابی داشته باشند.

«متناسب با ماهیت» یعنی فیلدهای غیرقابل‌اعمال حذف یا N/A می‌شوند؛ اما هویت پایه و provenance (منشأ و قابلیت ردیابی) نباید بی‌دلیل حذف شود.

## 2. حداقل هویت اجباری هر تولید
- Unique ID / شناسه یکتا
- Date / تاریخ
- Time / زمان، در صورت امکان ثبت معتبر زمان اجرا
- Owner / مالک
- Location / موقعیت مرجع، در صورت مرتبط‌بودن
- Project / پروژه
- Reference Point / نقطه مرجع یا والد
- Title / عنوان
- Type / نوع تولید
- Status / وضعیت
- Version / نسخه
- Purpose/Problem / هدف یا مسئله
- Governing Rule / قاعده حاکم
- Method/Action / روش یا اقدام
- Result / نتیجه
- Evidence / مدرک
- Verification / راستی‌آزمایی
- Provenance / منشأ و مسیر تولید
- Canonical Repository / مخزن مرجع
- Related Records / سوابق مرتبط، در صورت وجود
- Continuation Path / مسیر ادامه، در صورت ناتمام‌بودن
- Evidence Boundary / مرز دقیق ادعا و آنچه هنوز اثبات نشده

## 3. شمول
این قاعده باید، متناسب با ماهیت، روی موارد زیر اعمال شود:
1. Reference Documents / اسناد مرجع
2. Architecture Records / اسناد معماری
3. Principles / اصول
4. Rules/Protocols / قوانین و پروتکل‌ها
5. Hypotheses / فرضیه‌ها
6. Experiments/Tests / آزمایش‌ها و تست‌ها
7. Evidence Records / سوابق مدرک
8. Production Records / سوابق تولید
9. Checkpoints / نقاط توقف و بازیابی
10. Recovery/Continuation Records / سوابق بازیابی و ادامه
11. Validation Records / سوابق اعتبارسنجی
12. Research/Findings / یافته‌های پژوهشی
13. Evolution/Change Records / سوابق تکامل و تغییر
14. Memory/Retrieval Records / سوابق حافظه و بازیابی، در صورت اعمال
15. هر نهاد یا تولید جدیدی که بعداً به معماری اضافه شود.

## 4. قاعده زبان
نسخه قابل‌فهم برای همکاری انسانی باید فارسی اول و English دوم باشد. اصطلاح فنی انگلیسی می‌تواند حفظ شود و در اولین استفاده معنی فارسی آن روشن شود.

## 5. قاعده اعتبار
هیچ تولیدی صرفاً به‌دلیل داشتن قالب، VALIDATED یا FINAL تلقی نمی‌شود. هر ادعای حل‌شدن، نهایی‌شدن یا بسته‌شدن باید Evidence و Verification متناسب داشته باشد.

## 6. رابطه با فرضیه
اگر بخشی هنوز اثبات نشده است، باید صریحاً HYPOTHESIS / فرضیه باقی بماند. زنجیره‌سازی فرضیات اثبات‌نشده به‌عنوان واقعیت معماری مجاز نیست، وقتی تست واقعی ممکن است.

## 7. تکامل
این قاعده PERMANENT است؛ اما قالب می‌تواند بر اساس تجربه و شواهد تکامل یابد. تغییرات باید نسخه‌دار و قابل ردیابی باشند و تاریخچه حذف نشود.

## 8. هدف مهندسی
هدف این قاعده جلوگیری از تولید اسناد بی‌هویت، غیرقابل‌بازیابی یا غیرقابل‌راستی‌آزمایی و فراهم‌کردن یک مسیر واحد برای تبدیل تولید خام به رکورد مهندسی قابل اتکا است.

## 9. یادآوری سریع از آرشیو
در صورت مشاهده سند یا تولیدی که این مشخصات را ندارد، این سند باید به‌عنوان Reference Reminder بازیابی شود و کمبودها قبل از ادعای نهایی‌شدن مشخص شوند.

The rule applies across reference documents, architecture, principles, protocols, hypotheses, experiments, evidence, productions, checkpoints, recovery/continuation, validation, research findings, evolution/change, memory/retrieval records where applicable, and future artifact types.

**Permanent rule:** Hypothesis remains hypothesis until real testing and adequate evidence/verification justify promotion to a validated architectural fact.
