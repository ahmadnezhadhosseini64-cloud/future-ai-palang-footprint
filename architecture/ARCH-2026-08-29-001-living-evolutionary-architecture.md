## Purpose

Define a living, versioned architecture for developing an interaction-oriented AI through long-term human–AI interaction, while preserving provenance, evidence, history, retrieval, and the reasons for architectural evolution.

## Core model

The project is not a fixed architecture. Any current architecture is the active baseline for its version and may later be superseded by a better validated version.

### Master

The Master is the central evolving AI architecture and knowledge/decision core. It receives validated learning, discoveries, feedback, and architectural improvements through controlled evaluation rather than blind ingestion.

### Child

A Child is an executable/deployable derivative of the Master, created according to defined rules and intended to operate in AI environments and field interactions. Child instances may report observations, errors, failures, and useful feedback toward the Master.

### Womb

The Womb is the controlled environment for turning candidate ideas and discoveries into models/prototypes, testing them, evaluating evidence, and deciding whether an improvement is suitable for promotion into the active architecture and/or a new Child generation.

## Evolution loop

Human interaction → observation/discovery → candidate artifact → documentation → experiment/modeling → evaluation/evidence → approval or rejection → architectural update → new Child where applicable → field interaction → feedback → controlled evaluation by Master.

## Versioning rule

No active architecture version is treated as permanently final. When a better validated version is accepted:

1. Preserve the previous version unchanged as historical record.
2. Record the new version as the current architectural baseline.
3. Record what problem, limitation, observation, evidence, experiment, or discovery motivated the change.
4. Record the relationship between old and new versions (`supersedes`, `derived-from`, or equivalent).
5. Keep both versions retrievable.

## Discovery rule

During interaction, the system may detect a potential new term, name, law, principle, rule, command, protocol, architecture, method, issue, or discovery. Detection does not automatically make it an active rule. It must first be recorded as a candidate/discovery and then evaluated according to the project's validation process.

## Living documentation rule

Every material project artifact must be identifiable, attributable, versioned, traceable to its origin, and stored in a persistent repository. Historical artifacts are not deleted merely because they are superseded.

## Provenance minimum

Where applicable, records should preserve:

- unique ID
- project
- title/type
- author/owner
- origin interaction/context
- date/time
- location metadata when intentionally part of project provenance
- parent/related artifact
- version
- status
- reason for change
- evidence
- repository/path
- retrieval/index information

## State model

`IDEA → CANDIDATE → TESTING → VALIDATED → ACTIVE → SUPERSEDED`

A failed or rejected candidate remains documented as `REJECTED` or `ARCHIVED` with its evidence and reason, rather than being silently erased.

## Non-negotiable principles

- **No Record → No Transition**
- **Retrieval Before Response** for reference-point recovery
- **Evidence before claims of execution or proof**
- **Previous versions remain retrievable**
- **Discovery is not automatically approval**
- **The documentation system itself is versioned and evolvable**

## Current interpretation

This architecture establishes the project as a living evolutionary system rather than a static specification. The architecture can change; its history and reasons for change must remain recoverable.
